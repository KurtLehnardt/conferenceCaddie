# Decisions

This file records the decisions and fallbacks taken while building Conference Caddie, especially where they depart from, or add detail to, `docs/CONTRACT.md`. It is grouped by area.

## Data

- The five category groups in the feed are assigned by title. "All Sessions" is the track group, and every session has exactly one item in it. "Audience Level" is the level group. "End User Programming", "Solutions Showcase Programming" and "Presentation Slides" are flag groups. `scripts/build-data.mjs` exits with an error if a group ever fits none of these roles.
- Slides are confirmed. Category item 523121 is "Slides Attached" and question 137003 is "Presentation Slides". `slides_url` is the answer to question 137003 when it starts with http or https, and `has_slides` is true exactly when `slides_url` is set. That gives 112 sessions with slides, all of them talks.
- The feed's "Slides Attached" category is stale: only 54 sessions carry it, but 112 have a slides link. The `flags` array therefore includes "Slides Attached" whenever a slides link exists, so the flag always agrees with `has_slides`.
- The America/Denver offset is computed per instant with `Intl.DateTimeFormat` (`timeZoneName: "longOffset"`), not hardcoded. KubeCon + CloudNativeCon North America 2026 runs 9 to 12 November, and the few items dated 8 November are the Maintainer Summit and registration, so every offset is -07:00. `day`, `start_minutes` and `end_minutes` come from the venue-local clock.
- Kind rules, where the first match wins: an item is `housekeeping` when its description is empty and its title is an opening, closing, welcome, remarks or wrap-up; `break` when it has no speakers and its title (the part before any " | ") names coffee, lunch, breakfast, registration, a badge, a coat or bag check, snacks or a reception, or its track is Breaks or Registration; `talk` when it has at least one speaker; and `ambient` otherwise.
- The brief's talk rule needs both a speaker and a description, but four real sessions have speakers and no description (three keynotes and CNCF Bingo). They are kept as talks with an empty abstract, because dropping real keynotes from search is worse. This is a deliberate departure from the brief.
- Only the title before " | " is tested for break words. Without this, co-located events with the suffix "SEPARATE REGISTRATION REQUIRED" were wrongly classified as breaks.
- An item is sponsor content when its track is "Sponsor Demo Theater" or "Sponsor-hosted Co-located Events", or its title contains "sponsored by", "sponsored keynote" or "in-booth demos". Descriptions are not used, because a boilerplate sentence about sponsored content appears in many unrelated descriptions. That gives 62 sponsor items, of which 39 are talks. No keynote is flagged as sponsored.
- Titles and descriptions are trimmed, line endings are normalised to LF, and an empty description becomes an empty string. Track names keep the feed's emoji prefixes, for example "📚 Tutorials".
- The counts are 484 talks, 76 ambient items, 21 breaks and 19 housekeeping items, 600 in total. `DATA_NOTES.md` has the details.

## Search

- **Index.** In the MVP the real index was `caddie-talks-v1` behind the alias `caddie-talks`. Phase 2 moved the alias to `caddie-talks-v2`, which holds every feed item of every searchable conference; every search filters on `conference` and `kind: talk`.
- **Mapping.** The mapping uses `dynamic: false` instead of `strict`, so an extra field in `talks.ndjson` is stored in `_source` but never blocks ingestion. `title`, `abstract` and `speaker_taglines` use the english analyzer and `speakers` uses the standard analyzer.
- **Embedding model.** The `semantic_text` field has no explicit `inference_id`, so it uses the cluster default, `.jina-embeddings-v5-text-small`, a dense embedding model. No chat, completion or rerank endpoint is used anywhere.
- **No fallback was needed.** Semantic search, `copy_to` into `semantic_text`, an `rrf` retriever with a filter, aggregations with `rrf` and highlighting with `rrf` all work in one request on Elasticsearch 9.5.6. The lexical-only fallback was not taken.
- **Semantic retriever.** The contract asks for a `semantic` query. The server instead runs a `knn` query on the `semantic_text` field with `k` 50 and `num_candidates` 200, and Elasticsearch builds the query vector from the field's own inference endpoint. A `semantic` query on a dense field sizes its neighbour set from the request size, so `total` would change when `size` changed; a fixed `k` avoids that. This is still hybrid search with the same model, combined with the lexical query by an `rrf` retriever (`rank_window_size` 50, default `rank_constant`).
- **kNN pre-filter.** The knn query is pre-filtered only by the base filters: talks only, the conference, the start-time window and sponsor hiding. Day, track, level and slides selections are applied afterwards by the `rrf` retriever's filter. This keeps the nearest-neighbour set the same whatever the user selects, so the count shown next to a facet value is exactly the total the user gets after selecting it. The cost is some semantic recall under a narrow selection.
- **Lexical matching.** The `multi_match` over `title^2`, `abstract`, `speakers` and `speaker_taglines` uses `minimum_should_match: "2<60%"`. Queries of one or two terms must match every term, and longer queries must match 60% of them. Without this, a long natural-language query such as "making my cluster greener and using less energy" matched hundreds of talks on a single common word, and the right talk (the Kepler lightning talk) fell to rank 18. With it, the Kepler talk ranks first and no tested query got worse.
- **Facets and total.** Let M be the documents the main query matches: for a text query, the lexical matches plus the 50 nearest neighbours among documents that pass the base filters; in browse mode, every talk. Let B be the base filters and S(g) the selection in facet group g (day, track, level, has_slides). Then `total` = |M ∩ B ∩ every S(g)|, and the counts for group g are a terms aggregation over M ∩ B ∩ S(every other group). They are computed in one `_msearch`: the main query plus one size-0 query for each facet group that has a selection. `post_filter` is not used, because it would run after the neighbour search and lose recall. Because the start-time window is a base filter, the Morning and Afternoon totals of a text query need not add up to the unfiltered total; the time chips show no counts, so the UI shows no contradiction.
- **Text-query totals.** A text query's total is the lexical matches plus up to 50 semantic neighbours, so typical totals are about 50 to 120 even for a narrow query.
- **Saved talks.** The MVP removed saved talks and every talk overlapping them in time. The direction change of 2026-11-09 removed that filter: `saved_talk_ids` is still validated but never filters anything.
- **Browse mode.** An empty query is a bool filter query sorted by `start` ascending, then `talk_id`, by Elasticsearch.
- **Evidence.** Evidence prefers a highlighted abstract fragment, then a highlighted title, then the best semantic chunk, then the start of the abstract (`no_match_size` 200), then the title. The title reaches the semantic field as its own chunk through `copy_to`, so a semantic chunk that only repeats the title is skipped in favour of the best abstract chunk. The semantic highlighter ignores `encoder: html`, so the server HTML-escapes the semantic chunk itself, collapses its whitespace and cuts it to 300 characters at a word boundary. This only chooses the evidence text and never changes ranking.
- **Ranking.** All ranking happens in Elasticsearch. The server never reorders hits, and the browser never filters or reorders results.

## API

- Known values for `day`, `track` and `level` come from terms aggregations over `kind: talk` and are cached in memory for 10 minutes. A failed fetch is not cached. Track or level values that appear on no talk (for example "Breaks") get a 400, so the UI only offers values taken from the response facets.
- A selected day, track or level value with no matching documents is still listed in its facet with count 0, so the UI can show it as selected. `has_slides` always returns both true and false. Day is sorted by value ascending; track and level keep Elasticsearch's count-descending order.
- Every Elasticsearch failure returns `{"error":"Search is temporarily unavailable"}` with status 502. The Elasticsearch error body is never forwarded, and the log line holds only the status and a short cause such as "timeout".
- Each text query runs one embedding inference per `_msearch` item: one, plus one for each facet group that has a selection, so at most five.
- The request log has one line per request with the method, path, status and duration. It never holds search text, headers, bodies or keys. This was checked on the local run log.

## Frontend

- The app uses Vite 8, Preact, TypeScript and `lucide-preact`. JSX is compiled with Vite's built-in oxc option instead of `@preact/preset-vite`, so the only runtime dependencies are `preact` and `lucide-preact`.
- The search state lives in the App component, so results survive tab switches. Marking or unmarking a talk does not re-run the search, so a card never vanishes under the user's finger. The search re-runs on any query, filter or conference change. (Before the people-first change, cards showed an overlap hint and the app had a Build my agenda button; both were removed.)
- Normal searches request 20 results. Track and level chips equal to "Not specified" are hidden on result cards. Facet options with a zero count are hidden unless selected, and a selected value missing from the facets is shown with a count of 0.
- The accent color is #2457D6 in light mode and #85A8FF in dark mode. The `theme-color` metas are #f5f6f8 and #0f1115, and the app rewrites both when the user forces a theme.
- The app version comes from `web/package.json` through a Vite define.
- Plain headless Chrome could not render a 390px-wide viewport, so the frontend was screenshotted with `playwright-core` driving the installed Chrome at 390x844 in light and dark mode and at 1280 wide. No browser was downloaded.
- The production bundle has no mock data: `grep -r MOCK_FIXTURE_DO_NOT_SHIP web/dist` finds nothing, and the smoke bundle check confirms it.

## Deploy

- Both Dockerfiles use `node:26-slim`, which matches the local Node 26. If 26 is not the current LTS line, the `FROM` lines can change to `node:24-slim`.
- The root Dockerfile builds `web/` with `npm ci` against the committed `web/package-lock.json`, then copies only `package.json`, `server/` and the built `web/dist` into the runtime image. `data/` and env files are never copied. The image was built and run locally on port 8084, where `/api/health`, the app and a search all worked.
- `.dockerignore` and `.gcloudignore` are identical and exclude `data/`, `docs/`, `.claude/`, env files, logs, `node_modules`, `web/dist` and credential patterns.
- `scripts/deploy.sh` always runs the service as the dedicated `caddie-runtime` service account, which holds no project-level roles. The service runs with `--min-instances 0`, `--max-instances 2`, 1 CPU and 512 MiB, so it scales to zero when idle.
- The first deploy was blocked on Google Cloud authentication. It was completed on 2026-11-09 by the people-first integration; see the section on that deploy below.
- Colima was started during the deploy track so that Docker could run. It also started an existing, unrelated container. It was left running.

## Security

- The admin key in `ELASTISEARCH_API_KEY` is used only for index setup, ingestion and local runs, where it is passed inline in the command or through a child process's environment. It is never written to a file, printed or deployed.
- The deployed service uses only two scoped keys from Secret Manager, minted by `scripts/create-es-keys.mjs` as described in the section on the people-first deploy below. It never holds the admin key.
- The browser never holds a key and never calls Elasticsearch. The server sets the contract's Content-Security-Policy and the other security headers on every response, and the built app has no inline scripts and no external origins.
- Every commit was checked with `git diff --cached` against the values of `ELASTISEARCH_API_KEY` and `GC_API_KEY` before it was made. The smoke test scans `web/dist` for those values and for key-shaped strings.

## Direction change: people first, no scheduling (2026-11-09)

- The user changed the product's purpose. Conference Caddie now answers "Who here should I talk to?" first and "Which talks would I like?" second. It is not a scheduling tool, because each conference's official schedule already handles calendars and clashes.
- Removed: "Build my agenda", the saved-talk `must_not` time-overlap filter in `server/search.mjs`, its effect on facets, the "Overlaps a talk in your agenda" hint, every clash warning and every "conflict-free" or agenda-building wording. The stretch items "shareable agenda" and anything about agenda building are dropped.
- "Saved agenda" becomes "Interested": a plain list of marked talks in time order, on the device only. `POST /api/search` still accepts `saved_talk_ids` so older clients keep working, but no longer filters on it.
- Every talk links to its official session page with the label "Add to my schedule on the official site".
- Navigation order is People, For you, Search, Interested, and the home screen leads with people and suggested talks.
- New parts: conference topics built from talk titles, profiles with topic chips, People to meet, talk circles and Talks for you, all described in `docs/CONTRACT.md`.

## Phase 2: any Linux Foundation conference on Sessionize

- Phase 2 means "works for any Linux Foundation conference whose schedule is on Sessionize". Letting people sign in and add their own conferences is deferred to a separate project, saved in `docs/FUTURE_user_added_conferences.md`. The conference document keeps a `source` field, with `sessionize` as the only value, so that project is not blocked.
- Conferences are discovered from the LF events list and each schedule page's `data-sched-config`. The API code is never guessed. Events without a Sessionize config or without a schedule are listed as "Schedule not available here yet" with a link to the official schedule.
- The slug is derived from the event name plus the start year, because the LF list has no slug.
- The time zone comes from Sessionize's `api/data` Windows zone, mapped to IANA through the CLDR table in `data/windows-zones.json`, else from the operator file `data/conference-overrides.json`. It is never guessed. PyTorch Day Japan's Sessionize site is unpublished and gives no zone, so the override maps it to Asia/Tokyo.
- Track is the group named by `primaryFilterTitle`, level is a group whose title contains "level", and every other visible group becomes generic tags stored as a U+001F-separated keyword plus a display object. No KubeCon-specific category name or id remains in code.
- Sponsor detection was generalised to any category item or group named "sponsor", which now also flags sponsored keynotes (72 sponsor items on KubeCon).
- `presentationSlidesQuestionId` in the config is a question title, so it is matched as a title.
- Talk ids are `{conference}:{session_id}`. The old `caddie.saved.v1` data is not migrated.
- Ingestion is safe to re-run: unchanged sessions are skipped by `content_hash`, metadata-only changes use a Bulk partial `update` that omits `title` and `abstract`, and the Update API is never used because it re-runs inference.
- `filters.level` may be an empty array for a conference without a level group, so the frontend can always send the full filters object. `saved_talk_ids` must carry the request's conference prefix.

## Topics

- Topics are analysed in Elasticsearch in a temporary work index per conference: a curly-apostrophe fix, the standard tokenizer, lowercase, stop (`_english_` plus `config/topic-stoplist.txt`), a possessive strip, a filter that drops numbers and single characters, and shingles. The stop and length filters leave position gaps, so a bigram never spans a removed word. Counting uses a terms aggregation on the analysed title with `fielddata`, so neither the `_analyze` nor the script-counting fallback was needed.
- Labels come from `_mtermvectors` offsets on the original titles; the most common casing wins.
- Lucene's English stopword list is short, so words such as "from", "what" and "when" passed the analyser. Per-conference fix-up files in `data/topics/` remove them and merge plurals and synonyms as aliases (for example k8s into Kubernetes). Fix-ups exist for KubeCon, MCP Dev Summit Nairobi and PyTorch Day Japan. A merge never creates a target that occurs in no title; a target below three talks becomes a topic when its aliases bring it to three.
- Talks get their `topics` through a Bulk partial update, so tagging never re-embeds anything. Topic documents are rewritten only when they differ, so a re-run writes nothing.
- Topic quality pass (2026-11-09), after seeing the live KubeCon list. The top 12 held "Cloud", "Native" and "Cloud Native" as three chips, plus "Cluster", "Scale" and "Platform". Three changes: (1) a single word is collapsed when at least 75% of the talks holding it hold it inside a kept two-word topic, so "cloud" (28 of 37 talks inside "cloud native") and "native" go while "llm" (13 of 20 inside "llm inference") stays; (2) the possessive strip now runs before the stop filter, so "what's", "here's" and "let's" are removed by the plain words in the stoplist; (3) generic English words moved out of the KubeCon fix-up into the global stoplist, and domain-generic words for this audience ("cluster", "scale", "production", "workloads") sit in the KubeCon fix-up as removals, which keeps their two-word topics such as "multi cluster". The rule and threshold were tuned with an offline approximation of the analyser on the committed KubeCon titles; the live run should be checked against the top 20 it prints. "AI" and "Kubernetes" still appear in 114 talks each and match everyone; weighting rarer topic overlaps higher in matching is an open follow-up.

## People and talk circles

- There is no sign-in. On first opt-in the device generates a random `profile_id` and secret; the server stores only `sha256(secret)` and requires the secret for every write and every circle read. The first write uses `op_type: create`, so an existing profile can never be taken over.
- Conference-wide matches are reciprocal: a person sees matches only while they are visible conference-wide themselves. Sharing for one talk and conference-wide visibility are independent; sharing never puts a profile in conference-wide matches.
- A match reason names a shared talk only when the requester has also shared for it, so matches never reveal a circle the requester has not joined.
- The semantic people retrievers use a `knn` query on the `semantic_text` fields, as talk search does. Circles add a match-all retriever so every sharer is listed, below everyone who shares something with the requester.
- Profile writes whose text is unchanged use a Bulk partial update without the text fields, so toggling visibility or sharing never re-embeds anything.
- Profiles expire at 23:59:59 on the conference's last day in its own time zone, and every people query filters on that.
- The 30 seeded sample profiles for KubeCon are labelled "Sample · ..." with the contact note "Sample profile, not a real person". Several share for the same three talks. Sample topics that are not topics of the conference are skipped with a warning.
- Rate limits: people writes 20 per minute per device and 60 per IP; matches and circle members 30 per device and 90 per IP, because many attendees share a conference NAT; counts, recommendations and topics 60 per IP.
- Share for all (2026-11-09). Toggling sharing talk by talk was tedious, so the Interested screen has "Share for all" and "Stop sharing for all", plus a device-only preference "Share automatically for talks I mark, and stop when I unmark" (`share_new`). The preference is off by default, shows the sharing notice the first time, and catches up on the talks already marked when turned on. It is a device setting, not a server field: the server still receives one explicit `shared_talk_ids` list, and nothing is shared the user did not mark. The profile's visibility card also gets "Stop sharing for all talks". The 50-talk server limit is kept; "Share for all" shares the first 50 and says so. Writes to the shared-talk list run one at a time on the device, so two quick taps cannot read the same stale list and overwrite each other; the preference is stored only after its catch-up share succeeds; and a share that could not happen (no name yet, the 50-talk limit, a failed write) is shown as a toast on the screen where the talk was marked.

## Talks for you

- Elasticsearch 9.5.6 supports per-retriever `weight` in `rrf` in the wrapped form `{ "retriever": ..., "weight": n }`. Learn topics and interests have weight 1; speak topics and expertise have weight 0.5.
- Superseded for speak topics and expertise by the next section: they are no longer used for talk recommendations.
- Suggestions exclude ended talks (`end > now`) and talks the user already marked. Nothing in the request is stored or logged.
- `circle_count` uses the people key. If the people index cannot be read, every count is 0 and the suggestions still return.

## Review fixes (2026-11-09)

- The rate limits keyed on the first `X-Forwarded-For` entry, which the client chooses, so rotating it removed every per-IP limit. One shared `clientIp` in `server/ratelimit.mjs` now takes the last entry, which Google's front end appends on a direct `run.app` request, caps it at 45 characters (the longest textual IPv6 address) and falls back to the socket address. The people, recommendations, topics and suggest endpoints all use it.
- `POST /api/search` now has the same per-IP limit of 60 per minute, because every text search embeds its query.
- Both deployed keys were re-minted without `monitor_inference`, and the old keys were invalidated. A test with a throw-away role, user, key and a two-document `caddie-dev-*` index showed that a key with no cluster privileges can still index into `semantic_text` fields (single-document and Bulk), run `knn` with a `query_vector_builder` and run a `semantic` query, while `GET /_inference/_all` and a direct inference call return 403. Elasticsearch runs semantic_text inference on the user's behalf without checking the inference privileges. `scripts/create-es-keys.mjs` now checks that both keys are refused on the inference API.
- Expired profiles are now deleted. The server runs a people-key delete-by-query on `visible_until < now` (and on documents without `visible_until`, which are never live) at start, which covers every cold start, and then hourly on an unref'd timer. The request does not ask for a refresh, because the people key has no `maintenance` privilege and every query already hides expired documents. `npm run people:purge` runs the same delete as an operator step after a conference.
- The People, For you and Profile screens are keyed by the conference slug, so switching conference starts each with fresh state. The ended-talk banner ignores a pinned talk from another conference. Any navigation closes the conference switcher and the talk sheet.
- The visibility switch on the profile shows the requested state at once and a "Saving…" line beside it while the first save runs; on failure it returns to the stored state and shows the error.
- The topic findings (filler words, the colon-spanning "Theater: Agent", "Multicluster" next to "Multi-Cluster") are covered by the topic quality pass above, which landed on `main` at the same time. Its KubeCon fix-ups and stoplist were re-applied to the live index with `npm run topics` (KubeCon now has 96 topics; MCP Dev Summit Nairobi and PyTorch Day Japan were unchanged), because the smoke test checks the live list against the new stoplist.
- That re-run removed topics that stored profiles already held (for example "open", "native" and "scale"). A save that still sends such a topic is no longer rejected: a topic the stored profile already holds but the conference no longer lists is dropped, and only a new unknown topic gets 400.
- The old `caddie@` service account lost `secretAccessor` on `caddie-es-readonly` and `caddie-es-people`. Its project-level `roles/admin` binding is unchanged and remains the owner's decision.

## Offline mode (2026-11-09)

- Offline mode, stretch item 6 of the original brief, was pulled forward for the demo's airplane-mode beat.
- `GET /api/schedule?event={slug}` exports one conference's `kind: talk` documents from Elasticsearch with the read-only key: public feed fields, topic labels and an abstract trimmed to about 400 characters. It is cached for five minutes in the server's memory and in HTTP caches, gzipped when the client accepts it, and limited to 20 requests per minute per IP. KubeCon's export is about 500 KB, or about 125 KB gzipped.
- `web/public/sw.js` is registered only in production builds, as `/sw.js?build={id}`, where the id is the hashed file name of the entry script. ## Time phrases in search (2026-11-09)

- Stretch item 2 of the original brief. `POST /api/search` recognises "morning", "afternoon", "before lunch", "after lunch", "day N" and weekday names in the query with a fixed, rule-based table in `server/phrases.mjs`. No model is involved. A recognised phrase leaves the search text, so the retrievers see only what remains, and it becomes a filter clause in the base filters, so totals and facet counts already reflect it. An empty remainder browses in time order.
- "Morning" means the talk starts before 12:00 and "afternoon" at 12:00 or later, the same boundaries as the Time chip. "Day N" counts from the conference's `start_date` and is recognised only while that date is no later than `end_date`. A weekday name stands for every day with talks that falls on that weekday and is recognised only if one exists. Several day or weekday phrases are alternatives; every other phrase narrows the result.
- Lunch comes from the conference's own `break` items whose title matches "lunch": one Elasticsearch aggregation per conference, cached for ten minutes, gives each day's earliest start and latest end. "Before lunch" means starting before that day's lunch begins, and "after lunch" means starting once it has ended. A day with no lunch item matches neither phrase, and a conference with no lunch item does not recognise them, so the words stay in the text. The nominal lunch hours are never invented.
- The response carries `search_text` and `time_phrases` (`key`, `label`, `days`, `applied`). The app shows each applied phrase as a chip with a remove control. Removing one adds its key to `ignore_phrases` on the next request: the phrase still leaves the text but no longer filters. The app forgets a key once the text no longer holds the phrase. Offline keyword search does not interpret phrases.
- The smoke test gains m1 (a "tuesday afternoon" query is filtered and can be removed, checked against the committed data) and m2 ("after lunch day 2" is bounded by that day's lunch break from the committed data, and unrecognised phrases stay in the text).

## Import my schedule (2026-11-09)

- **Scope.** The user asked for a way to import a personal schedule exported from anywhere (PDF, CSV, plain text, .ics or JSON) and match it to the conference's real talks, with Elasticsearch as the matching engine. This is new, user-requested scope. The deferred "upload" item was about importing conference data (user-owned conferences); this feature adds no conference data and stores nothing on the server. It also takes no URL, so "server-side fetching of user URLs" stays deferred.
- **Endpoint.** `POST /api/import/schedule` takes `{ event, filename, mime, content_base64 }` or `{ event, text }`, as described in `docs/CONTRACT.md`. The upload lives in memory for one request. Nothing is indexed, stored or logged: the request log keeps its one line of method, path, status and duration, and the only error line is an Elasticsearch status code or a count of failed searches. The body limit of about 7.2 MB applies to this route only; every other route keeps its own small limit. An instance runs at most four imports at once, because each holds the upload in memory several times; a fifth gets 503 with `Retry-After`. The rate limit is 10 per minute per IP.
- **Extraction in Elasticsearch.** Documents go through the `attachment` ingest processor (Apache Tika) in `POST _ingest/pipeline/_simulate` with an inline pipeline, so the document is parsed and returned but never indexed. `indexed_chars` is 200000 and `remove_binary` is set. Word, OpenDocument, RTF and legacy Office files are accepted as well, because Tika reads them at no extra cost; the file picker still advertises PDF, CSV, text, .ics and JSON. The type is sniffed from the content, not the name. The cluster's audit log is disabled and `emit_request_body` is false, so the simulate request body is not written to an audit log either.
- **Parsing.** iCalendar, CSV and JSON are parsed in the server with Node built-ins (no new dependency). Text and extracted documents are split into items at blank lines, leading times and date headers. Wrapped lines are merged; times, dates, room lines, URLs, e-mail lines and "Add to calendar"-style lines are dropped; `Speakers:` lines become speaker text. A time range is often followed by a one-character session-type badge in Sched's "my schedule" PDF, which is removed. The part after a final ` - ` is treated as the speaker list, so the part before it is offered as the title.
- **Candidates.** A candidate needs three words, at least two of them content words, so short fragments and name lines are not sent. The title of a structured entry (CSV, ICS, JSON) or of an item that starts with a time may have two words, because those are clearly titles ("Harbor ContribFest"); two-word candidates can only match as title words, which needs both words. Each item's preferred text goes first, then each item's second choice, and so on, up to 300 candidates, so a long file cannot crowd out later items.
- **Matching in Elasticsearch.** One `_msearch` runs one search per candidate over the conference's `kind: talk` documents, size 1. Each search is a bool of named queries: `exact_title` (`match_phrase` on `title`), `title_words` (`match` on `title` with `minimum_should_match` `3<75%`), `speaker` (`match` on `speakers` with the item's speaker text, two words minimum) and `time` (a one-minute range on `start` when the file gave a date and time). One of the two title queries must match. `exact_title` is sent only when the candidate has three content words, because a short phrase appears inside many titles. The confidence label comes from `matched_queries`: exact title, then title words plus speaker, then title words plus time, then title words. Per talk the server keeps the hit with the highest Elasticsearch score. It never scores or re-ranks; the review list follows the order of the file. Ended talks are included, because a schedule of a running conference holds talks that already happened.
- **Limitation.** `match_phrase` cannot tell an exact title from a phrase inside a longer title, so "exact title" means the candidate appears word for word in the title. The talks index has no keyword subfield for titles, and adding one would need a reindex that re-embeds every talk.
- **Key privilege.** The deployed read-only key needed one more privilege. A throw-away role, user and key on the cluster showed that the raw cluster action `cluster:admin/ingest/pipeline/simulate` is enough, and that the named privilege `read_pipeline` would also allow reading every stored pipeline, so the read-only role now holds only that action. `scripts/create-es-keys.mjs` adds it and gained `--only <secret>`. Only the read-only key was re-minted (`--only caddie-es-readonly`); the people key is unchanged. All 18 checks passed, including that both keys are still refused on the inference API, that the read key can extract text in a simulated pipeline but cannot read or create pipelines, and that the people key cannot run a simulated pipeline. The superseded read-only key was not invalidated; it holds fewer privileges than the new one.
- **Caveat on that privilege.** Any key that may simulate a pipeline may put any processor in it, including an inline `inference` processor, and Elasticsearch runs it without checking the inference privileges. This was verified only with the embedding model, so the cluster's chat, completion and rerank endpoints were never called. The server only ever sends its own fixed attachment pipeline and never takes processors from a request, and the key never leaves the server. This is the cost of extracting PDFs in Elasticsearch as the user asked.

## Find & connect (2026-11-09)

- The product does two things: find the people whose own words about what they have built match what you are stuck on or want to learn, and sync up in person. Sched already has attendee lists, a my-code profile share and messaging, so Caddie builds none of those; chat is a stretch goal that exists only to hand off a conversation Caddie started in person. See `docs/FIND_AND_CONNECT_SPEC.md`.
- **Search is open to everyone visible; presence only decides when.** `POST /api/people/matches` takes free text and an `around_now` switch. Finding people never requires being findable yourself.
- **Rare beats common.** One `rrf` retriever fuses a semantic leg and a lexical BM25 leg over `expertise` and `about` with the topic legs; the specificity rule treats a hit found only through top-10 topics as broad: dropped from text searches, kept in "Around now" only when both people are in the same zone, ranked last and labelled. The matched passage is returned as `evidence` and becomes the first reason. There is no result cap; pages of 20.
- **Zone and rendezvous over GPS.** Browser GPS is 20 to 100 m indoors, so presence is a self-reported zone (the conference's room names plus five fixed zones) with an optional spot line, and a meet ends in a named meeting point and a "how to spot me" line. Coordinates are a later, optional ranking signal, never a radar. A zone deep link (`#/here/{zone}`) lets anyone print a QR code for a table or booth.
- **Consent at every step, everything expires.** Presence turns itself off after 60 minutes (and after 5 minutes in the background). Asks are now-only: you can ask only someone who is around, the ask expires in 15 minutes, and accept means now. A match who is not around is watched, not booked; the app says when they are around so you can ask then. Anything else is a meeting booking, which this product refuses. An accepted meet is active for 20 minutes; afterwards only participants, topic, state and times are kept. In the same zone the path from noticing to handshake is one tap: "Wave" sends the ask with a default note, accept makes the shared zone the meeting point, and both how-to-spot-me lines show at once. Zone and spot are returned only between two people who are both around; spot-me only inside an active meet to its two participants. Block is symmetric and silent, with an identical 403 whichever side blocked, and ends any open meet between the pair. Three "Not now" in a day pauses a requester until the next day; that count lives in Elasticsearch, not a token bucket, because it has to survive a restart and mean "until tomorrow".
- **Presence lives on the people document** as partial updates that never touch the embedded text, so the search is one query and position pings cost zero model calls. Every new index is `caddie-people-*` so the existing people key covers it.
- **Filtering is a wordlist for now.** `config/moderation-words.json` (seeded from LDNOOBW, CC-BY 4.0) checked after NFKC, lowercase, diacritic stripping and leet substitution; URLs other than linkedin.com are refused. The classifier and the percolator index come in the next phase. Copy says "filter", never "safe".
- **Reviewed as a counter-positioning to Brella and Grip**: no accounts, no onboarding forms, no scheduling, no hosted buyers, no sponsor or lead features, no organizer dashboards, no white-label, no push, no Bluetooth. Those are permanent refusals, not deferrals.
- **Ultrasonic proximity (18.5 to 19.5 kHz chirps) evaluated and declined.** It would refine a position only after two people have already agreed to meet and can see each other, while the serendipity use needs continuous microphone capture that iOS Safari does not allow in the background and that would light the mic indicator for the whole conference. Phone speakers roll off above about 17 kHz, pockets and hands cut 20 to 30 dB, halls are loud and reflective, and the band is audible to many young people. An unsolicited acoustic token also lets any recorder log who stood near whom, which breaks the rule that nothing about where you were is kept. Sub-room proximity, if ever wanted, is the tabled Android companion with Bluetooth.
- **GPS bands: coordinates are a ranking signal, not a radar, and bands come before consent.** The position is optional (a second step after the zone, `watchPosition` in the foreground only, at most one write every 15 s, stopped when the page is hidden and with presence), rounded to 5 decimals, dropped above 200 m accuracy and cleared with presence, so the server never holds a trail. It does two things. First, it is one more `rrf` leg (`distance_feature`, 100 m pivot) that moves nearby people up the list, which is what "nearby people rank first" meant all along; it counts neither for nor against specificity, because standing close by is not experience. Second, before anyone has agreed to anything, another person learns only a band (`same_zone`, `near`, `around`, `venue`) and only while both are around: a band tells you whether walking over is realistic without letting anyone draw a circle on a map, and a list of bands cannot be turned into a position by moving around, which a list of distances can. A review showed that this promise did not hold as first built: the bands compared precise positions, and the requester's own position is whatever their client sends, so three bisections of the 300 m edge (about 36 spoofed presence writes and reads) put a stranger within 0.2 m of someone. It is now enforced by the data the bands are computed from: every fix is stored with the centre of its ~100 m grid cell (`presence_cell`, latitude snapped to 0.001°, longitude to the same distance at that latitude), `near` means the same cell and `around` means cell centres under 300 m apart, and the ranking leg is a `distance_feature` on the cell with the requester's cell as origin; no people search reads another person's precise position any more. So whatever positions a requester claims, two people anywhere in the same cell answer every probe identically, and the most anyone can learn without a meet is which cell someone is in. A second, weaker guard drops a fix (zone-only, no error) that implies a move above 7 m/s from the device's previous fix of the last ten minutes, which stops the instant jumps such probing needs; it can be sidestepped by clearing the position first, which is why the cells, not the speed check, are the guarantee. A real distance (to 10 m) and a bearing exist only inside an active meet, only on the meet read, only for its two participants, and only because both already accepted each other; the inbox, the action responses and every other route return neither, and no route anywhere returns a coordinate. The zone and the meeting point stay the plan; the arrow and the distance are a rough aid underneath them, which is why the meet screen says "Positions indoors are rough." and puts them below the rendezvous and the spot-me lines. The notice adds the one sentence that covers it: "Your exact position is shared only with someone you accept, only until you meet, and never stored after."
- **Passive by default: the zone confirmation replaces the timer as the safeguard.** The normal state is a phone in a pocket, pulled out in the coffee line, so a stale zone is the main failure, not a forgotten switch. The presence switch now offers "For an hour" (the MVP behaviour: off after 60 minutes and after 5 minutes in the background) and "Until I turn it off today" (`PUT /api/presence` with `until: 'day'`, `presence_until` at the end of the conference day, capped at `visible_until`). In the day mode backgrounding keeps presence, and the check moves to the moment that matters: whenever the app comes back to the foreground (or is opened) with a zone last confirmed more than ten minutes ago, the top of the People tab asks "Still in {zone}?" with Yes, the four likeliest other zones and "Other…"; one tap confirms or moves the zone and records the time, and closing the row counts as a confirmation. The same row appears in the hour mode, so the ten-minute check is the privacy mechanism in both: a person is never shown in a zone they have not vouched for recently while using the app. The chips are ordered by recency of use on this device; the schedule has no room coordinates, so a position cannot reorder them yet, and the row never shows one. The server adds only the `until` mode; the confirmation state (`confirmed_at`, `confirm_pending`, `recent_zones`) lives on the device.
- **Filter: percolator rules plus a classifier, failing closed (Then phase).** The wordlist moved into `caddie-people-rules-v1`, a percolator index whose `text` analyzer does the leet, case and diacritic folding, so every rule is an Elasticsearch query (`match_phrase`, or `regexp` for `re:` entries), `--reload-rules` changes them without a deploy, and the same store that holds the people holds the rules; the in-process wordlist stays as the fallback whenever the percolate call fails, so the MVP behaviour is the floor. A wordlist alone misses insults and threats spelled with ordinary words, so after the rules pass, Google Cloud Natural Language `moderateText` (a classification API, no generative model, reached with the runtime service account's own token, no new secret) scores the line: at or above 0.8 in a watched category it is rejected with the same filtered message, at or above 0.5 it is **held**: stored pending, shown only to its author, reported as `classifier`. Any classifier error or timeout holds too, never accepts, because the cost of a held line is a few minutes' delay for one person while the cost of a slur reaching a stranger is the product's promise; "Waiting for the filter; it will appear shortly." is the only copy for that. Caveat: `moderateText` is English-centric and a stretched or non-English insult can pass it, so the rules stay the first line and the report button the last. Copy says "filter", never "safe".
- **Home is Around (Then integration).** The spec's "default state is passive" means the first thing a person with presence on should see is who is around, not a search box. So the People tab now opens on the Around view while presence is on: "Still in {zone}?", the nudge banner, the presence card, then "Who's around" with the people in my zone first and the rest of the venue after, each group in the server's order (the client only splits the page by the `zone`/`proximity` the server sent; it never re-ranks within a group), and the text search collapsed to a single "Find someone specific" button. The list is fetched when the tab opens, refreshed quietly every 60 s while the tab is visible (first page only, no flash), and fetched again when "See who" on a nudge lands on it, because the person it names arrived after the list loaded. Presence off keeps the old layout with the switch on top. The switch label dropped "(while the app is open)" because presence can now stay on for the day, and the notice ends "It turns off by itself after an hour unless you choose to stay around for the day."
- **Held lines (Then integration).** `connect.mjs` awaits `moderate()` for spot, note and spot-me lines. A `hold` is stored with `presence_spot_pending`, `note_pending` or `spot_me_pending`, shown only to its author, answered with `held` on the 200, and filed as one report by the fixed reporter `classifier`, which counts as one of the two reports that hide a target. Nothing re-checks a held line: the author's next write of that field replaces it, presence off or the end of the meet clears it, and the operator CLI handles the rest.
- **A hide outlives the profile document (review fix).** Turning both visibility choices off deletes the people document, and the create path wrote no report flags, so a profile hidden after reports came back visible by toggling visibility off and on while its reports stayed on file. Now every create and every full reindex counts the person's reports (one size-0 search with a terms aggregation on `target_kind`, `reportCountsFor` in `server/report.mjs`, because the profile and spot counts are both named by the same `ref`) and sets `hidden` and `spot_hidden` again at two reporters; `hidden_for_owner` in the response follows. It fails closed: when the count fails, a reindex keeps the flags the document carries and never unhides, and a create answers 502 instead of making the profile visible on a guess. Only the operator's `--unhide` (which deletes the reports) or `--purge` lifts a hide; an operator `--delete` of a hidden profile no longer lets it come straight back visible either. The push nudge also stops at once for a trigger that is hidden after reports or is a sample profile, and never pairs anyone with a sample profile.

## Web Push nudges (2026-11-09)

- **Push is the unlock for the pocket case.** The product's default state is passive: the phone is in a pocket in the coffee line, and the app should notice that someone worth talking to is right there. An in-app nudge only reaches someone who is looking at the app, which is the one person who did not need it. The spec deferred Web Push to "the next unlock after this phase" and said the client nudge rule would become the push rule unchanged; that is what landed: the same trigger (a strong, never broad, match in my zone, both of us around), the same cooldown (once per pair per day), a new channel. The earlier "no push" in the counter-positioning list meant organizer or sponsor broadcasts; this is one attendee's own opt-in nudge, which names nobody, and the refusal of broadcasts stands.
- **One dependency, and why.** The root had no npm dependencies, because the server needed only Node built-ins. Web Push needs VAPID signing (ES256 JWT) and RFC 8291 payload encryption (ECDH on P-256, HKDF, aes128gcm with the push service's record framing), which no built-in does end to end and which is easy to get subtly wrong. The coordinator allowed exactly one: `web-push`, pinned to an exact version, installed in the runtime image with `npm ci --omit=dev` from the root lockfile. The server still runs on `node:http`, and `web-push` is imported lazily on the first nudge, so a server without the keys serves everything else and logs one line that nudges are off.
- **Dedupe by index create.** "Once per pair per day" is enforced by writing the nudge record with `op_type: create` under `_id = {event}:{day}:{min_profile_id}:{max_profile_id}` before sending. The write is the lock: two instances, or two presence writes a second apart, cannot both send, and there is no in-memory state to lose on a restart. The same records carry `receivers` (who was actually pushed), and a `_count` over the last hour gives the per-receiver limit of 3; the record is written even when neither person has a subscription, so a pair is nudged once a day whatever their settings. Records expire with the conference and are deleted with either profile.
- **The rule runs after the response.** `PUT /api/presence` answers first and then runs the one matches query as the writer (`when: around_now`, size 20, the same `peopleQuery` and block filter as the matches route, so nothing is ranked twice or differently) and sends. A slow push service never slows a presence write, and every failure is one log line with a status or error class.
- **What the sentence says about the other person.** For the writer, the evidence is the other person's matched passage as the matches query returns it, `<mark>` stripped, about 80 characters at a word boundary. For the other person, there is no second query, so it is the start of the writer's `expertise` (the same fallback `evidenceFor` uses), else their first speak topic label; someone with neither gets no push, because a sentence without evidence would be noise. Never a name, a distance or a reference.
- **Secrets.** `scripts/vapid-keys.mjs` prints no key: it writes the pair to two git-ignored `*.key` files, prints the `gcloud secrets create ... --data-file` commands for `caddie-vapid-public` and `caddie-vapid-private`, and tells the operator to delete the files. `deploy.sh` mounts the private key from Secret Manager as `VAPID_PRIVATE_KEY`, passes the public key as a plain env var (every browser receives it) read from `caddie-vapid-public`, sets `VAPID_SUBJECT` from the shell or the repository URL, and deploys with nudges off when the private secret does not exist yet.
- **iOS needs the Home Screen.** Safari delivers Web Push only to a Home Screen web app (iOS 16.4+), and `PushManager` does not exist in a Safari tab, so the switch shows a two-line explainer (Share, then Add to Home Screen) and stays off until the app runs in `display-mode: standalone`. Chrome on Android gets the captured `beforeinstallprompt` as an "Add to Home Screen" button before the permission request, because a notification from an installed app is the one people keep. Permission is asked only after the notice and a tap; a denied permission shows one line.
- **Verified locally**: a push-flow test against the Elasticsearch stand-in with `PUSH_TRANSPORT=stub` (a recorder in place of `web-push`): the pair gets exactly one push each with the exact sentence and no name, ref or profile id; a second presence write the same day sends nothing; a broad match, a blocked pair and the fourth push to one receiver in an hour send nothing; a 410 deletes the subscription; unsubscribing and deleting the profile remove the subscription and the records. `web-push` itself was checked once against a local TLS endpoint (VAPID header, `aes128gcm`, TTL and urgency headers, a 410 surfacing as `statusCode`). Playwright in mock mode: the row under the presence switch, the iPhone Safari explainer, the Home Screen and Android paths ending in "On", the notification shown through the registered worker, the Settings mirror, the denied hint, and `#/people?around=1`. Real delivery through Apple's and Google's push services could not be exercised here.
- **Integration note**: the push branch was cut before the day-long presence landed. On the merged branch "Until I turn it off today" keeps presence on in the background, so a push can arrive hours after the phone went into a pocket; in the hour mode the pocket window is still the 5 minutes before presence turns itself off. The push rule runs after the response of the same `PUT /api/presence` that stores a held spot line and a position, and the nudge query passes the writer's own position as the distance leg's origin, so it is exactly the Around view's query.

## Android companion: find people near me by Bluetooth (2026-11-09)

- **Native is un-tabled for Android only, and only for the pocket case.** "The default state is passive" is the spec's test, and the web cannot pass it with the phone in a pocket: a browser tab in the background gets no radio and no timers, Web Bluetooth cannot advertise anywhere, and Web Push (the next unlock) still needs a server that knows two people are close, which a self-reported zone cannot say. Bluetooth proximity is the only signal that works indoors, hands-off and offline from any infrastructure, and Android is the only platform that lets an app advertise and scan from a foreground service. The "no Bluetooth" line in the Find & connect review stands for the web app and for Brella-style organiser features; this is an optional companion for one platform, off by default, and the web app is unchanged. iOS is not attempted: background advertising there is restricted to CoreBluetooth's overflow area and the two sides could not hear each other reliably.
- **Capacitor over a rewrite.** The companion is the same web app, bundled, plus one plugin. Capacitor gives a WebView shell, a plugin bridge and a Gradle project from the existing `web/dist` with three pinned dev dependencies in `web/` and nothing in the server; the screens, storage keys and API client stay one codebase. A Kotlin or Compose rewrite would fork the product in a week when the only native need is one radio. `CapacitorHttp` carries API calls in the native layer so the same-origin check and CSP need no exception for a `https://localhost` WebView origin.
- **Rotating tokens, nothing stored.** What goes over the air is a 16-byte random token under a fixed service UUID; it resolves only on our server, only while presence is on, and is replaced every ten minutes, so nobody with a sniffer can follow a person from the coffee line to a room. Both phones scan and both report, so the server never writes a sighting: it resolves the tokens of one report, ranks the people with the same `matches` retriever the search uses (as the requester, restricted to those documents), answers with the strong matches, and forgets. A device may ask only while it is itself broadcasting, so there is no listen-only mode. A report tells the server which tokens one phone heard for the length of that request; that is the whole privacy cost, and it is written down in `docs/CONTRACT.md`. The nudge is one local notification per person per day with the evidence and no name, and the record of who was nudged lives on the device under the same key as the in-app nudges.
- **The threshold is -75 dBm (`BLE_NEAR_RSSI`).** At medium transmit power a phone-to-phone RSSI of -75 dBm is roughly two to four metres with bodies and pockets in the way; -85 would reach across a hall and nudge people who cannot see each other, -65 would need the phones almost touching. The server applies the threshold, so it can be tuned at the venue without an app update; the phone sends anything above -90 so the server has the room to tune downward.
- **Extended advertising, not legacy.** A 128-bit service UUID with 16 bytes of service data is 34 bytes, and a legacy advertisement holds 31, so the plugin uses Bluetooth 5 extended advertising (Android 8.0+, hardware since about 2018). A phone whose chip lacks it sees the row but is told its Bluetooth cannot send the code. The alternatives were a 16-bit UUID or a manufacturer id we do not own, or a 10-byte token; squatting on assigned Bluetooth SIG space was not acceptable and a shorter token was not asked for.
- **Target SDK 34, minimum 26, compile SDK 36.** Capacitor 8's library compiles against 36 and the app module shares that; the app targets 34 as specified, which is the version that introduced the `connectedDevice` foreground service type the plugin declares. Google Play may require a higher target for new uploads; raising it is one line in `web/android/variables.gradle` and changes nothing in the plugin.
- **Unbuilt here.** The sandbox has Java 21 and Gradle 8.14 but no Android SDK, and `dl.google.com` is refused by the proxy, so the Gradle project is generated and build-ready but `assembleDebug` has not run; `docs/ANDROID.md` has the exact steps. The web part builds and typechecks with and without `VITE_API_ORIGIN`, and the server flow (token minted with presence, rotation, sightings resolving only live tokens, blocked, hidden, broad and weak dropped, nothing persisted, 51 tokens rejected) ran against the Elasticsearch stand-in.

## Keyword fallback when embeddings are unavailable (2026-11-09)

- Every semantic query asks Elasticsearch to embed the text with the `semantic_text` field's inference endpoint. When that endpoint is over its trial quota, unallocated or down, every such query fails while keyword queries keep working, and the live app answered "This is unavailable right now" for any search with text and for For you. Now `server/semantic.mjs` pauses semantic queries for 60 seconds after one fails; search, recommendations, people matches and circle members answer the same request with keyword matching alone and add `degraded: { semantic: true }`, which the app shows as "Meaning-based matching is paused right now; these are keyword matches." Only the Elasticsearch error type reaches the log, never query text. The pause means one failed request per minute, not one per search.
- Profile writes get the same treatment: indexing `about`, `interests` and `expertise` embeds them through `copy_to`, so while embeddings are unavailable the document is written without those three fields and with `text_hash` null (plus an unindexed `text_pending: true`), the response carries `degraded: { semantic: true }`, and the person stays visible and can share. The null hash makes their next save a full reindex that embeds the text once the endpoint is back.
- **Only an inference failure pauses (review fix).** The first version paused on any failed semantic request, so one shard hiccup or timeout switched the whole process to keywords for a minute and, worse, stripped the text from every profile saved in that minute; a 429 Bulk item (what the trial limit answered with) was not recognised at all, so those saves were 502s. Now the transports of `people.mjs`, `search.mjs` and `recommend.mjs` read an error response, an msearch item or a Bulk item for its status and its error types (with a yes/no on whether a reason names inference or a trial limit; the reason itself is never kept or logged), and `isInferenceFailure` in `server/semantic.mjs` decides: `status_exception`, `inference_exception`, `model_deployment_*`, any type naming inference, or such a reason. Every pause site (people matches and circle members, talk search, recommendations, the push nudge, Bluetooth sightings and profile writes) pauses and retries keyword-only only then; a profile write also treats a 429 item as an embedding failure. Anything else fails the one request as before. The nudge and the sightings, which used to send their semantic query with no fallback at all (so every sightings report was a 502 while embeddings were down), now rank through the same `rankPeople` helper as matches.
- **The text of a degraded save is kept, not dropped.** It goes into `pending_about`, `pending_interests` and `pending_expertise`, mapped `text` with `index: false` and copied nowhere, so nothing embeds or searches it. The owner's next write embeds it: a profile save is a full reindex anyway (`text_hash` null never matches), and a presence write re-indexes the document from its pending fields once semantic matching is available again, guarded by the sequence number it read, without failing the presence write when that does not work. The web app, when a save answers `degraded`, sends the profile once more 70 seconds later (after the minute's pause), once, not in a loop.


## In-cluster embeddings: caddie-e5-small replaces the EIS trial (2026-11-09)

- **Decision.** Every `semantic_text` field now uses the inference endpoint `caddie-e5-small`, the built-in multilingual E5 small model (`.multilingual-e5-small_linux-x86_64`, 384 dimensions) deployed on the cluster's own ML node, instead of the cluster default `.jina-embeddings-v5-text-small` on the Elastic Inference Service. ## Deletes without the refresh privilege, and the profile delete order (2026-11-10)

- **Cause.** Smoke checks q8 (unblock) and q9 (delete removes everything) failed against the live service, and each 502 followed the log line "People request to Elasticsearch failed: status 403". The people key holds `read`, `write` and `view_index_metadata` on `caddie-people*` and no refresh privilege, while unblock, `deleteConnections` and the push unsubscribe sent `_delete_by_query?refresh=true`. Elasticsearch deleted the matching documents and then refused the refresh with 403. Local runs passed because they used the admin key.
- **The key stays as it is, for the server.** Commit 53bd019 replaced those deletes with `deleteWhere` in `server/people.mjs`: a search for the matching ids, then a Bulk delete with `refresh=wait_for`, which `write` covers, as the live profile writes and the `create-es-keys.mjs` verify step (`PUT _doc?refresh=wait_for` with the people key) already show. The earlier decision to leave `maintenance` off the people key (see "Review fixes") therefore stands for the service, the people role in `scripts/create-es-keys.mjs` is unchanged, and the key does not need to be minted again. A future `_delete_by_query?refresh=true` in the server would bring the 403 back.
- **Operator scripts still need the admin key for their deletes.** `npm run rules:reload` (`scripts/moderation-rules.mjs`) and `npm run people:seed` (`scripts/seed-people.mjs`) still send `_delete_by_query?refresh=true` and use `ES_PEOPLE_API_KEY` ahead of `ELASTISEARCH_API_KEY` when both are set; `node scripts/moderation.mjs --unhide` and `--purge` send it with whichever of the two keys they have. With the people key they delete the matching documents and then fail with 403. For `rules:reload` that leaves the rules index empty: the percolator then matches nothing, the server does not fall back to its wordlist because the index exists, and rule moderation is off without any error. So these scripts run with the admin key only, which `docs/OPERATOR_CHECKLIST.md` now says at step 5. Making `moderation-rules.mjs` write the new rules before it removes the old ones is a follow-up.
- **Delete order.** Deleting a profile, and the both-choices-off write that deletes it, used to remove the profile document first and its blocks, meets, push subscriptions and nudge records after. When one of those deletes failed, the request answered 502, and trying again found no profile, answered 200 and never removed the rest. Deleting the connections first fixed that but opened a worse gap: the blocks went first while the profile could still be found, so a later failure (a timeout, a 5xx, a Bulk 429) left the person findable in matches, Around and circles with every block gone, and someone they had blocked could see and ask them again. `deleteProfileAndConnections` in `server/people.mjs` now runs in this order:
  1. One Bulk partial update hides the profile: `open_to_meet: false`, `shared_talk_ids: []` and `PRESENCE_OFF`, which clears presence, the position and the Bluetooth token, with `refresh=wait_for`. Every way of finding a person checks one of those fields: matches and the Around view, nudges and Bluetooth sightings require `open_to_meet`; circle members, circle counts and For you's circle counts require a shared talk; an ask goes through `personByRef`, which requires either. `docByRef` stays unfiltered on purpose, so a hidden profile can still be blocked and reported. A 404 means the document is already gone, and the request answers 200 as before.
  2. Meets, push subscriptions and nudge records are deleted, then blocks. Blocks go last because a delete that fails part-way leaves a hidden profile that its owner can make visible again with a later profile write, and it must still carry every block then.
  3. The profile document goes last. Until then every failure answers 502, and trying again authenticates against the document (it keeps `secret_hash`) and redoes the whole delete. `visible_until` is left alone, so the hourly purge cannot remove the document before a retry.
- **The second pass stays, as best effort.** The hide stops new lookups but not requests already under way: an ask that passed `personByRef` just before the hide, a nudge that was already ranking, a block by ref, or the owner's own device subscribing to push can still write after the first pass has finished with that index. A second pass over the connections after the document is gone removes what has landed by then. It costs four searches. A failure there is logged with its status and the request still answers 200, since trying again would find no profile and change nothing. A write that lands after the second pass stays: the purge removes such a meet once it runs out and a push subscription or nudge record when the conference ends; a late block is never purged, but it only keeps two people apart.
- **Test.** `npm test` runs `test/delete-profile.test.mjs` with `node:test` and no new dependency. It replaces `fetch` with an in-memory stand-in for Elasticsearch, so nothing reaches the network, and drives both routes that delete a profile. It checks the order above; that a failure at any step between the hide and the blocks (an HTTP 503, a network error, a timeout or a Bulk item 429) answers 502 with no block and no document deleted and the profile hidden with its secret hash; that a failure at the blocks or at the document delete still leaves the hidden document; that trying again after any of these finishes the delete; and that a failure in the second pass answers 200 and is logged. Run against `server/` from d1684f0, 54 of its 56 tests fail, and each of the 36 that fail a step before the blocks fails on "no block was deleted".
- **Smoke.** The leak check `l` allowed C's contact only in responses labelled `A-members`, and later also `B-members`. It now allows it only in the circle's member list for the circle talk, answered to a caller that shared for that talk when it asked. `api()` tracks each test device's shared talks from the profile writes the server accepted, taking the list the request sent rather than the server's echo of it, and from the deletes, so the check follows q10 making B a sharer and p11 deleting B without depending on labels or on the order of the checks. Check `l0` fails when an accepted write echoes a different list from the one it sent. `api()` also prints a NOTE line whenever a first attempt answers 5xx or fails, because the silent retry had hidden the 502s behind q8 and q9 from the output.

## Schedule import bounds (2026-11-10)

A review reproduced two faults in `POST /api/import/schedule` against an Elasticsearch stand-in. Both are fixed in `server/import.mjs`; the endpoint, its limits on the request and its results are otherwise unchanged.

- **Backtracking.** The e-mail line pattern `^\S+@\S+\.\S+$` is cubic on a long line that does not match: an 8 KB pasted line of `@.` held the event loop for about 20 s, and health checks waited. The trailing-punctuation strip ran on a whole candidate before it was cut to 300 characters, and the ` - ` separator split ran on iCalendar `SUMMARY` values and CSV cells whose runs of spaces were not collapsed; both are quadratic, and a 150 KB run of colons, a 200 KB `SUMMARY` or a 200 KB CSV cell held the loop for 10 to 20 s. Now every line, CSV cell and iCalendar property is cut to 1,000 characters before any regular expression sees it; a candidate is cut to 300 characters before the strip; the e-mail check is `^[^\s@]+@[^\s@]+$` on at most 254 characters plus index checks for a dot in the domain, which cannot backtrack; and `SUMMARY` values, CSV cells and JSON titles have their spaces collapsed, as plain-text lines already had. Every other pattern in the module was checked: each is anchored with quantifiers that cannot overlap, or runs on at most 1,000 characters. The inputs above now take 4 to 12 ms per request, and `GET /api/health` answered within 11 ms while four of them ran at once.
- **Memory.** The whole text was split into an array of lines up front, and a block of lines with no blank line gave one entry per line before the 3,000-entry limit was checked. One upload of 5 MB of short lines peaked at 428 MB RSS (354 MB over idle), three at once at 1,154 MB and four at 1,200 MB, more than the 512 MB Cloud Run instance. Now lines are found by index; plain text and iCalendar stop after 100,000 lines and every parser after 3,000 entries; a block stops taking lines once it can fill the remaining entries; speaker text stops once it holds 300 characters; CSV cells keep 1,000 characters and parsing stops at 5,000 rows or 100,000 cells; the JSON walk stops at the entry limit and reads at most 100 names per speaker field; and a JSON file is parsed once instead of twice. The same upload now peaks 44 MB over idle, three at once 103 MB and four 119 MB (191 MB RSS). Fifteen other 5 MB shapes (one long line, blank lines, headerless CSV, one quoted cell, long iCalendar events, JSON arrays), which held up to 543 MB over idle before, now stay between 37 and 58 MB, except a JSON object of 588,000 keys at 124 MB, which is the cost of parsing it.
- **Four imports at once stays.** No single worst-case upload is above 150 MB over idle, so `MAX_ACTIVE` stays 4 and the decoded limit stays 5 MB; four of the worst JSON shape at once peaked at 380 MB, inside 512 MB. `scripts/deploy.sh` is unchanged.
- **Results unchanged.** Nine realistic files (a pasted list of "Title — Speaker — Tue 10:30" lines, Sched-style text, the same list as a .txt file, a folded .ics with `TZID` and UTC starts, a Google Calendar CSV, a headerless CSV, Sessionize-style JSON, a JSON array of titles and a paste of odd lines) gave identical responses and identical `_msearch` queries before and after, against a stand-in that answers the named queries. Lines are read differently only past a bound, and a line like an address with two `@` signs is now kept instead of dropped as an e-mail line.
- **Remaining cost.** A 5 MB JSON object with hundreds of thousands of keys still holds the event loop for about half a second while it is parsed and its keys listed, so four at once delay other requests by about 2 s; before this change it was about twice that. A smaller limit for JSON files would bound it further. It was not changed, because no sizes of real whole-conference exports were measured.
- **Test.** `npm test` runs `test/import-bounds.test.mjs` with `node:test`, an in-memory stand-in for Elasticsearch and no new dependency: each backtracking input above finishes in under 500 ms; seven worst-case 5 MB uploads import in a child process whose V8 heap is capped at 64 MB; and eight ordinary files keep their candidates, speaker text, time hints and matches. Against `server/import.mjs` from a17ca15, 13 of its 26 tests fail: seven backtracking cases take 10 to 20 s each and six of the seven uploads run out of heap.

## Finishing failed profile deletes, blocks that outlive the blocked profile, and guarded own-document writes (2026-11-10)

- **Cause.** A critic of PR #10 found four server-side gaps. (1) A delete that hid a profile and then failed, and was never tried again, left the hidden document with its name, about, expertise, contact fields and `secret_hash` until `visible_until` and the hourly purge, against the rule that a document exists only while its owner is visible or sharing, and `npm run people:export` still exported it. (2) Deleting a profile deleted blocks in both directions, so a blocked person could delete and re-create their profile from the same device (the same `profile_id` and `ref`) and reappear to whoever blocked them. (3) The presence write and the Bluetooth token rotation were partial updates without a sequence number guard, so one that read the profile before the hide and landed after it put presence or a token back on the hidden document. (4) The hide had no `retry_on_conflict`, so a presence write or a report landing at the same moment turned the delete into a 502.
- **The pending state is its own marker.** The plan allowed an explicit `delete_pending_at` field if a legitimate profile could look like a pending delete. None can: `putProfile` deletes the document when both choices are off, `scripts/seed-people.mjs` skips such profiles, the key check document of `scripts/create-es-keys.mjs` is expired and deleted at once, and the smoke test writes documents straight to Elasticsearch only with `open_to_meet: true`. So `open_to_meet: false` with no `shared_talk_ids` value marks a pending delete (`PENDING_DELETE_QUERY`, `isPendingDelete`). A new field would also have needed a mapping change before the purge and the export could query it, and with `dynamic: false` an unmapped field matches nothing, so a deploy before `people:setup` would have silently kept every pending delete and exported it.
- **The purge finishes pending deletes.** It runs first in the hourly purge and in `npm run people:purge`, in pages sorted by `updated_at` and `profile_id` with `search_after`, so a backlog larger than one page is worked through in one run. A search hit is only a candidate: the search runs on the refreshed view of the index and may be stale, so each candidate is read again with a realtime `GET`, and nothing is touched unless it is still a pending delete with the sequence number and primary term the search returned. A profile its owner made visible again after the search therefore keeps its meets, push subscriptions, nudge records and blocks. Then come its meets, push subscriptions and nudge records, then the document with `if_seq_no`/`if_primary_term` from that read, then the blocks the person made. Elasticsearch answers a guarded delete of a missing document with 409, the same as a changed one, so a second realtime read tells the two apart: gone means the owner's own retry finished the delete, and its blocks are deleted; present means it changed in the few milliseconds since the read, and it is kept with its blocks (still pending, it is found again by the next run). The same second read skips the blocks when a profile was re-created from the same device right after the delete; a re-creation in the milliseconds between that read and the blocks delete would still lose the blocks the old profile made, which the delete was removing anyway. The blocks go after the document for the reason they go last in the delete itself. A failure before the document delete leaves the document for the next run; one after it leaves blocks that run out with the conference.
- **A pending delete is treated as gone everywhere else.** `authenticated()` returns null for it, so its owner's device cannot block, ask, report, subscribe to push or write presence while the delete is unfinished, and only the profile write and the delete read the document themselves. `peopleByIds` leaves it out, so the inbox skips meets with the person and the blocks list shows them without a name. The export leaves it out.
- **Blocks belong to their blocker.** A profile delete removes only the blocks the person made; blocks others made of them stay until the blocker lifts them, deletes their own profile, or the conference ends. Blocks now carry `expires_at`, the latest of the conference's `visible_until` and the `visible_until` of the two profiles, so a block never runs out while either profile can still be found, and the purge deletes them after it, as it does push subscriptions and nudge records. An end date moved later after a block was written reaches it only when the block is written again; that is accepted, since end dates rarely move and checking both profiles for every expired block would cost a lookup per block at the end of every conference. The web app already shows a block without a name as "Someone you blocked", or with the name the device cached, and unblock works by the stored `ref`.
- **Existing blocks get `expires_at` from `people:setup`.** Mapping the field does not index it in documents that already carry it, so `npm run people:setup` re-indexes the blocks in place (`_update_by_query` without a script, then a refresh), and then gives each block still without it the end of its conference, computed from `end_date` and `time_zone` as the server computes `visible_until`, with a script that never overwrites a value. The alternative, purging blocks without `expires_at` once `created_at` is 30 days old, was rejected: a profile can exist long before its conference, and such a rule would drop a block before the conference it was made for. Blocks of a conference that has no document or no `end_date` are left without `expires_at` and are never purged, as all blocks were before. The setup needs the admin key and runs before the deploy (`docs/OPERATOR_CHECKLIST.md`, step 2); until it has run, the purge's range query on the unmapped field matches nothing and no block is deleted early.
- **Own-document writes are guarded.** `updateOwnProfile` in `server/people.mjs` writes a partial update with the sequence number and primary term of the `authenticated()` read. On a 409 (or a 404) it reads and checks the profile again once, so a presence write or token rotation that raced a hide finds no profile and answers 403 `profile_required`, while one that only raced another change (a token rotation from the Android app, a report) still succeeds; a second conflict answers 409 like a conflicting profile write, and a document gone by the second write answers 403 `profile_required`. The web app treats a 409 on a position write as passing (the next fix tries again) and shows "That did not go through. Try again." when the presence switch gets one. `DELETE /api/presence` only clears, so it stays unguarded and retries conflicts (`retry_on_conflict: 3`). Meets also count a person as around only while `open_to_meet` is true and their presence is live, so presence left on a document that is not visible conference-wide is never shown, and an active meet with such a person ends.
- **Shared constants without side effects.** `PRESENCE_OFF`, `PENDING_DELETE_QUERY`, `isPendingDelete`, `visibleUntil` and `dayBounds` moved to `server/people-shared.mjs`, which `server/people.mjs` re-exports. Importing `server/people.mjs` starts the hourly purge, so the purge, export and setup scripts import the shared module instead of repeating the values; the CLI purge now clears every presence field of `PRESENCE_OFF` (the position's cell and time and the Bluetooth token included), as the server does.
- **The hide retries conflicts and the deletes run side by side.** The hide is a plain partial update (no upsert) with `retry_on_conflict: 3`. Meets, push subscriptions and nudge records are deleted concurrently; `Promise.allSettled` waits for all three before a failure is answered, so nothing is still deleting when a retry starts. The blocks still go after them, and the document last.
- **Tests and CI.** `test/helpers/fake-es.mjs` is a small in-memory Elasticsearch (documents with sequence numbers, the query types the server sends, terms aggregations, `search_after`, Bulk with `if_seq_no` and `retry_on_conflict`, failure injection, hooks and a barrier), used through a stubbed `fetch` and, for the CLI scripts, over loopback HTTP. It refuses what Elasticsearch refuses: a guarded delete or index of a missing document is a 409, and `if_seq_no` together with `retry_on_conflict` fails the whole Bulk request with 400 (`test/fake-es.test.mjs`). `test/delete-profile.test.mjs` covers the delete order, the concurrency, block ownership, a profile re-created from the same device, partial Bulk failures and hide conflicts; `test/pending-delete.test.mjs` the purge in the server and in the CLI (the realtime checks, a profile re-enabled before or after them, a document the owner's retry deleted, a profile re-created after the delete, paging), the setup's backfill and the export; `test/guarded-writes.test.mjs` the guarded presence and rotation writes, the presence clear and meets with a person who is not visible; `test/blocks.test.mjs` block expiry and the blocks list. Of these 107 tests, 89 fail against `server/` and `scripts/` from a17ca15; the 18 that pass are regression guards and the three checks of the stand-in itself. `.github/workflows/test.yml` runs `npm test` and the web package's tests on Node 22 and the latest Node for every pull request and every push to `main`, with the actions pinned by commit and no persisted credentials.

## Shared contracts v1 for the native apps (2026-11-10)

Phase 1 of the native-apps plan (`docs/NATIVE_PLAN.md`) starts with four contracts that every tier and both apps build against: capabilities, the talk bundle, the People API and Bluetooth derived tokens. Each has a spec under `docs/contracts/`, a draft 2020-12 JSON Schema under `contracts/schema/`, fixtures under `contracts/fixtures/` and, where there is logic to share, a Node reference implementation under `contracts/js/`. Nothing in `server/` changed.

- **No new dependency.** The schemas are checked by `contracts/js/validate.mjs`, a small validator for the subset of draft 2020-12 the schemas use, which refuses every other keyword so a schema cannot rely on one it would ignore. Ajv would have been the first dev dependency, for checks that fit in about three hundred lines. The schemas are standard draft 2020-12, but closed mode and the asserted `format` keyword are this validator's extensions, so the checks the tests rely on are this validator's. The validator has a closed mode for producers, in which a typed object schema rejects properties it does not list, so one schema serves both the lenient consumer and the strict producer.
- **Capabilities.** Readers ignore unknown fields, map unknown enum values to the most conservative known one and treat a missing flag as off; only a backend with no document at all is read as today's full feature set. That legacy case is recognised positively, by the server's exact 404 body `{ "error": "Not found" }` on `/api/capabilities` followed by exactly `{ "ok": true }` from `/api/health`, and only for a backend that has never served a document to the device, so a failing backend is never mistaken for a legacy one. `people.reports` must be true whenever people features are on, because a backend that shows other people's text must let users report it. A deep link or QR code that switches the backend needs https and an explicit confirmation naming the new base URL, and device secrets and cached state are kept per base (origin and path), since two tier 1 sites can share an origin. Version negotiation is `api_version` plus an optional `min_api_version`, which works for static files as well as servers.
- **Talk bundle.** Vectors are a raw int8 file (`vectors.i8`, rows of 384 signed bytes), not base64 in JSON: a quarter smaller than base64, nothing to decode, one SHA-256 to verify, and a phone can map it straight into a byte array. Each row is quantised on its own with a max-abs scale to [-127, 127] and the scale is not stored, because cosine similarity, the only use, does not depend on it. `bundle.json` is canonical JSON with no floats and no timestamps, so a rebuild of unchanged inputs gives the same bytes and the same content hash, and the hash names the bundle's immutable directory. `conferences.json` is a superset of the `GET /api/conferences` response. Break items stay in the bundle because the time phrases need the lunch windows; only talk and ambient items get vectors, and only talks get related talks. The `model` block pins the embedding conventions every embedder follows: CLS pooling (Workers AI is called with `pooling: "cls"`), L2 normalisation before quantisation, no instruction for talk text (`title + "\n" + abstract`), the model card's query instruction for queries, 512 tokens truncated at the end; reference embeddings computed with transformers.js are committed so other runtimes can check themselves. Following the redistribution decision above, a public bundle carries the CC BY 3.0 attribution (licensor, licence, source, changes and the publisher's takedown contact) and only speaker names and one-line taglines, without the speaker profiles and their links.
- **People API.** The freeze follows the code where it and `docs/CONTRACT.md` disagree (the `spot_hidden` presence field, the poll buckets of the inbox and meet reads, and the others listed in `docs/contracts/people-api.md`). A conformance test runs all 24 routes through the real handlers against an in-memory Elasticsearch stand-in that stores documents and evaluates the server's filters, and validates every answer in closed mode with every list non-empty at least once, and a source check fails if a frozen route is removed or renamed; a route added to the server is only reported, so concurrent work on `server/` is not blocked by it.
- **Bluetooth.** After a security review of the plan, the server stores no per-person key: `ble_key = HMAC-SHA256(ble_master_secret, "caddie-ble-key-v1" || uint16be(byte length of UTF-8 profile_id) || profile_id_utf8 || presence_nonce)`, with a 16-byte nonce rotated on every presence write with `ble: true` and stored with the id of the master that issued it, so the master secret is a keyring that can be rotated without breaking live sessions and retired at once after a leak. A database leak alone therefore links no tokens; a master-secret leak does. `ble_key_id` (8 bytes of an HMAC of the key) comes back with the key and with every sightings answer, so a device notices a replaced session and re-keys. The token table maps a token to a profile and a nonce tag, and every hit is checked against the store, so a session stops resolving on every instance as soon as presence ends or the nonce changes. Two critic rounds shaped the Phase 4 mitigations and the threat model. Everything a client reports is claimed (the RSSI, the zone, the position), so the mitigations narrow probing rather than prevent it, and the spec says so: a sighting resolves only for a person in the requester's claimed zone or the same or a neighbouring ~100 m cell (on by default, `ble.colocation_required`), which makes each request cover one claimed place and makes the prober visible there; at most 10 new people per device per window and 30 per rolling hour, counted on the final answer and kept where every instance sees it (the conference's Durable Object on tier 2, the requester's own people document on tier 3, since per-instance memory would double the caps on two Cloud Run instances); the zone only within the zone; and Android restarts its advertising sets with each token (an app cannot set its address type, which needs `BLUETOOTH_PRIVILEGED`). The spec states what remains: a matching attacker with sniffers learns that a named person was near a sniffer at a given time, a new device identity costs one profile write, and on iOS, whose address rotation cannot be aligned with the token, one resolution lets a passive sniffer network follow that person for the rest of the presence session. A retired master answers 403 `ble_rekey`, distinct from `ble_required`; a device re-keys only while its presence is live, at most once per window, repeating its full presence, which also ends a re-key ping-pong between two devices sharing credentials. The server accepts windows w - 1, w and w + 1, which covers clock skew both ways, and the sightings interval is capped at half a window (300 seconds) in `derived-v1` so that a late report never needs w - 2. The over-the-air payload gained a format byte (`0x01` + 16 token bytes) so a later format cannot be misread, while a bare 16-byte value stays the legacy token; the GATT `token` characteristic is `944ddf9a-6eea-4583-978f-9da68fc3f562`. The golden vectors were computed by the reference implementation and by `openssl`, and the test checks them again with an independent SHA-256 and HMAC written from FIPS 180-4 and RFC 2104.
- **Topics snapshot.** The live topic lists of the four searchable conferences were captured on 2026-11-10 with four public `GET /api/topics?event=` requests and committed under `contracts/fixtures/topics-live/`, so the Node topics builder can be diffed against them before Elasticsearch is retired.

## Public bundle builder (2026-11-10)

`scripts/build-bundles.mjs` builds the talk bundles of the GitHub Pages demo from the committed data. It sits on top of the shared contract in pull request 17 and must merge after it.

- **Model, pinned and verified.** `@huggingface/transformers` 4.3.2 runs `Xenova/bge-small-en-v1.5` at a pinned revision in fp32 on the CPU. That export's `onnx/model.onnx` has the same SHA-256 as the official `BAAI/bge-small-en-v1.5` file and its tokenizer files are byte-identical to the official ones. The four files are fetched only from the pinned revision's URLs and each is checked against a SHA-256 pinned in code before it is loaded, and the library is given a local directory with remote models disabled, because its own loader ignores the revision for some files.
- **Separate package.** The library lives in `tools/bundles/` with its own lockfile so that the root `npm ci`, the Docker build and the Android workflow do not install onnxruntime. Installs of it use `npm ci --ignore-scripts` (the CPU binaries ship in the package), because onnxruntime-node's postinstall would otherwise download an unverified CUDA provider from nuget.org on linux; `ONNXRUNTIME_NODE_INSTALL=skip` is the fallback.
- **Determinism and reuse.** Inference uses one thread and one text per call, so a vector depends only on its own text. Because another CPU could still differ in the last bit, the builder reuses the int8 rows of the currently published bundles when the embedding identity in `build-info.json` and the text hash match, so unchanged conferences keep their content hash and are not republished. The source is not trusted: paths, files, size and redirects are constrained, the bundle must verify, and a sample of its rows must match a fresh embedding (cosine at least 0.999) or the whole source is discarded. A scheduled `--reuse-from none` rebuild recomputes everything.
- **Topics without Elasticsearch.** Bundles need topics and the topic builder only existed against Elasticsearch, so `scripts/lib/topics.mjs` ports it with a regular-expression tokenizer in place of the Elasticsearch analyzer. It reproduces the live lists in `contracts/fixtures/topics-live/` exactly for all four conferences and a test holds it to that. Candidates whose term gives no valid topic id are dropped and logged, and contractions were added to `config/topic-stoplist.txt`. `scripts/topics.mjs` is unchanged and still serves tier 3.
- **Speaker data.** A public bundle carries each speaker's name and a short title and organization line, never bios, photos or links. The line comes from the index-aligned speaker profiles through the contract builder, is cut at the first " | " and capped at 100 characters, and is null when it cannot be matched with certainty.
- **Email addresses** in abstracts are replaced with "[email removed]" in the published text, so the bundle's `text_hash` and the embedding cover the redacted abstract, and the vector-reuse key is the hash of that published text. The reason is that abstracts are free text typed by speakers and an address in a public static file cannot be taken back once cached.
- **Takedowns.** `data/takedowns.json` lists talks to drop and speakers whose name and tagline to remove, per conference, applied by every build, failing closed on any entry that matches nothing (unless marked purged: true, for content already removed from data/) or names no conference. A takedown also requires removing the content from the committed data and raw snapshots, and `reason` must not identify anyone. The takedown contact defaults to the repository's issue tracker, which is public; CI should pass `--takedown` explicitly, and the maintainer may choose a private contact.
- **Attribution.** The contract fixes the attribution fields, not their text. The licensor line says the Linux Foundation's event information is CC BY 3.0 and that session and speaker content is copyright the speakers and organizers.
- **Index location.** The contract puts `conferences.json` at `{bundle_base}`, so it is written to `dist-pages/bundles/conferences.json`. The Pages workflow also expects `dist-pages/conferences.json`, so a byte-identical copy is written there too. Only searchable conferences are listed.
- **Publisher and takedown contact.** No takedown contact is recorded elsewhere in this repository, so the default is the issue tracker with the publisher named "Conference Caddie (Kurt Lehnardt)"; both can be set with `--publisher-name` and `--takedown`.

## Profile deletes on the device: no resurrection, and unfinished deletes (2026-11-10)

- **Cause.** "Delete my profile" sent its DELETE without looking at the profile edit still waiting for its one-second debounce, or at a profile write already on its way. Either could reach the server after the delete and create the profile again, and the device then removed its key, so nobody could delete that profile. A failed delete also left everything in place on the device: the next profile edit, or a talk marked while "sharing follows Interested" was on, sent a PUT that made the half-deleted, hidden profile visible again. The failure message said "Your profile may be partly deleted" for every error, including a 429, 403 or 400, where the server changes nothing, and turning both visibility choices off gave no hint that the server copy might already be hidden.
- **What is guaranteed.** Within one tab, no profile write is sent while a delete covering its conference runs, and the DELETE waits until every profile write already sent has been answered. A write in flight is waited for rather than aborted, because aborting the request in the browser does not stop the server from applying it. Across tabs, profile writes and deletes take one Web Lock, `caddie-people-writes`, so they do not interleave either. Each write checks the stored delete records again, from storage, once it holds the lock, and a write is dropped when another tab has removed the device's identity. Android System WebView has Web Locks from version 69. A browser without them falls back to the per-tab guarantee only. The wait for earlier deletes, writes in flight and the lock is 15 seconds in all. After that the DELETE is sent anyway but counts as unconfirmed: its mark stays, the device keeps its key, and the delete runs again later.
- **Delete records on the device.** A per-conference mark, `caddie.delete-pending.v1.{slug}`, is written before each DELETE and removed when the server answers 2xx. Every 404 is a failure: the API answers 200 for a profile it does not hold, so a 404 means the request never reached the delete. A 400, a 404, a 429 or the API's own 403 `forbidden` on a first attempt also removes it, since the server changed nothing. A 5xx, a network error, a request that ran out of time, any other 403 (a proxy or a firewall says nothing certain), or any failure after an earlier mark keeps it. On success `on_server` is cleared before the mark, so if the app stops between the two writes, the next attempt only repeats a finished delete. "Delete my profile" is also stored as a whole, as `caddie.delete-all.v1`, before its first request. Only the final clearing of the device, or "Stop trying on this device", removes it. While it is stored, every pass deletes at every conference that holds the profile, may hold it or has a mark, so a conference that answered 429 the first time is deleted later too. A record that another tab has removed is never written back. Each record carries its attempt count, the time of the next automatic attempt, the count of refused keys in a row, the last failure and the time the delete was first asked for.
- **While a delete is unfinished.** No profile edit, share or visibility write goes to a conference with a mark, and none goes anywhere while "Delete my profile" is stored. Marking a talk with "sharing follows Interested" on shares nothing, and a share the user asks for answers that the removal has to be finished first. When turning both choices off may have done part of its work, the choice applies on the device, so the switch shows off. Before the DELETE of that branch is sent, the visibility is read again, after the wait: if a write answered meanwhile made the profile visible again, a PUT goes instead.
- **Clearing the device.** Clearing the device can now happen in a background retry as well as on the profile screen, so it lives in `sync.ts`. It drops the browser's push subscription, then stops what runs in memory: the Bluetooth scan, presence timers and the position watch, the inbox poll's state, nudges and watches. Then it removes every stored people record (PR #18's list plus the delete records). The in-memory reset is registered by `people/index.ts` through `registerRuntimeReset`, because those modules pull in the native bridge, which `node --test` cannot load. Every delete the server confirms also ends presence and push for its conference on the device, as PR #18 does for turning both choices off.
- **First writes.** Before the first write for a conference, the device records `maybe_on_server`. It removes the flag once the server answers, or after a 4xx refusal of the same write that set it. A refused retry after a lost first write keeps the flag. If the answer never arrives, "Delete my profile" and turning both choices off still send a DELETE there; for a document that does not exist it is a cheap 200.
- **Retries.** `startDeleteRetries`, which the shell calls once, tries again at start-up, when the app comes back to the foreground, when the connection returns, and on a timer. Each automatic attempt waits for the record's next time. That wait doubles from 30 seconds up to 30 minutes, and is at least as long as a Retry-After header asks, up to an hour. A return to the foreground while the browser reports itself offline sends nothing. Only one tab retries at a time; it holds the Web Lock `caddie-people-delete-retry` and the others skip. Without a device identity nothing can be deleted from this device, so its records are dropped, and "Delete my profile" finishes by clearing the device and saying the server copy could not be deleted from here. After three 403 `forbidden` answers in a row, five failed attempts of any kind, or a day since the delete was asked for, the profile screen offers "Stop trying on this device". The copy says what that does: after "Delete my profile" it clears the device only, and what the server still holds may stay visible to other attendees until the conference ends, with no way left to delete it from this phone.
- **Messages.** A 5xx or network failure of "Delete my profile" says the profile may be partly deleted and to try again to finish. A 429 says the profile was not deleted yet and to wait a minute. The API's own 403 `forbidden` says this device is not allowed to delete it. A 400 says the server could not handle the request. After an earlier attempt that may have done part of the work, a later 4xx says the delete has not finished and that the profile may be partly deleted, never "not deleted". Turning both choices off uses the same split: "may already be hidden from others at this conference" for a 5xx or network failure, and "nothing changed", with the switch back on, for a first refusal. The notice at the top of the profile screen names the conference when it is the one on screen, and its Try again sends the result of "Delete my profile" to the Delete card. An automatic share that waited behind a finished "Delete my profile" ends quietly instead of asking for a name.
- **Tests.** `npm --prefix web test` runs `web/test/*.test.mjs` with `node:test` and no new dependency: Node strips the TypeScript types itself (Node 22.6 or later, hence the `engines` field), and `web/test/loader.mjs` resolves Vite's extensionless imports and sets `import.meta.env`. `PeopleApiError` assigns its fields by hand instead of using constructor parameter properties, which type stripping cannot run. `web/test/env.mjs` stands in for `window`, `document`, `localStorage`, `fetch` and, where a test installs them, Web Locks; nothing reaches the network. The tests pass on Node 22 and 26, and the retry tests check that the DELETE has gone out before the test itself calls anything. Twenty-two single changes to `sync.ts` were each checked to make at least one test fail. They were: no retry at start-up, on `visibilitychange` or on `online`; `startDeleteRetries` doing nothing; a held edit never sent again; 404 handling either way; the stored "Delete my profile" request or its block on every conference removed; retrying only marked conferences; writing back a mark another tab removed; no special case without a device identity; backoff or Retry-After ignored; retries in every tab; no `maybe_on_server`; no re-read before the both-off DELETE; the automatic-share check removed; an unconfirmed delete treated as confirmed; the send guard removed; presence and push not ended after a confirmed delete; and the in-memory reset skipped. Two tests drive the 15-second limit with mocked timers. No test covers the order of the `on_server` and mark writes. The Android APK picks this up on its next build, since it bundles the same web app.
- **Second review: another tab, and staying findable.** A second critic round found that a tab could undo another tab's "off", and that presence, Bluetooth, push and asks carried on while a delete was unfinished. Turning both choices off now writes the conference's mark before it waits for the write lock, so a write that another tab has queued for the lock finds the mark and is dropped. Every profile write reads the visibility from storage once it holds the lock, not from its tab's copy (whose storage event may not have arrived), drops itself when the conference no longer holds a document, and builds its body from that state; a visibility change starts from the stored state as well, and the debounced edit checks `on_server` in storage for each conference. A write is also dropped when another tab removed the device identity or replaced it with a different `profile_id`. When a delete starts, before its first DELETE, Bluetooth stops for the conference (for "Delete my profile", Bluetooth, every presence timer and the position watch), presence ends on the device, and a presence DELETE goes to each conference where presence was on. When the profile DELETE is then refused before the server changed anything, the message adds that presence was turned off (and, after turning visibility off, that it can be turned on again), since that part did happen. Until the delete is done, `putPresence`, `putPresenceBle`, `rotateBleToken`, `putPushSubscription` and `requestMeet` refuse on the device with 403 `delete_pending`, from the stored records (`deleteCovers` in `storage.ts`), so another tab's delete counts at once. A confirmed delete also turns off `open_to_meet` and the shared talks of its conference on the device.
- **Nothing waits forever.** Profile writes, profile deletes and presence deletes time out after 20 seconds, reading the answer included, with a timer and an `AbortController` rather than `AbortSignal.timeout`, which older WebViews lack. A save waits at most 25 seconds for the write lock, longer than one request may take, and then says to try again. A retry pass that has not finished after two minutes is no longer waited for, so Try again cannot stay on "Working". A tab that finds another one retrying waits for its timer instead of polling the lock. A stored retry time more than an hour ahead is read as an hour (a corrupt value or a clock set back), and the timer never asks for more than the browser's limit of 2^31 - 1 milliseconds.
- **Tests of the second review.** `web/test/delete-hardening.test.mjs` covers the stops and refusals while a delete is unfinished, which 403 counts as a refused key, the "Stop trying" thresholds and copy, the time limits (a DELETE that never answers, an answer that stops halfway, a save that waits too long for the lock), saves under the lock, a removed or replaced key, the retry timer and the caps on retry times. `web/test/delete-two-tabs.test.mjs` imports a second copy of the modules (`sync.ts?tab=b`; `web/test/loader.mjs` passes the query on to every module that copy imports), which shares `localStorage`, `fetch` and Web Locks with the first, as a second tab does, and receives no storage events. The 66 web tests pass on Node 22 and 26. Each of these single changes makes at least one test fail: a write or a visibility change reading the tab's cached visibility, the "off" mark written only after the lock, no refusal of presence writes, no stop before "Delete my profile", no word about the stopped presence after a refusal, every 403 counted as a refused key, saves without the lock, and requests without a time limit.
- **Accepted risk: Android can lose the last writes to localStorage.** Chromium, and so the Android System WebView, keeps `localStorage` writes in memory and commits them to disk in batches after a short delay. If Android kills the app's process within that window (the user swipes it away, or the system reclaims memory), the last writes are lost, and the delete records are among them. A lost mark makes the device forget that a delete was started: it shows the profile as visible again, and the next edit would send a PUT that makes a profile the server had already hidden visible again before the hourly purge finishes it. A lost clearing after a confirmed "Delete my profile" leaves the old key and profile on the device, and an edit would create the profile again. Both need the process to die within seconds of the write and then an edit, and the user sees the profile as still there. The web layer has no way to force the commit. The Android app could keep the delete records in native storage (Capacitor Preferences) instead; that is left for the native work.

## Tier 3 capabilities document and Bluetooth derived tokens v1 (2026-11-10)

The tier 3 server serves `GET /api/capabilities` and resolves Bluetooth derived tokens v1 under the Phase 4 mitigations (`docs/contracts/capabilities.md`, `docs/contracts/ble-tokens.md`).

- **The mode follows the keyring.** The server advertises `ble.mode` `derived-v1` exactly when the master keyring `BLE_MASTER_KEYRING` (Secret Manager `caddie-ble-master`) is configured, and the legacy `server-rotate` otherwise, so the document always says what the server does. The document is computed once at start from the configuration; `push.apns` and `push.fcm` are false because this server holds no APNs or FCM key, and `push.webpush` is true only when all three VAPID settings are set. `colocation_required` is true in both modes, unlike the `tier3-transition` fixture, because this server applies the co-location rule and the caps to legacy tokens too. That is a change for the old APK on the first deploy, keyring or not: two old-app users who claim different zones and share no position no longer resolve each other.
- **Refusing to start.** An unusable keyring, including one whose current id is not among its keys, or an unusable `TALKS_BUNDLE_BASE` throws when `server/capabilities.mjs` is imported, and `server/index.mjs` imports it first, before the people module starts its purge. No error quotes the keyring, and the keyring is removed from `process.env` as soon as it is read. The deploy pins the newest enabled version of the secret instead of mounting `latest`, because Cloud Run resolves `latest` whenever an instance starts, and the three-step rotation relies on a keyring change reaching every instance only through a deploy. `scripts/ble-master.mjs` reads the pinned version back from the service and refuses a promotion the service does not hold yet and a retirement of the key the service still issues under; gcloud runs with its logging turned down and its error output is never shown, since it could carry a payload.
- **One code path for both kinds of token.** The server imports the key derivation, the token table, the co-location rule and the caps from the reference implementation `contracts/js/ble-token.mjs` instead of copying them, so the Dockerfile copies that file into the image. A presence write with `ble: true` mints both a legacy token and a fresh nonce, so an old APK and a new app can share a backend during the transition, and the rotate route keeps working. A session under a retired master is answered 403 `ble_rekey`, except when its legacy token is live and was rotated: only the old APK calls the rotate route (the write sets `ble_rotated`), and the old APK does not know `ble_rekey`, so it keeps working until its token runs out. A new app never rotates and is asked to re-key at once; a derived-v1 client also re-keys on an answer without `ble_key_id`.
- **One-way discovery for an old APK whose legacy token died.** The old app's presence write also gives it a derived session, which it never uses. When its legacy token stops being rotated (the background failure of 2026-11-09), its broadcast token resolves to nobody, but its derived session still lets it ask, so it can discover others while nobody discovers it. This is accepted: the server cannot tell an old app's derived session from a new app's without the rotation mark, requiring a live legacy token would stop every new app (which never rotates), the requester is still around with a session it made with `ble: true`, and every mitigation (co-location, caps, the zone only within the zone, blocks and reports) applies to what it learns. It ends when the old APKs are retired.
- **Where the state lives.** The nonce (base64url) and the id of its master are stored on the person's people document, mapped as keywords that are neither indexed nor kept in doc values, so they are never searchable or aggregatable; they are cleared with presence everywhere `PRESENCE_OFF` is written, and also by a presence write that starts a new presence session without `ble`, because one nonce is one presence session. The caps record `ble_caps` (`{ ref, at, w }`, pruned to the last hour, mapped as an object that is not indexed) is on the requester's own document, written with the sequence-guarded own-document update only when an answer adds someone new and without waiting for a refresh, since the guard reads with a realtime GET. It is kept across presence sessions. `ble_caps_until`, indexed, is when its newest entry leaves the hour; both purges clear the record once that has passed (a guarded update, so a record written after the purge's search is kept), so the server keeps whom it returned to a device for an hour, not for the conference. The export leaves all of these out.
- **Concurrent requests of one device.** An entry stamped later than the request reading the record (one that started later but wrote first, or one from the instance whose clock is ahead) counts as returned at the time of the read; without that, the reference `applyCaps` leaves out entries from after its now, and two concurrent requests could together return twenty new people in a window. When the guarded write loses twice, the answer keeps only the people already returned in this window. A profile save that loses to such a write (or any other) reads the document again and writes once more, so it neither fails nor drops the record.
- **The token table** is cached per instance and per conference for the current window (at most 64 conferences, least recently used dropped first, 20,000 documents each, with a log line naming only the conference when that limit cuts it short). It reads only documents that carry a legacy token, which every derived session has, and is rebuilt at each window change and, on a token it cannot find, when it is older than 30 seconds. Every hit is checked against the store in the one query a sightings request already ran, so a cached entry never resolves an ended or replaced session.

## Native apps skeleton (2026-11-10)

- **Layout.** `native/` is one Gradle project in the shape of JetBrains' current template for Android Gradle Plugin 9: `shared` (Kotlin Multiplatform, no UI), `composeApp` (Compose Multiplatform UI, built as an Android library and as the `ComposeApp` iOS framework that also exports `shared`), `androidApp` (the Android application) and `iosApp` (the Xcode project). AGP 9 no longer lets a Kotlin Multiplatform module also be the Android application, so `androidApp` is a separate module and the multiplatform modules use `com.android.kotlin.multiplatform.library`.
- **Versions.** Kotlin 2.4.21, Compose Multiplatform 1.12.2 with Material3 1.12.0-alpha03 (the version its release notes pair with it), AGP 9.3.3 and Gradle 9.7.1. AGP 9.5.1 is newer, but Kotlin 2.4.21 is documented as compatible with AGP up to 9.3 and Gradle up to 9.7, so the build stays inside that range. Dependabot is told (`.github/dependabot.yml`) to skip AGP and Gradle minor and major updates until a Kotlin release lists them, and to skip the Material3 artifact entirely: Material3 is bumped by hand together with Compose Multiplatform (Material3 1.13.0-beta02 pairs with CMP 1.13.0-beta02 and needs compileSdk 37.1), and `native/scripts/check-compose-pairing.sh` fails CI when the two catalog versions stop sharing a major.minor. Dependabot alerts and security updates are enabled on the repository, and `dependency-submission.yml` sends the native Gradle dependency graph on every push to main so alerts cover those dependencies.
- **Android SDK levels.** minSdk 26, the first version with the Bluetooth 5 extended advertising API, which matches the Capacitor app. targetSdk 36. compileSdk is 37 rather than 36, because Compose 1.12 and Lifecycle 2.11 refuse to build against 36; compileSdk changes only which APIs the code can see, not the app's runtime behaviour.
- **No iosX64.** Compose Multiplatform 1.12 publishes no x86_64 simulator libraries, and Xcode 27 runs only on Apple silicon. The Xcode project excludes x86_64 from simulator builds for the same reason.
- **Same application id, one release key.** The native Android app keeps `app.conferencecaddie`, the Capacitor app's id. A single release keystore, generated once and held outside the repository, signs release builds of both, so the native app can later be installed as an update over the Capacitor app. The key is PKCS12, so the key password equals the keystore password.
- **No Apple team id in the repository.** `iosApp/Configuration/Config.xcconfig` leaves `TEAM_ID` empty and optionally includes a gitignored `Local.xcconfig`. CI passes the team id from the `APPLE_TEAM_ID` secret. The TestFlight job exists but runs only when its seven secrets are set in the `release` environment.
- **Capabilities.** `shared` has a `Capabilities` data class shaped like the sketch in `docs/NATIVE_PLAN.md` (section 7.2). It parses leniently: unknown keys are ignored and an unknown tier falls back to the demo tier. `Capabilities.Legacy` stands for today's server, which has no capabilities document. It turns people features on and Bluetooth off, because the native apps will implement only derived-v1 tokens. The People tab is shown only when `people.enabled` is true.
- **Signing never runs next to project code (review of PR #16).** The jobs that run Gradle or npm build the release APK unsigned and get no secrets. A separate job signs the file with `zipalign` and `apksigner` from the runner image, without a checkout, and fails unless the certificate matches the repository variable `ANDROID_RELEASE_CERT_SHA256`. The signing secrets (`ANDROID_KEYSTORE_BASE64`, `ANDROID_KEYSTORE_PASSWORD`, `ANDROID_KEY_ALIAS`, `ANDROID_KEY_PASSWORD`) live in the GitHub environment `release`, which only `main` may deploy to; the repository-level copies were deleted. Signing happens only on `main`: pushes and manual runs for the native workflow, manual runs for the Capacitor workflow, which no longer signs on `android/**` pushes. Every action is pinned to a commit SHA and Dependabot proposes updates.
- **TestFlight uses manual signing.** An Apple Distribution certificate and an App Store profile go into a temporary keychain from secrets, and the API key is used only for the upload. This avoids an Admin-role API key that automatic signing would need to create certificates on a fresh runner. It has not run yet; `native/README.md` lists the seven secrets.
- **The TestFlight jobs are split so signing never runs next to Gradle (second review of PR #16).** The first version imported the distribution certificate into an unlocked keychain with `security import -A` and then ran `xcodebuild archive`, whose "Compile Kotlin Framework" phase starts Gradle; the Gradle daemon was still running when the API key was written. Any Gradle plugin or build script could have used the key or read the API key. Now three jobs run on `main` when the seven secrets exist. `ios-release-build` has no secrets: it runs the same unsigned `xcodebuild archive`, so `embedAndSignAppleFrameworkForXcode` builds the Release device framework and the Compose resources with exactly the archive's Xcode settings, packs both with the Xcode version into a tar file kept for one day, and stops the Gradle daemon. `ios-sign` sets up no Java, Gradle or Kotlin/Native and deletes the Gradle wrapper from its checkout; it refuses a framework built by another Xcode version, imports the certificate into a temporary keychain with `-T /usr/bin/codesign` instead of `-A` and the partition list `apple:` for signing keys only, and archives with `OVERRIDE_KOTLIN_BUILD_IDE_SUPPORTED=YES`, which makes the build phase skip Gradle, `FRAMEWORK_SEARCH_PATHS` pointing at the prebuilt framework and `CADDIE_PREBUILT_COMPOSE_RESOURCES`, which the build phase copies to where the Compose plugin puts the resources. It exports a signed IPA (`ExportOptions.plist` now has the destination `export`), deletes the keychain and profile whatever happened, and keeps the IPA for one day. `testflight-upload` checks out nothing; it writes the API key with `umask 077` into a directory in the runner's temp folder, uploads with `xcrun altool --upload-package`, the form the help of altool in Xcode 26.4 and 27.1 gives for an IPA, which finds the key through `API_PRIVATE_KEYS_DIR` (checked with both), and deletes the key whatever happened. The signing job still runs the Swift compiler and the project's build phase on checked-out code, which is accepted: that code is the repository's own and starts no build tool that downloads plugins. Locally, an unsigned archive built the way `ios-sign` builds, from a copy of `native/` without `gradlew` or any `build` folder, succeeded with the build phase reporting that it skipped Gradle; the app binary had the same size and symbols as the one from the Gradle path, and a marker file passed as a Compose resource arrived in the app's `compose-resources` folder. If the first real export fails with `errSecInternalComponent`, the key needs another partition (`apple-tool:`) or another trusted tool; the log names the tool.
- **The Capacitor app keeps no backups either (second review of PR #16).** It keeps the people features' device secret in WebView storage, and this PR release-signs it with the key the native app shares, so its manifest now sets `allowBackup="false"` and `fullBackupContent="false"` and has the native app's `data_extraction_rules.xml`. Both apps' rules exclude every domain, the device-protected `device_*` domains included, from cloud backup and device-to-device transfer. That is the only change to the Capacitor app.
- **Smaller fixes from the second review of PR #16.** The unsigned R8 release APK is built on pull requests too, so a change that breaks shrinking fails before `main`; naming, upload and signing stay on `main`. Both sign jobs refuse an APK name that is not `conference-caddie[-native]-<hex>-release.apk` with the hex a prefix of the commit being built. `BackendUrl` reads a host as IPv4 when its last label is a decimal number or `0x` with hex digits, as WHATWG does, and accepts only a canonical dotted quad without a trailing dot; before, `https://example.0x1` (which the reference refuses) was accepted and `https://1.2.3.4.` gave a base with a trailing dot that the reference does not have.
- **Backend URLs and stored secrets.** `BackendUrl` implements the contract's `normaliseBackendUrl()` rules (https only, local http in debug builds, no credentials, query or fragment) and is stricter where a WHATWG parser would repair input. Per-backend secrets are keyed by the normalised base, not the origin, following the review of PR #17, so two tier 1 sites under one GitHub Pages origin never share a secret.
- **Privacy defaults.** The Android app turns off backup and device-to-device transfer and cleartext traffic (debug builds allow http to local hosts only). The iOS privacy manifest declares the required-reason APIs that `nm -u` finds in the Release framework (FileTimestamp `C617.1`, SystemBootTime `35F9.1`); DiskSpace was not found, so it is not declared.
- **Builds.** Release builds run R8. CI version numbers are 1000 plus the run number, above the Capacitor app's `versionCode`. Gradle checks every dependency and plugin it resolves, the Kotlin/Native compiler distribution included, against `native/gradle/verification-metadata.xml`. That does not cover what Kotlin/Native downloads by itself into `~/.konan/dependencies` (LLVM, libffi and the sysroots), nor a `~/.konan` restored from the Actions cache, which Gradle does not download again; the cache is written only by runs on `main`.

## Tier 3 schedule import accepts text with format hints (2026-11-10)

The free-tier Worker accepts `{ event, text, filename?, mime? }` for pasted or browser-extracted text, and the web app's Pages build sends exactly that for PDF, Word and OpenDocument files. The tier 3 server rejected `filename` and `mime` together with `text`, so smoke check im3b failed against it. The server now accepts the same shape and mirrors the Worker's validation: unknown keys get 400, both or neither of `content_base64` and `text` get 400, and `filename` and `mime` keep their length limits. With text, the two fields only help choose the format (a `.csv` or `.tsv` name or a CSV or TSV type reads as CSV, with a tab delimiter for `.tsv`); a `.pdf` name or an unexpected type falls back to content detection and plain text. They never cause a fetch or a decode, and the 200,000 character, 5 MB and rate limits are unchanged.

## People matching on Elasticsearch 9.5: the rrf explanation and semantic floors (2026-11-10)

A live diagnosis of the tier 3 server found two faults in people matching. Both are fixed in `server/people.mjs`; a critic round then split the floor by path and tightened the edges (the second half of this section).

- **The explanation moved one level down.** The specificity rule reads which retrievers found a hit from the rrf explanation (`explain: true`). `matchedLegs` read the top level of the explanation as one detail per retriever. On the people index, Elasticsearch 9.5.6 puts the rrf node ("rrf score: [..] computed for initial ranks [..]", one detail per retriever) one level down. The people index has nested fields (the `semantic_text` chunks), so Elasticsearch adds a filter that keeps the nested chunk documents out of the hits (`FieldExistsQuery [field=_primary_term]`, a field only top-level documents have), and the top of the explanation is a "sum of:" whose two details are the rrf node and that filter. The top level therefore always has two details. With two retrievers and the topics leg first (a profile with chips and text), the second detail (the filter, value 0) read as "not found by the text leg", so every hit looked found by topics alone, and a person found only by their text, who shares no topic, was dropped as broad from matches, from the push nudge and from Bluetooth sightings. With three retrievers or more the count did not match, the legs were unknown, every hit counted as specific, and people who share only one of the conference's ten most common topics were shown in the `anyone` view and in text searches, nudged and listed over Bluetooth. The tests did not see it because the stand-in returned the flat shape the code expected.
- **Fix.** `matchedLegs` looks for the rrf node by its description and its number of details, from the top down to three levels below it, so the shape of Elasticsearch 8 (the node at the top) and of 9.5 both read. A detail that names its retriever ("in query at index [1] [text-2]") must name the leg at its position, or the legs count as unknown. The stand-ins return the shape captured from the live cluster with read-only `explain: true` searches over the sample profiles (`test/lib/rrf-explanation.mjs`, used by `test/lib/fake-es.mjs` and by the conformance test's own stand-in). The critic re-checked the parsing live on seven combinations of legs.
- **When the legs cannot be read.** That happens when the cluster refuses the explanation (`searchPeople` runs the search again without it) or returns a shape the node search does not recognise. The matches view keeps every such hit, as before, so a person searching never loses a real match to an unreadable response. The push nudge and Bluetooth sightings judge such a hit by its shared topics alone: it is broad unless it shares a topic outside the ten most common. They reach a person who did not search, so a generic match there costs a notification, and when in doubt they say nothing (`isBroad`'s `unknown` option, `'topics'` by default and `'specific'` in matches). The two answers differ on purpose. Both causes are logged with `console.warn`, naming only the conference and the number of legs, at most once in ten minutes each, so a future change of shape shows up in the logs instead of silently.
- **No floor on the semantic legs.** A `knn` leg returns the k nearest profiles whatever their score, and with the E5 small model nearly every profile is near. Measured on 2026-11-10: against the smoke's made-up text, the best of the 132 KubeCon sample profiles scored a cosine of 0.79 to 0.83 and their median 0.76 to 0.81, while the profiles written with that text scored 0.88 to 0.94. Every profile joined every semantic leg, so anyone who also shared a common topic outranked the one person whose text matched (smoke p2, q1 and q10 once the explanation was read correctly). The Worker's comment in `worker/src/people/rank.js` (lines 35 and 36) that this "was harmless" with E5 is therefore wrong; it is left for the session that owns the Worker, since this change does not touch `worker/`.
- **How the floor works.** Each semantic people leg passes `similarity` on its `knn` query. On a `semantic_text` field in 9.5.6 Elasticsearch accepts it, inside an rrf retriever too, and compares it with the raw cosine, not the score (a floor of 0.84 returned a lowest cosine of 0.8423). The measurements below are read-only: cosines from the `caddie-e5-small` endpoint (`_inference` with `input_type` `search` and `ingest`, which reproduced the `knn` cosines to four decimals) and `knn` searches over the 132 sample profiles, where a profile counted as relevant when its text names the query's subject.
- **One floor per path.** A first version used 0.84 everywhere. The critic showed that it was both too high for short searches and too low for the paths that notify, so there are three floors, each in its own variable:

  | Path | Variable | Default | Why |
  |---|---|---|---|
  | A search with a `query` (it also has the keyword leg) | `PEOPLE_SEMANTIC_MIN_SIMILARITY` | 0.82 | Short tool names score low against whole profiles, and the keyword leg finds the exact names. |
  | Matches without a query (`anyone`, `around_now`) and circle members | `PEOPLE_SEMANTIC_PROFILE_MIN_SIMILARITY` | 0.84 | No keyword leg backs it, and the person did ask, so recall matters more than in a push. |
  | The push nudge and Bluetooth sightings | `PEOPLE_SEMANTIC_PUSH_MIN_SIMILARITY` | 0.87 | They reach a person who did not search; a text match must be close to count as specific. |

  The nudge and the sightings run the same query with the push floor on the text legs, so a text-only match between 0.84 and 0.87 is listed in matches but neither nudged nor sighted, while a shared rare topic still counts. Unset or empty gives the default; `off`, `none` or `false` sends no `similarity`; a value that is not a number falls back to the default and one outside -1..1 is clamped, each with a warning at start that does not quote the value. The server logs the floors in effect at start, and `scripts/deploy.sh` passes the three variables through from its environment (empty means the default).
- **Evidence, searches.** Short tool queries against the expertise and about legs, relevant (the profile names the tool) kept / unrelated kept:

  | Query | Leg | 0.80 | 0.82 | 0.84 | 0.86 |
  |---|---|---|---|---|---|
  | Kyverno | expertise (13 name it) | 4 / 0 | 1 / 0 | 0 / 0 | 0 / 0 |
  | Crossplane | expertise (12) | 12 / 17 | 4 / 1 | 1 / 0 | 0 / 0 |
  | Envoy | expertise (11) | 11 / 10 | 2 / 0 | 1 / 0 | 0 / 0 |

  At 0.84 "Kyverno" and "service mesh" keep no relevant profile on the semantic legs; at 0.82 each keeps its closest, with few unrelated ones, and the keyword leg finds every profile that names the tool. Below 0.82 the unrelated ones grow quickly. The smoke's searches stay safe at 0.82: its relevant pairs score 0.884 to 0.941.
- **Evidence, matches without a query.** Ten realistic interests against the expertise leg (367 relevant and 943 unrelated pairs): 0.82 keeps 209 relevant and 290 unrelated, 0.83 143 and 128, 0.84 77 and 29, 0.85 29 and 5, 0.86 12 and 0. - **Evidence, push.** A generic text with common chips is the case to stop. Sample profiles admitted by a semantic leg, of 131 (expertise) or 132 (interests):

Counterexamples: a generic text still reaches about a fifth of the sample profiles at 0.87, because the templated samples name the same labels ("Cloud Native", "AI", "Platform"); and four realistic interests (Postgres, supply chain, autoscaling, GPU inference) get no text-based nudge at 0.87 and rely on a shared rare topic.
- **Evidence only from a leg that found the person.** Elasticsearch returns a semantic highlight for every hit that has the field, whether or not that leg found it (on 9.5.6 all 21 hits that a `knn` leg with a 0.95 floor did not find carried an `expertise_semantic` highlight). So a person found by a topic alone could be shown, pushed or sighted with a chunk the floor had judged unrelated. `rankPeople` now drops each semantic highlight unless the leg on that field found the hit, and `evidenceFor` falls back as for a profile with no chunk. Circle members now ask for the explanation too, so their chunks follow the same rule.
- **Limits of these numbers.** The sample profiles are generated from a template ("I want to learn more about ..." against "I can talk about ..."), which scores 0.82 to 0.91 against itself whatever the topics; real attendees write freer text. - **The Worker's floor.** The free stack's Worker has one floor, `PEOPLE_SEMANTIC_FLOOR` 0.61, for bge-small with CLS pooling (`worker/src/people/rank.js`). The server's floors are chosen per path from relevant and unrelated pairs as above. The two models score on different scales, so the numbers are not comparable.

## The web app moves to the Cloudflare Worker's origin (2026-11-10)

The review of the free stack found (R18) that the GitHub Pages origin `https://kurtlehnardt.github.io` is shared by seven other live Pages sites of the same account. Every page on one origin can read that origin's `localStorage`, so any of those sites, or a compromise of any of them, could read Conference Caddie's device secrets (`caddie.device.v1`) and act as its users. The user chose to serve the app from the Cloudflare Worker.

- **One origin for the app and the API.** The Worker, renamed from `conference-caddie-api` to `conference-caddie`, serves the web app as Workers static assets (`[assets]` in `worker/wrangler.toml`) on `https://conference-caddie.<subdomain>.workers.dev`, the same origin as the API. Static assets are free on Workers. The exact URL is printed by `worker/scripts/deploy.sh`, which builds the app before it deploys.
- **Static files never reach the Worker's code.** Only `/api`, `/admin` and their subpaths run the Worker (`run_worker_first`), so app files cost no Worker request and never count in the API's pace budget. Other paths with no file get `index.html` (`not_found_handling = "single-page-application"`), so a deep link such as `/e/{slug}` boots the app with status 200. `html_handling = "none"` serves `/index.html` as it is, because the service worker precaches it and a redirected response cannot answer a navigation.
- **Headers.** The Worker-mode build (`npm --prefix web run build:worker`) writes `_headers` with the Cloud Run server's Content-Security-Policy (`connect-src 'self'`, `frame-ancestors 'none'`) and its other security headers. Each hashed file under `/assets/` is named in its own immutable rule, rather than `/assets/*`, because the asset layer answers a missing file with `index.html` and that answer must not be cached for a year under a name a later build could reuse. `index.html`, `sw.js` and the manifest are `no-cache`, and the icons keep for an hour. The service worker also refuses to cache an HTML answer under an asset's name.
- **The build.** The Worker-mode build uses base `/`, an empty `VITE_API_BASE` (same origin) and the in-browser document reader (`VITE_CLIENT_EXTRACT=1`), as the Pages build did, and writes `web/dist-worker/`. The default build (`npm run build`, Cloud Run) is unchanged. The GitHub Pages app build (base `/conferenceCaddie/`, the copy of `index.html` to `404.html`, `.nojekyll`) is retired.
- **CORS.** The Worker accepts its own origin (a browser sends `Origin` on same-origin writes too) and the localhost development origins in `ALLOWED_ORIGINS`. `https://kurtlehnardt.github.io` is no longer allowed. Requests with no `Origin`, as the native apps send, are served without CORS headers, as `docs/contracts/people-api.md` says. Neither `contracts/` nor `docs/NATIVE_PLAN.md` names an origin the native apps send. The admin routes still refuse any request with an `Origin` header.
- **GitHub Pages keeps only public data.** `pages.yml` publishes the talk bundles, `conferences.json` and the tier 1 `capabilities.json`, whose `talks.bundle_base` stays `https://kurtlehnardt.github.io/conferenceCaddie/bundles/`, plus a landing page with no script and no storage access that links to the app (the repository variable `CADDIE_APP_URL`) or says it is not live yet. The same page is the site's `404.html`, so old links and the old QR code still lead to the app. These files hold no secrets, so the shared origin does not matter for them. The capabilities schema has no field for the app's origin, so `GET /api/capabilities` is unchanged.
- **What this costs.** Device secrets created on any earlier origin stay there; the app was never published on Pages, so no user loses a profile. The demo QR code must be regenerated for the new URL after the deploy (`node worker/scripts/make-qr.mjs`). This decision supersedes, for the web app, the line "kept as the tier 1 demo page on GitHub Pages" in the native apps plan above.

## Native design system and app shell (2026-11-10)

- **The native apps copy the web app's design rather than Material's defaults.** The colours, type sizes, radii, spacing and shadows are the custom properties of `web/src/styles.css`, light and dark, mapped onto Material 3 so the few Material components used (text field, sheet, dialog) match. A CSS pixel is taken as one dp, and text as one sp, which is what a phone browser does at the web's device-width viewport, so a screen of the native app and the same screen of the web app line up at a 390 by 844 viewport.
- **No bundled font.** The web app's font stack is the platform's system font (San Francisco on iOS, Roboto on Android), which is also Compose's default, so nothing needs a licence or adds weight.
- **The web's lucide icons, generated, not hand-copied.** `native/composeApp/scripts/generate-lucide-icons.mjs` reads the icon nodes from the `lucide-preact` version the web app installs and writes their path data into one Kotlin enum; circles, rectangles and lines become paths. Material icons were not used because the web app does not use them. Lucide's ISC licence (and MIT for the icons from Feather) is kept in `native/licenses/lucide.txt` and shown in Settings, since its notice must travel with every copy.
- **Same layout and words as the web.** The tab bar has the web's tabs in the web's order (People, For you, Search, Interested); Settings moves from the skeleton's tab bar to the app bar's gear, as on the web. `Strings` holds the web's copy word for word, with each group citing its web file; copy only the native apps need (Server, Storage, the server confirmation) is marked native only. Tier 1 has no People tab and opens on For you, as the plan says.
- **One confirmation for every server switch.** A server typed in Settings gets the same confirmation a `caddie://connect` link will get: it names the base URL exactly and warns when the server is not the build's official one. Registering the link scheme is left for later.
- **The shell takes its data from outside.** `App()` receives `ShellState`, `ShellActions` and per-tab content slots, so the talk features plug their screens in without changing the shell, and the shell can be tested with plain values.
- **UI tests run on both platforms from one source set.** Compose Multiplatform's `runComposeUiTest` tests in `composeApp/src/commonTest` run on the iOS simulator and, through the Android library plugin's device-test source set, on an Android emulator; an instrumented smoke test starts the real `MainActivity`. CI runs the Android ones on an emulator started by `reactivecircus/android-emulator-runner` (pinned to v2.38.0's commit), without secrets.
- **iOS theme overrides go on the window.** A Theme setting of Light or Dark sets the interface style of the window that hosts the Compose view controller, so everything in it follows the choice: the status bar, the SwiftUI host that is the window's root controller, and anything UIKit presents from it later (alerts, share sheets). The review feared that the first version, which set the style on the Compose controller only, left the status bar on the device's appearance; on the iOS 27 simulator it did not (both versions were checked with the device in dark mode and the Theme forced to Light, and the other way round), but the window is the place UIKit documents for an app-wide style. The window is reached through the host controller's view once it appears, rather than through `UIApplication.sharedApplication`, which crashed the Kotlin/Native test process, which has no application; tests have no host controller and leave the style alone.
- **Debug-only launch options.** Debug builds accept launch arguments (iOS) or intent extras (Android) that open a tab, Settings, the switcher, a theme, a pending server confirmation or a gallery of the Search components, so screenshots and manual checks do not depend on tapping; release builds ignore them.

### Review fixes to the design system and shell (2026-11-10)

- **The shell keeps clear of every inset itself.** Since the shell draws its own app bar and tab bar instead of Material's `Scaffold`, each part pads for the insets on its side: the app bar for the status bar and the horizontal safe area (the display cutout, and the navigation bar when it sits at the side in landscape), the content for the horizontal safe area, and the tab bar for the navigation bar while its surface still reaches the screen's edges. The keyboard inset goes to the screens with text fields (Settings uses `imePadding()`), with the tab bar's height already deducted. On iOS the Compose controller's own keyboard behaviour is turned off (`OnFocusBehavior.DoNothing`), so the view does not also slide up under the status bar. Saving a valid server hides the keyboard before the confirmation opens; a refused address keeps it up for the correction.
- **The web's wide layout from 768 dp.** At a window width of at least 768 dp the tabs move to an 88 dp rail on the left (which scrolls when a phone in landscape is too short for it), with the web app's icon on top (drawn from lucide's calendar-check on the icon's blue), and the app bar and the screen stay in a column at most 720 dp wide, centred; chip rows wrap instead of scrolling. As on the web, this also applies to a phone in landscape. Both layouts are one composition tree, so a screen keeps its state when the window changes width.
- **Touch targets follow each platform, visible sizes follow the web.** Buttons and icon buttons stay 44 dp tall and chips 36 dp, as on the web, but every control reserves the platform's minimum touch target with Material's `minimumInteractiveComponentSize()`: 48 dp on Android, 44 pt on iOS, set through `LocalMinimumInteractiveComponentSize`. Chips and the search field have a minimum height rather than a fixed one, so large text makes them taller instead of clipping it.
- **Large text never hides an answer.** The confirm dialog's title, body and content scroll while its buttons stay on screen, and the buttons wrap onto two lines when they do not fit side by side, so the server confirmation, which a tap on the scrim cannot dismiss, can always be answered. Tab labels stay on one line and shrink towards their default 12 sp when a large font size would not fit four tabs on a narrow phone, as iOS tab bars do, instead of breaking "Interested" across two lines.
- **One server question at a time.** A server typed in Settings and a server from a link get the same confirmation; if a link arrives while the typed server's question is open, it waits and is asked next, instead of replacing the question the person is reading. Both confirmations report through the same `onChangeServer(base)`, so its owner clears the pending link only when the base is that link's (`pendingAfterSwitch`); confirming the typed server leaves a waiting link pending.
- **Only http(s) links reach the browser, from every component.** Talk cards drop links with any other scheme before drawing them, besides the shell's own check. The debug `caddie.connect` launch option goes through `BackendUrl` with the rules of a link (no local http exception), so it can only produce a question a real link could.
- **Toasts follow the accessibility timeout.** A toast stays for the web's five seconds, or for longer when the system's accessibility settings ask for it (Android's "Time to take action"), counting its action button; it dismisses through the caller's latest callback.
- **Full third-party notices, generated.** Settings' Open-source licences lists every licence the apps ship with the libraries it covers, by platform, and its full text: Apache 2.0 for every Maven dependency (Kotlin, Compose, AndroidX, kotlinx, Skiko, Guava's listenablefuture, JSpecify), and for the iOS app the native code Skiko links statically, which no dependency report lists: Skia and skcms (BSD 3-Clause), HarfBuzz, ICU (Unicode License v3), libpng, libjpeg-turbo, libwebp, zlib, Expat, Wuffs and the Adobe DNG SDK, found with `nm` on the release framework. `native/scripts/third-party-notices.py` generates the list from the Android release classpath and the iOS klibs, and the iOS CI job runs it with `--check`; a dependency group missing from its licence table, or a new Skiko version, fails the check until someone has read the licence. In the broad groups (AndroidX, `org.jetbrains`, kotlinx) every artifact is approved by name as well, so a new artifact there under another licence cannot slip through on its group; and an iOS report with Compose but no Skiko fails, since it would leave out the bundled native code. Settings draws the notices, a couple of thousand lines, in a LazyColumn. A plugin such as AboutLibraries was not used: it would add a Gradle plugin and runtime library to the strictly verified dependency set and still could not see Skiko's native components.
- **Accessibility semantics.** The app bar title and the switcher button are headings, as are screen titles such as "My schedule" (styled as the web's `.screen-title`); the tab bar, the switcher list and segmented controls are traversal groups rather than containers with their own description, which screen readers would read instead of their children. "I'm interested" is a checkbox-like toggle, so screen readers hear it as checked or not checked.
- **More of the shell is tested on both platforms.** The UI tests now also cover the system Back (the activity's back dispatcher on Android, a navigation event dispatcher on iOS, where Compose's back handler listens for the edge swipe), the Theme setting, release builds ignoring every debug option, the debug connect option's link rules, an official-server link without a warning, the link that waits for a typed server, a 320 dp phone at twice the font size, a 1024 by 768 window and a phone in landscape, the confirm dialog at 2.5 times the font size, talk card links and toggle, chip rows, and toasts. Compose's `DeviceConfigurationOverride` sizes and font scales are not supported on iOS, so the tests use a small helper that lowers the density to fit and leaves out the real window's insets. The tests set the Server URL without focusing the field, because the software keyboard of an emulator with a small screen covers the Save button while it animates; the keyboard itself was checked on the emulator and the simulator. CI also starts the R8 release build on the emulator (`native/scripts/release-smoke.sh`) and signs the release APK only after the emulator job passes.

## Native apps phase 2a: talk features on the device (2026-11-10)

- **Capabilities follow the contract.** `Capabilities.effective()` is a port of `effectiveCapabilities()`: unknown values fall back to the most conservative known value (an unknown `tier` becomes the label `unknown`, which gates nothing), a missing field is off, `{}` and documents without an integer `api_version` are invalid, a range entirely above this app's majors means "update the app", people features need both `enabled` and `reports`, and presence gates GPS bands, meets and Bluetooth. `near_rssi` is clamped, the other numbers fall back to their defaults per field, the service UUID is always the v1 constant, and `bundle_base` is used only when it is https, ends in `/` and has no credentials, query or fragment. `Capabilities.Legacy` is now exactly `legacy-effective.json` (`server-rotate` Bluetooth); what this app can use of any feature set is a separate filter, `forThisApp()`, which turns `server-rotate` into none (Phase 4 brings only derived-v1) and `semantic: client` into off. The contract fixtures run in the common tests.
- **Discovery and the "has served a document" mark.** Discovery is `discoverCapabilities()` step for step, including the strict legacy probe (the exact 404 body, then the exact health answer, only for a backend that has never served a document). The last good document and the mark are stored per normalised backend base. A failure leaves the app on its cached document; with none, the build's default backend (the live tier 3 server, decision 6) falls back to the tier 1 demo for talk features, and any other backend shows as unreachable.
- **A connect link needs a confirmation that names the base.** `ConnectLink.parse()` follows `parseConnectLink()`: https only with no debug exception, and the prompt "Switch to the server at <base>?". The confirmation screen exists; the platforms do not yet route `caddie://connect` links to it.
- **Bundles are verified before use and kept until a new one verifies.** The client reads `conferences.json` entry by entry like `readConferenceIndex()`, sends `If-None-Match` with a stored ETag and keeps the last good copy per URL for offline use. It downloads exactly `bundle.json` and `vectors.i8`, reading each no further than the size the index gives, and runs the client checks of `verifyBundle()` (sizes, SHA-256, content hash, path, canonical JSON, the semantic rules), which never throw. A bundle that passes is decoded strictly against the schema's shapes (a wrong type anywhere refuses it, and links must be http(s)) and must belong to the conference it was listed for. It is written to `{content hash}` under a per-backend directory, then installed in SQLite in one transaction, and only then is the previous directory deleted. SHA-256 and canonical JSON are implemented in common Kotlin and checked against the published SHA-256 vectors and the fixture bytes.
- **SQLite with FTS5 through the bundled androidx.sqlite driver.** One database holds the settings, the HTTP cache, the installed bundles with an FTS5 index per backend and conference, and the interested lists. Migrations are a list of statements per `user_version`, applied in order, each in a transaction; a database from a newer app is refused rather than downgraded. A JVM target on `shared` runs the common tests on Linux and macOS with the desktop build of the same driver; Android host tests are no longer used because they cannot load its native library.
- **Keyword search ports the server's behaviour, not its scores.** FTS5 with the Porter stemmer stands in for Elasticsearch's english analyzer, English stop words are dropped, and the server's `minimum_should_match: "2<60%"` is applied by counting matched terms. BM25 weights title 2, abstract, speakers and taglines 1 as the server does, and also searches topics, track and room at 0.5, which the server leaves to its semantic leg; until on-device embeddings arrive (phase 2b), those words would otherwise find nothing. Filters, the facet counts (each group counted without its own selection), time phrases (ported from `server/phrases.mjs`, lunch from the bundle's break items), Happening now (judged in the conference's time zone) and "Did you mean" chips (ported from `server/facets.mjs`) follow the server. Between two partial suggestion matches, Elasticsearch orders by BM25 and the app by talk count, so their order can differ.
- **Talk screens.** The Search view, the Filters sheet and My schedule follow the web app's structure and wording. A talk opens in a sheet that adds what the bundle carries: speakers with their taglines, the abstract and the precomputed related talks, which open in the same sheet and work offline. For you stays a placeholder until phase 2b; People stays hidden unless the backend serves people features.
- **Debug-only local backends.** Debug builds may point at plain http on `localhost`, `127.0.0.1`, `[::1]` and `10.0.2.2`, and then also accept a bundle base on those hosts, so bundles built with `scripts/build-bundles.mjs` can be served from the developer's machine. Release builds accept neither.
- **No App Transport Security exception on iOS.** Instead of allowing plain http in the iOS app, local testing serves the bundles over https with a certificate from a throwaway CA that is trusted only in the simulator (`xcrun simctl keychain booted add-root-cert`). The app and its Info.plist stay the same in every configuration.
- **A bundle base with nothing published yet is "No conferences yet".** The live tier 3 server already names the Pages bundle base, which answers 404 until the Pages workflow publishes; the app shows the web's empty state rather than an error. When the default backend cannot be reached at all and nothing is cached, the app tries the tier 1 demo for talks.

### Phase 2a review fixes (2026-11-10)

- **Stored first, fetched behind it.** At start the app shows the cached capabilities, the cached conference list, the stored conference, its installed bundle and the marked talks before it sends a request, then asks the backend again (stale while revalidate). A network that accepts connections and never answers used to hold the start behind three 60-second timeouts; now it only keeps the capabilities marked as being checked, and the switcher, search and stars work meanwhile. The core's calls run one after another under one lock that is held only to read local state and publish results, never across a request; downloads run in jobs that publish only if the backend and the conference they worked for are still selected. A conference chosen while the list is being fetched keeps the choice.
- **Capabilities follow their max-age.** The document is fetched at every start and, on return to the foreground, again once it is older than its `max-age` (an hour without one), or at once while the copy in use is the offline one, as `docs/contracts/capabilities.md` asks. The conference list keeps its 15-minute rule.
- **The tier 1 fallback is stored like any document.** When the default backend is down and the demo answers, the demo's document is stored under the default backend's base, marked as the fallback, so an offline start later finds its conference list and bundle instead of "no conference list saved". It never sets the "has served a document" mark of the default backend, and the default backend's own document replaces it as soon as it answers.
- **"Update the app" also shows with a copy in hand.** A conference list of a later `index_version`, or a conference whose bundle has a later `bundle_version`, keeps the copy the app can read in use and says so above the talk screens; it no longer counts as offline.
- **A star lands in its talk's conference.** The conference of a mark comes from the talk id (`{slug}:{id}`), and a conference switch publishes the slug, the bundle and the marked talks in one update, so a tap during a switch cannot store a talk under the other conference.
- **Marked talks keep a copy.** As the web keeps `toInterested()` copies in local storage, each mark stores the talk's public schedule fields (title, speakers, room, track, times and links), refreshed whenever a bundle still holds the talk. My schedule shows a talk the current bundle dropped from its copy, and the tab's count is the number of talks the list shows.
- **Two database files.** Everything that can be downloaded again (the cached conference lists, the installed bundles and the search index) moved from the main database to a cache database attached to the same connection. On iOS the cache database and the bundle files sit in directories excluded from backups, while the main database (settings and marked talks) stays in them; after a restore the bundles are downloaded again, which the tests cover by deleting the files under an installed bundle. Schema version 2 of the main database drops the old cache tables, so a database from the first 2a builds migrates in place.
- **A database that cannot be opened never stops the app.** The platforms open the database lazily on its own I/O thread, so Android's main thread never waits for it. A corrupt main database is moved to `caddie.db.unreadable-{time}` (the newest three copies are kept, older ones deleted) and replaced by an empty one, and the person is told once. A main database from a newer version of the app (a downgrade, or a restored backup) is left where it is, so that version opens it again after an upgrade, and the launch runs in memory, as it does after any other failure (no space, no permission); the notice then says that talks marked now will not be kept. A broken cache database is deleted and created again without a word. `CaddieDatabase.open()` still throws, which the tests use to check the refusal itself.
- **Bundle files that are too large are invalid, not offline.** A file that grows past the size the index gives is reported as a bad bundle; only a failed transfer counts as offline.
- **Search survives a rotation and offers Retry.** The Search screen's state lives in a ViewModel (Lifecycle 2.11's `lifecycle-viewmodel-compose`), and the open talk in saved state, so an Android configuration change keeps both; searches still run in the composition's scope, and one cut short runs again. A search that fails shows the web's "Something went wrong" state, or its banner above earlier results, with Retry.
- **Links never get the local http exception.** A server confirmed from a `caddie://connect` link or a QR code must be https even in debug builds; only a server typed in Settings may be local http there. The core keeps a "typed" mark per backend base, and only a typed server's capabilities may name a plain http bundle base on a local host, so an https server reached through a link cannot point the app at one either.
- **The default conference is judged in its own time zone.** "Has not ended" compares the conference's end date with today's date in the conference's time zone, not in UTC.
- **Response bodies are streamed with a hard limit.** `KtorHttp` reads the body through `prepareGet().execute {}` rather than letting Ktor buffer it, refuses a declared `Content-Length` above the limit before reading, and stops reading as soon as the bytes pass the limit, so a host that sends an endless body costs at most the limit in memory. The bytes go straight into one array sized from the declared length, which grows only when a compressed body runs longer, so a body is never held twice.
- **Every bundle file has its own cap, checked before downloading.** `bundle.json` may be at most 16 MB (KubeCon's is 1.3 MB) and `vectors.i8` at most 32 MB, and the vector file's listed size must equal the entry's vector count times its dimensions; an entry that breaks any of these is refused before a byte is fetched. Reading `bundle.json` means its bytes, its text and its JSON tree at once, so these caps are what keep a hostile index from exhausting memory; an allocation that still fails (or any other error) refuses the bundle instead of ending the app, and the core's jobs catch errors as well as exceptions for the same reason. The conference list is capped at 1 MB (some 750 conferences), which also keeps its request timeout near two minutes.
- **Large files get time to arrive, stalls still fail.** The whole-request timeout of a GET grows with the size it may read, at a minimum average rate of 8 KB/s (60 seconds at least), so a bundle on slow venue Wi-Fi is not cut off after a minute; the 30-second socket timeout ends a transfer that stops sending. Range requests to resume a broken download were left out: bundle files are small enough to fetch again.
- **Text is hashed as Node encodes it.** Before hashing, lone UTF-16 surrogates are replaced with U+FFFD, because the JVM's encoder writes them as `?` while Node and Kotlin/Native write EF BF BD; without this a `text_hash` could differ between Android, iOS and the producer.
- **Zone abbreviations come from Intl.** The talk time's zone name uses a table generated from Node's Intl in en-US (`native/shared/scripts/generate-zone-names.mjs`), which lists every zone that US English abbreviates, including Canada, Mexico, Central America and the Caribbean and their aliases; every other zone is written as a GMT offset, as Intl writes it.
- **The 60% rule counts within one field.** The server's `multi_match` is of type `best_fields`, which applies `minimum_should_match` to each field separately, so the device now requires the needed number of terms within a single column (title, abstract, speakers, taglines, topics, track or room) instead of across all of them; ranking is still BM25 over every column.
- **The licence notices cover the network stack.** Ktor, OkHttp and Okio (Apache 2.0) and SLF4J's API, which Ktor uses on Android (MIT, its text in `native/licenses/slf4j.txt` from the jar, since its POM names no licence), are in the notices script's table, so `third-party-notices.py --check` passes and Settings lists them. androidx.sqlite and the kotlinx libraries were already covered by their groups; the SQLite source the bundled driver compiles is in the public domain and needs no notice.
- **The talk screens follow the shell's layouts.** They sit in the shell's centred column of at most 720 dp in a wide window, their chip rows wrap there as the shell's do, and the sheets keep Material's 640 dp maximum width, the web's `.sheet` width. UI tests open them in a 1024 by 768 window, a phone in landscape and a 320 dp phone at twice the font size.
- **A server that needs a newer app says so with nothing saved.** When discovery finds only documents a newer app can read and nothing is cached, the conference list's state is "update_app" with "This server needs a newer version of the app", not "offline".
- **Tests wait for the core, not for its requests.** `CaddieCore.awaitIdle()` returns once every earlier call and every fetch it started have finished; the tests use it where they used to wait for a request to go out, which raced the job still publishing, and the test teardowns close the database with `closeWhenIdle()` after any statement a screen's search still has queued.
- **The live Pages bundles, through both engines.** A probe (run once, not kept) fetched the published `conferences.json`, revalidated it with its weak ETag and downloaded a bundle through OkHttp on the JVM and NSURLSession in the booted iOS simulator: both decode the gzip body, both answer the conditional request with 304 rather than URLCache serving a 200, and the sizes and hashes match the index. Kotlin's standalone simulator test runner cannot validate the github.io certificate chain (Let's Encrypt's Root YR), while Safari and the app in the booted simulator can, so the probe runs in the booted device.
- **"Not published" is the shell's state.** A conference listed without a bundle is not searchable in the switcher, so the person meets the shell's "Schedule not available" state rather than the talk screens' own copy of it; the UI tests check that path.

## Native apps phase 2b: meaning-based search on the device (2026-11-10)

- **The query model ships in the app: bge-small-en-v1.5 int8.** The apps embed search queries with `Xenova/bge-small-en-v1.5` `onnx/model_quantized.onnx` (34.0 MB, the int8 export the contract fixture already measures as `similarities_q8`) at the revision the bundle builder pins. The talk vectors stay the builder's fp32 embeddings, quantised in the bundle. Measured on 72 attendee-style queries (`native/shared/fixtures/query-embeddings.v1.json`, generated by the builder's own fp32 embedder): the int8 query vectors have a mean cosine of 0.9960 to fp32 (minimum 0.9818), the same top talk for 91.7% of the queries and 91.9% of the top 5 in common over KubeCon's talk rows. The other int8 exports were worse (`model_int8.onnx` 0.9741, `model_uint8.onnx` 0.9884); fp32 would add 133 MB, and fp16 is not well supported by ONNX Runtime's mobile CPU kernels. Shipping the file, rather than downloading it on first use, keeps search working offline from the first launch and keeps phones from contacting Hugging Face; the cost is size (below). The build downloads it from the pinned revision and refuses it unless its size and SHA-256 match (`native/gradle/pinned-downloads.properties`), so the repository holds no model file.
- **The same numbers on every platform.** The real model runs in the tests: on the JVM (an Apple silicon Mac) and in the iOS simulator `BgeEmbedderTest` gives mean 0.996 and minimum 0.9818 (median 3.7 ms and 6.7 ms per query), and on an arm64 Android 16 emulator `EmbeddingDeviceTest` gives mean 0.9960 and minimum 0.9818 (median 4.4 ms, p95 5.5 ms, 0.5 s to load the model; 9.8 ms, 132 ms and 0.9 s in a run while other builds loaded the machine). Both also check the contract's conformance rule on `contracts/fixtures/embedding/reference.v1.json` (every cosine within 0.02 of fp32, the same best talk). A query takes 2 intra-op threads; one thread was not needed for determinism, because each query is embedded on its own.
- **ONNX Runtime 1.30.0 on Android, iOS and the JVM.** 1.31.1 is on Maven Central, but Microsoft publishes no iOS archive for 1.31 (`pod-archive-onnxruntime-c-1.31.x.zip` is a 404), so every platform stays on 1.30.0. Android uses `onnxruntime-android` (the full build) through the Java API, the JVM tests the `onnxruntime` CPU package, and iOS the C API from the official pod archive, through a Kotlin/Native cinterop whose `.def` holds a small C wrapper (open a session from bytes, run one text and copy out the [CLS] state, close). The static library goes into the klib and from there into the ComposeApp framework and the test executables; Xcode needs no change. The archive's SHA-256 is pinned, because its podspec carries none. An encoder in Swift was the plan's sketch, but the cinterop lets the shared tests run the real model in the iOS simulator.
- **ONNX Runtime's telemetry is off.** ONNX Runtime 1.30 on Android and Apple platforms uploads usage events to Microsoft (`mobile.events.data.microsoft.com`) and keeps a device id, unless `ORT_DISABLE_TELEMETRY` is set before it starts (`core/platform/posix/telemetry.cc`). The apps set the variable once, first thing at start and on the main thread (`CaddieApplication.onCreate` on Android, `MainViewController` on iOS), because `setenv` is not safe while another thread reads the environment; every session also turns the environment's telemetry events off. The Android manifest removes the AAR's telemetry content provider and the `ACCESS_NETWORK_STATE` permission it adds, in the app and in the UI tests' APK, and the Gradle test tasks set the variable for the test processes. The app still sends nothing but requests to its backend and the bundle host. Three checks keep it so: a Gradle task fails any build whose merged manifest has an ONNX Runtime provider or the permission, the release smoke test reads the installed package with `dumpsys package`, and a CI script fails on any use of ONNX Runtime's Java or C API outside `openEncoder`'s two implementations, so every session gets these settings.
- **Size: one APK per ABI, and the published one is arm64-v8a.** The model (34 MB) and ONNX Runtime's native library (23 to 39 MB per ABI) made one APK for three ABIs 66 MB. The build now makes one APK per ABI, without a universal APK: arm64-v8a (39.5 MB) is the one CI signs and the one published on GitHub Releases, under the same `conference-caddie-native-<commit>-release.apk` name, so the release flow does not change; x86_64 (41.5 MB) is built for emulators, where CI runs the release smoke test, and for Chromebooks. 32-bit ARM and x86 are dropped: a phone with only a 32-bit system (some low-end Android Go models) cannot install the native app and keeps the Capacitor app, which has no native code and stays one APK. All the APKs of one build share a version code, which is fine for one published APK; a store that takes several would need a code per ABI. Native libraries are stored compressed in the APK (`useLegacyPackaging`), which takes 95 MB off the download and puts it back on the phone once installed. An ONNX Runtime build reduced to the model's operators could shrink it further.
- **The tokenizer is ours, in common Kotlin, and equal to transformers.js.** `WordPieceTokenizer` implements the model's BertNormalizer, BertPreTokenizer and WordPiece, and is checked against transformers.js on 198 cases (the queries, edge cases of every script, emoji and control characters, and real talk texts). It follows transformers.js where that differs from the Rust tokenizer: a text longer than 512 tokens is cut after `[SEP]` is added, so it ends without one, which is how the builder embedded long talks; and ideographs outside the Basic Multilingual Plane are not padded as Chinese characters.
- **Hybrid ranking as the server ranks.** A text search fuses the FTS5 keyword list (now over the server's fields only: title at weight 2, abstract, speakers and taglines) and the 50 talks nearest by meaning among those that pass the base filters, by reciprocal rank fusion with the server's rank window of 50 and Elasticsearch's rank constant of 60. Facet selections apply after the nearest talks are chosen, as the server's knn pre-filter holds only the base filters, so a facet count is still the total the person gets. The server cannot return a keyword match outside both lists' windows; the device lists them after the fused ones in keyword order, so the total and the list agree. Ties go to the better keyword rank, then the better meaning rank, then the talk id.
- **Keywords alone when the model is not there.** While the model loads (about a second) and if it is missing or fails, search runs on keywords as in phase 2a, topics, track and room included, and once the model has failed results say "Meaning-based matching is not available on this device; these are keyword matches." (the web's note, worded for a device). A bundle without vectors, an embedder of another model and a failed embedding all fall back the same way.
- **Why this rank needs no second request.** The web asks the server for a debug search when a drawer opens; on the device every text search computes the fused, keyword and meaning ranks anyway, so the panel opens at once. Its words are the web's, except the closing note, which names the device instead of Elasticsearch.
- **Evidence.** A result's passage is the stretch of the abstract around the first word of the search text (the server's highlighted fragment), else the start of the abstract, else the title, so no result has empty evidence. A bundle has one vector per talk, so the server's "best semantic chunk" has no equivalent.
- **For you is the server's recommendations, plus marked talks.** Learn topics (a talk with more of them first) and the learn text (embedded as a query; keyword matches over title and abstract without the model, then marked as such) are fused by reciprocal rank fusion; ended and marked talks and every non-talk are left out, and the reasons name only the request's learn topics, as DECISIONS "For you is learn-only" requires. Native only: the talks nearest to the centre of the marked talks form a third list, because on a backend without people features marking talks is the only signal many people give; each suggestion it placed says which marked talk it is like. That list needs only the bundle's vectors, so it works without the model. Ties go to the earlier talk, so the same request always gives the same order.
- **What you want to learn lives on the device.** On the web the learn topics and text are part of the people profile. A tier 1 backend has no profile, so the apps keep the learn topics per backend and conference and the text per device in their own database, and edit both in a sheet opened from For you (the web's topic picker and text field). Phase 3's profile can take them over.
- **Topic picker.** The bundle's topics, ranked as `GET /api/topics`; type-ahead and "Suggested for you" port `server/topics-api.mjs`. Elasticsearch's bool_prefix also scores word pairs and rare words higher; here every matched word counts the same, so close matches can be ordered differently. Its chips, search field and text field are new design-system components (`TopicChip`, `PillSearchField`, `LabelledTextField`) drawn from the web's `.pp-chip`, `.pp-field` and `.pp-text`.
- **Related talks stay the bundle's lists.** The contract gives every talk its five nearest by int8 cosine and tells clients not to recompute them; each now also offers the official link the web gives a related talk, while the row itself opens the talk in the sheet.
- **A new conference list and its bundle appear together.** The core published a refreshed list and then, in a second update, the bundle state that follows from it, so a screen (or a test) could see the list marked offline beside a bundle that was not; `CaddieCoreTest` caught it on the iOS simulator about one run in two. Both now go out in one update.
- **The hosts offer the model; the core loads it when it is needed.** `CaddieApp` takes the model loader as a parameter: the Android activity and the iOS view controller pass the shipped model, and UI tests pass a fixed embedder or none, so they never depend on reading 34 MB of resources. The core runs the loader on the first text search, or the first For you request with learn text, not at start. A failed load is tried again by a later search after a pause that starts at 30 seconds and doubles up to 30 minutes. When memory is short (Android's `onTrimMemory` at the background level or at running-critical, iOS's memory warning) the core closes the session and gives its memory back, and the next text search loads it again. An embedder lives as long as the process otherwise.
- **Licences.** The licences screen now carries ONNX Runtime's MIT licence with the notices of the components it includes (its `ThirdPartyNotices.txt` of 1.30.0, about 340 KB of text) and the model's MIT licence, both for the files that ship outside Gradle's reports too (the C library on iOS, the model on both platforms); `scripts/third-party-notices.py` lists them, splits every text into its paragraphs when it generates the Kotlin file, so the screen does no text work when it opens, and joins texts longer than a class file's string limit. The screen is a lazy list of those paragraphs. `LicencesTimingTest` measures it: on the iOS simulator the first frame took 7.2 s and scrolling to ONNX Runtime's notices 10.3 s when the screen unwrapped the texts with a regular expression, and 15 ms and 0.8 s now; on the Android emulator 332 ms and 4.2 s before, 102 ms and 3.0 s now.
- **Wide windows, landscape and large text.** The new screens sit in the shell's content column and use its touch-target minimum; they were checked in landscape (the rail and the 720 dp column) and at a font scale of 2.
- **The exit criterion runs as a test.** `TalkSmokeTest` (`./gradlew :shared:smokeTalks -Pcaddie.smokeSite=<dir>`) runs every talk check of `scripts/smoke.mjs` that applies to the device against bundles built from the committed data and the shipped model, with the smoke test's names and its expectations from `data/`. All 34 pass; 6 are HTTP validation, paging or speak-topic checks with no device equivalent and are listed as N/A. CI builds the bundles and runs it on every pull request that touches `native/`.

The web has no share of the list: its "share card" on My schedule is ShareAllControls, which shares the person's people profile for the listed talks, needs the People API and belongs to phase 3. `InterestedScreen` keeps the `shareAll` slot with the same signature as the phase 3 branch, so that card plugs in there. Native only, the menu adds "Share list", which sends the list as plain text (the talks by day in the conference's local time, with speakers, room and the official link, and the zone) through the system's share sheet. Text rather than an image: it is small, readable by screen readers, pastes into any app, and needs no renderer per platform.
- **Schedule import on the device is the Worker's import.** The Worker's in-memory port of `server/import.mjs` (`worker/src/talks/import-parse.js` and the matcher in `import.js`) is ported to common Kotlin with the same bounds: lines, cells and properties cut to 1,000 characters before any pattern runs, 100,000 lines, 3,000 entries, 5,000 CSV rows or 100,000 cells, 300 candidates of at most 300 characters, an e-mail check that cannot backtrack, and spaces collapsed before any split. Patterns that use `\s`, `\d`, `\b`, `$` or Unicode classes are matched in code rather than with `Regex`, because those mean different things on the JVM, Android and Kotlin/Native; the remaining expressions are ASCII-only and run on short squashed lines. Every case of `test/import-bounds.test.mjs` runs in `commonTest` on the JVM and the iOS simulator (a heap cap cannot be set from a common test, so the 5 MB shapes check the parser's bounds and time instead), and 28 files produced by the Worker's own code (`native/shared/scripts/generate-import-fixtures.mjs`) give identical candidates (127) and matches (99). Known differences, all at the edges: characters outside the Basic Multilingual Plane count as non-letters, JavaScript's month-table prototype quirk ("constructor 10" read as a date line) and `Date.UTC`'s two-digit years are not copied. The smoke checks im1, im2, im3b, im4 and im5 pass on the device; im3 (a PDF) is N/A by decision 8.
- **On a backend that imports on its server, the device still can.** When the capabilities say `imports.schedule: server` (tier 3), the app reads the file as UTF-8 and sends `{ event, text, filename, mime }` to `POST /api/import/schedule`, as DECISIONS "Tier 3 schedule import accepts text with format hints" allows (a backend found through the legacy probe gets no hints, since it refused them). Matches are mapped to the bundle's talks by `talk_id`; one the bundle lacks counts as unmatched. A 413 or 422 shows the server's sentence. A network failure, a timeout, a 5xx, a 429, another 4xx or a malformed answer imports on the device instead, and so does a file whose text is over the server's 200,000 characters, or a backend the app already knows to be offline: an import never fails only because the server is out of reach, and tier 3 changes nothing for the talk features. Nothing is logged.
- **Files: the platforms' pickers, and "Open in", read safely.** The file picker is Android's Storage Access Framework (`OpenDocument` for `text/*`, `application/json` and `application/octet-stream`, the last for calendar files a provider does not type) and iOS's `UIDocumentPickerViewController` as a copy (CSV, TSV, JSON, text, calendar and `.ics`). Calendar and spreadsheet files can also be opened in or shared to the app: Android intent filters for `text/calendar`, `text/x-vcalendar`, `text/csv`, `text/comma-separated-values` and `text/tab-separated-values` (view and send), and iOS `CFBundleDocumentTypes` for `com.apple.ical.ics`, `public.calendar-event`, CSV and TSV, without opening in place. Android reads only `content:` addresses another app grants, never `file:`, which could name the app's own private files (a confused deputy); iOS deletes the copy the system made for the app once it is read. At most 5 MB and one byte are read, off the main thread. PDF, Word, OpenDocument and RTF files are refused by name, type or first bytes (decision 8), with a sentence that names the formats the apps read.
- **Links follow the web's routes.** `caddie://connect?url=` goes to the existing confirmation through `pendingConnect` and `pendingAfterSwitch`, never gets the debug builds' local http exception, and a refused one is dropped without a word. `caddie://e/<slug>#/<tab>?view=&day=` is `web/src/lib/route.ts` with `caddie://` for the origin, so a web address becomes an app link by changing its start; the web has no link to a single talk, so neither do the apps. The slug is percent-decoded once and must be a bundle slug the backend lists; tabs, views and days are taken only from the known values; people routes open the People tab, with the screen they name since the people core's review fixes (`AppLink.PeopleRoute`, below); anything else, and any link over 2,048 characters, is ignored. Android's activity is `singleTask` so a link reaches the running app. QR codes need no scanner in the apps: the phones' camera apps open `caddie://` links once the scheme is registered, so no camera permission or library is added.
- **No https App Links or Universal Links.** Both need a file at the root of the domain that serves the web app (`/.well-known/assetlinks.json` and `/.well-known/apple-app-site-association`). The tier 1 site is a GitHub Pages project site under `/conferenceCaddie`, whose domain root belongs to another repository; the tier 3 server and the Worker could serve them, but that needs a deploy this phase may not make, and Universal Links also need the associated-domains entitlement in a signed build. They can be added when the web app's own origin is settled.
- **The shell waits for the capabilities before it settles on a tab.** The shell picked its tab in the first frame, before the capabilities arrived, so a first start against tier 3 opened on For you and stayed there when People appeared (seen on the iOS simulator and, in the release-readiness check, in the signed APK from `main`). The shell now keeps the tab asked for (a tap, a link or a launch option), or none: with none it shows the backend's first tab, so an untouched shell moves to People when it appears, while a tab the person picked stays picked, and a tab the backend does not offer shows the first tab until it is offered. This is the same rule as the phase 3 branch's `ShellNavigation.tab`, so the two merge without a change of behaviour. The app bar now has the web's order: the Offline badge, the tab's actions, the gear.
- **Version 0.4.0.** The Android `versionName` and iOS `MARKETING_VERSION` move from 0.1.0 to 0.4.0, the native release the notes are drafted for (after the Capacitor app's v0.3.0); version codes stay 1000 plus the run number.
- **Release readiness, checked, not run.** The secrets `native.yml` reads for TestFlight match `native/README.md` both ways (seven, in the environment `release`); the signed arm64-v8a APK of the last `main` run (`conference-caddie-native-14f2ad5-release.apk`) verifies with v2 and v3 signatures, its certificate is the project's (SHA-256 `15:02:52:…:7C:7B`), and it installs and starts on an API 36 emulator. The only open risk is the first TestFlight run itself, whose `altool` form is written down with its fallback.

### Phase 2c review fixes (2026-11-10)

- **JSON files are read with a bound on memory.** `Json.parseToJsonElement` built the whole tree of a file: 5 MB of `[1,1,1,…]` is some 2.5 million values, about 200 MB, enough to end the app, and any app could send such a file to the exported activity. `BoundedJson` now reads import files and the server's import answers: it checks the whole text against JSON.parse's grammar in one pass without recursion, builds at most 200,000 values and nothing deeper than 16 levels (the walk reads containers to 8 levels and the values just under them, at most 50,000 containers), and does not read as JSON a text nested deeper than 512 levels (JSON.parse has no such limit; no export comes close). A file past the bound is still read as JSON, as the Worker reads it, with the walk's part built. `BoundedJsonTest` checks that a 5 MB flat array builds at most the bound and that five million levels are refused at once. The import also catches errors as well as exceptions, in the core and in the screen's model, so an allocation that fails refuses the import instead of ending the app.
- **A file from another app waits for a tap.** A file opened in or shared to the app opens Import my schedule with the file named and a "Find talks" button; nothing is parsed before that tap. Android reads at most 5 MB and one byte of it off the main thread (`IncomingIntents`), ignores an intent replayed from the recents list (`FLAG_ACTIVITY_LAUNCHED_FROM_HISTORY`) and one whose extras cannot be read (a crafted parcel), and still reads only `content:` addresses; `IncomingIntentsTest` covers each. On iOS the copy the system makes is deleted once read, which `IosFilesTest` checks, and only a file in the app's temporary directory or `Documents/Inbox` is ever deleted.
- **A batch of marks keeps its order.** An import, and an Undo of Clear list, marked their talks with one timestamp, so the list fell back to talk id order; each mark is now a millisecond after the one before it, in the order given.
- **The share sheet gets its subject from a public API.** The iOS share sheet's item is a `UIActivityItemSource` that gives Mail its subject, instead of setting a private key on the controller.
- **The Capacitor app's Interested lists are kept.** The native app installs over v0.3.0 (same id, same key), whose WebView kept the Interested lists in local storage under `https://localhost`. Reading Chromium's LevelDB files directly would need Snappy and the SSTable format, so the native app asks Android's WebView, which reads them itself: once, and only when the old app's `app_webview` directory exists, a hidden WebView loads a page the app serves at that origin (every request answered by the app, nothing from the network), whose script hands back the `caddie.interested.v1.*` keys (at most 100 keys, 2 MB each, 4 MB in all). `LegacyInterested` keeps the entries that pass the web's own check, at most 2,000 per conference, in the order they were marked, with a copy of each talk when its times carry the local offset; they go to the default backend, which the old app always used, after any mark already made in the native app. The profile and the device secret in the same storage are not moved: phase 3 owns them and can read them the same way. Until then, someone with a people profile in v0.3.0 should delete it there before updating (the release notes say so).
- **Smaller fixes.** The import's backtracking test measures against reading 200 KB of ordinary text on the same machine (at least 500 ms, or twenty times that), so a slow debug runner does not fail it; shell requests are numbered by a counter rather than the clock. A known difference in the import's patterns: `IGNORE_CASE` folds only ASCII letters on the JVM and Android but Unicode on Kotlin/Native (JavaScript's `i` without `u` folds by upper case); every pattern is ASCII, so this matters only for the few non-ASCII letters that fold to an ASCII one (the Kelvin sign, the long s) in a schedule line's labels, and common Kotlin offers no ASCII-only flag.

## Native push on the tier 3 server (2026-11-10)

The tier 3 server sends the push nudge to the official iOS and Android apps through APNs and FCM, beside Web Push (`server/native-push.mjs`, the optional routes `PUT` and `DELETE /api/push/native` in `server/push.mjs`, `docs/contracts/people-api.md`, Native push registration). This supersedes "push.apns and push.fcm are false because this server holds no APNs or FCM key" in the capabilities decision above.

- **Only the official deployment pushes natively.** Decision 3 of the native apps plan stands: there is no push gateway, and only the backend that holds the publisher's APNs key and Firebase project can reach the official apps. `push.apns` is true only when `APNS_KEY_ID`, `APNS_TEAM_ID` and `APNS_KEY_FILE` (the path of the mounted `.p8` file, review round 2 below) are all set and usable, and `push.fcm` only when `FCM_PROJECT_ID` is (FCM needs no key, see the review fixes below). With none of them set the server answers `apns: false, fcm: false`, which is what the live service answers today and what every third-party operator keeps.
- **No new dependency.** APNs runs over `node:http2` with token-based authentication: an ES256 JWT (`kid`, `iss`, `iat`) signed by `node:crypto` from the `.p8` key, with `dsaEncoding: 'ieee-p1363'` because JOSE wants the raw 64-byte signature. One session per APNs host is reused for every push and dropped on GOAWAY, close, error, a request timeout or 10 idle minutes. FCM uses the HTTP v1 API with global `fetch` and the runtime service account's own access token from the metadata server (review fixes below). The root keeps its single dependency, `web-push`.
- **One optional route for both platforms.** `PUT /api/push/native` takes `{ event, platform: "apns" | "fcm", token, environment? }` and `DELETE` takes `{ event, platform, token }`. One route with a platform field, rather than one per platform, lets tier 2 serve FCM alone with the same shape. It is an additive optional route, so it went into the same v1 schema and route table with its fixtures, spec and the conformance run (now 26 routes) in this change, as the contracts' versioning rules require; no existing route changed. The routes are marked `frozen` in the route table because this server serves them now. `environment` (`production` by default, or `sandbox`) is per registration so a development build can use the same server; it is refused with `fcm`.
- **A platform the server does not push to answers 404 `push_unavailable`.** A 200 that stores nothing would let the app believe it is registered. A 400 says the input was wrong, which it is not; a 409 tells clients to read again and retry; a 5xx tells them to try later. A 404 falls in the client rule's class "not possible now, refresh the view", and it is also what a backend without the route answers (`{ "error": "Not found" }`), so a client treats both alike and keeps its in-app nudges. Clients are gated by `push.apns` and `push.fcm` anyway; the 404 covers a stale cached capabilities document. The new stable code is in the error table. `DELETE` answers 200 whatever the configuration, so a device can always remove its token.
- **Stored with the Web Push subscriptions, without a mapping change.** A registration is a document of `caddie-people-push` keyed by `sha256("{event}:{profile_id}:{platform}")`, so a device keeps one registration per platform at every conference it is used at, and a new token overwrites the old one (review fixes below). It carries the mapped `event_id`, `profile_id`, `created_at` and `expires_at` like a subscription, so the profile delete, the finishing of a pending delete, both purges and the delete route remove it with no new code; `platform`, `token` and `environment` are unmapped, and the index's `dynamic: false` keeps them in `_source` only, never searchable and never returned.
- **The limits cover every channel together.** A receiver is anyone with a Web Push subscription or a native registration on a channel the server sends on; one nudge to a receiver is one push to each of their subscriptions and registrations, written once into the nudge record's `receivers`, so the 3 an hour count nudges, not devices. The once-per-pair-per-day record is unchanged. With native push configured and VAPID not, the rule now runs instead of stopping, and the start line says "Web Push nudges are off" rather than "Nudges are off". Without any native settings the rule and Web Push behave exactly as before.
- **APNs priority 5.** It is APNs' normal priority, the one FCM maps its own normal priority to, and it matches the Web Push nudge's urgency normal and the FCM `priority: normal` sent alongside. A nudge is a suggestion, not a person's ask, and `apns-expiration` (now + 600 s, the Web Push TTL; FCM `ttl: "600s"`) drops one that cannot arrive in time rather than showing it late. `apns-collapse-id` and FCM's `tag` are `caddie-nudge`, the service worker's notification tag, so a newer nudge replaces an older one on the phone as it does in the browser.
- **Provider and access tokens.** The APNs provider token is used for 40 minutes. A 403 `ExpiredProviderToken` or `InvalidProviderToken` renews it and retries the push once, but only when the token is at least 20 minutes old: Apple refuses renewals more often than that (`TooManyProviderTokenUpdates`), and a younger token was refused for a reason a new one would not fix. The FCM access token is used until a minute before it expires, concurrent sends share one token request, and a 401 renews it and retries once. A refused provider token that another push has already renewed is retried with the current one (review fixes below).
- **What deletes a registration.** APNs 410, and 400 `BadDeviceToken` (not `DeviceTokenNotForTopic`, see the review fixes below); FCM 404 `UNREGISTERED`, and 400 `INVALID_ARGUMENT` only with a field violation on `message.token`. A 404 without `UNREGISTERED` is what a wrong project id gives, and any other `INVALID_ARGUMENT` would be this server's message; deleting on those would wipe working registrations. Anything else (`DeviceTokenNotForTopic`, 429, 5xx, timeouts, `SENDER_ID_MISMATCH`) logs one line, `Native push failed: {platform} {status} {reason code}` or the error class, and keeps the registration.
- **Secrets.** The `.p8` key is mounted from `caddie-apns-key` as a file of a secret volume that `APNS_KEY_FILE` names (it was the env var `APNS_KEY_P8`, deleted from `process.env` once read, until review round 2 below), pinned to its newest enabled version at deploy time like the Bluetooth keyring, because the key id and team id are read at the same moment from the newest enabled version of `caddie-apns-ids` (`"<key id> <team id>"`, not secret, read by `deploy.sh` like `caddie-vapid-public`); a key version added later must not reach new instances with the old id. FCM has no secret (review fixes below); the runtime service account gets only the Firebase Cloud Messaging API Admin role on the Firebase project. A deploy turns each channel on only when asked (`NATIVE_PUSH_APNS=1`, `NATIVE_PUSH_FCM=1`, review round 2 below). A setting that is present but unusable keeps its channel off with one log line at start that names the setting and the rule, never its value. No key, JWT, access token or device token is ever logged.
- **Accepted for now.** A profile holds at most one registration per platform at each conference, and the nudge pushes to at most the newest 10 subscriptions and registrations of a receiver (review fixes below); a made-up APNs token is deleted at its first push with `BadDeviceToken`. Real delivery through Apple's and Google's services was not exercised: the tests use injected transports, the stub recorder and a local plain-text HTTP/2 server, and the shapes follow Apple's and Google's documentation.
- **Validation.** `npm test` ran 482 tests, all passing (434 before), when this section was written, and 484 at the head the first review read (3e456a8, after the Gitar fix and a merge of `main`); the review fixes below bring it to 497: the JWTs verified against the generated public keys, token reuse and renewal, every APNs and FCM answer above, the configuration and its log lines, the token formats, the real HTTP/2 transport (session reuse, GOAWAY, timeout), the routes with their closed bodies, profile checks, pending delete and write bucket, the delete and purge paths, the nudge sending to Web Push, APNs and FCM together under the shared limits with no name, ref, `profile_id`, spot line or distance in any push (and, after the review, only the generic alert natively), and the capabilities flags with and without settings.

### Native push review fixes (2026-11-10)

- **A native push is a generic alert.** APNs and FCM payloads reach Apple and Google in plain text, while a Web Push payload is end-to-end encrypted to the browser (RFC 8291), so the Web Push nudge's words do not go to the native apps: the receiver's zone, a passage of another attendee's own words and the conference slug in the app URL would all have been readable by the platform. Every native push is now the same bytes but the token: title `Conference Caddie`, body `Someone whose experience matches yours is in your zone right now` (the web app's push notice says "someone whose experience matches yours is in your zone"), and the constant deep link `caddie://people?around=1` (APNs: top-level `deepLink`; FCM: `data.deepLink`), with no `data.url`. No nudge id is sent either: the app has no route that would take one, and Around now shows the match through the authenticated API once the app is open. A phone registered at two conferences opens Around now of the conference it has open, which is accepted. Web Push keeps its words, because only the browser can read them.
- **FCM without a key.** The server no longer holds a service account key for FCM. On Cloud Run it asks the metadata server for the runtime service account's own access token (`GET http://metadata.google.internal/computeMetadata/v1/instance/service-accounts/default/token`, `Metadata-Flavor: Google`; Cloud Run's service identity guide, https://docs.cloud.google.com/run/docs/securing/service-identity, and its container contract, https://docs.cloud.google.com/run/docs/container-contract). That token carries the `cloud-platform` scope (since review round 2 the server asks for `firebase.messaging` only, see below), and the FCM HTTP v1 `messages.send` reference (https://firebase.google.com/docs/reference/fcm/rest/v1/projects.messages/send) lists under Authorization scopes "Requires one of the following OAuth scopes: `https://www.googleapis.com/auth/firebase.messaging` or `https://www.googleapis.com/auth/cloud-platform`" and under IAM Permissions `cloudmessaging.messages.create` on the project, which the role Firebase Cloud Messaging API Admin (`roles/firebasecloudmessaging.admin`, https://docs.cloud.google.com/iam/docs/roles-permissions/firebasecloudmessaging) holds. So the operator links a Firebase project and grants `caddie-runtime` that role there; nothing is exported, stored or rotated, an organisation policy against service account keys needs no exception, and the server already calls the Natural Language classifier the same way. `FCM_PROJECT_ID` alone configures FCM and turns it on; `FCM_SERVICE_ACCOUNT_JSON` and the secret `caddie-fcm-service-account` are gone from the server, `scripts/deploy.sh`, the checklist and the contract. The token is cached until a minute before it expires, like the classifier's. After a failed token request no other is made for 60 seconds: a send in that time fails at once as `failed` with `Native push failed: fcm token backoff` and keeps its registration, so a metadata server in trouble is not asked again for every push. A server outside Google Cloud with `FCM_PROJECT_ID` set advertises `push.fcm: true` and fails every FCM send at the token; only the official Cloud Run deployment sets it.
- **`DeviceTokenNotForTopic` keeps the registration.** APNs answers 400 `DeviceTokenNotForTopic` for every token when `APNS_BUNDLE_ID` is wrong, so deleting on it would wipe every registration after one bad deploy. It now fails with a log line like any other refusal; only 410 and 400 `BadDeviceToken` delete.
- **FCM `INVALID_ARGUMENT` deletes only when it names the token.** A 400 `INVALID_ARGUMENT` counts as gone only with a `google.rpc.BadRequest` field violation on `message.token`; without details, or naming another field, it fails and keeps the registration. The shape follows Google's error model and the FCM error documentation, not an observed answer. Follow-up: check it against a real answer once the official deployment sends to a made-up token.
- **The push flags mean configured and well-formed, and turn off when refused.** `push.apns` and `push.fcm` cannot prove that Apple or Google accept the credentials before a send. After five authentication failures in a row a channel turns itself off until the server restarts: the flag, and so `GET /api/capabilities` (now built per request from fixed settings and the two live flags), answer false, sends stop, `PUT /api/push/native` answers 404 `push_unavailable`, and one line says `APNs push is off: 5 authentication failures in a row.` (or `FCM`). Five, because one is a hiccup and five in a row, with a renewed token in between, is a revoked key, a wrong team or a missing role binding. Only failures that this server's credentials cause count, so no client can switch a channel off for everyone: for APNs a 403 from the production host (Apple reserves 403 for "an error with the certificate or with the provider authentication token"; a client chooses sandbox, and a key may be limited to one environment), for FCM a 401 that a fresh token did not cure and a 403, except `SENDER_ID_MISMATCH` and `THIRD_PARTY_AUTH_ERROR`, which one registration token causes. Any answer past authentication (sent, gone, another 4xx) resets the count; 429, 5xx, timeouts and token request failures say nothing either way. Each Cloud Run instance counts for itself, so for a while one instance may still answer true; a client then gets the 404 at its next registration.
- **A refused provider token retries with a token another push renewed.** When APNs refuses the provider token as expired or invalid and another push has renewed it in the meantime, the push retries once with the current token, rather than skipping the retry because the current token is younger than 20 minutes.
- **GOAWAY and connection errors on the APNs session.** On GOAWAY the transport rejects at once every push in flight on a stream above the server's last stream id (node's HTTP/2 layer also refuses them; the transport does not rely on it), and lets those at or below it finish on the closing session. A push that fails with a connection error (GOAWAY, a refused stream, `ECONNRESET`, `ECONNREFUSED`, `EPIPE`, or node's cancelled-stream and closed-session errors) is sent once more on a fresh session; `apns-collapse-id` makes a push that did arrive twice show once. A timeout is not retried, because its ten seconds are spent. Both cases are tested against a real HTTP/2 server on 127.0.0.1: GOAWAY with two pushes in flight, and a refused connection.
- **One registration per device, platform and conference.** A registration is now keyed by `sha256("{event}:{profile_id}:{platform}")` (the profile id is the device's own), so a token the platform rotates replaces the old one instead of leaving a dead registration beside it; the previous key, `sha256("{event}:{platform}:{token}")`, kept every token a device ever had. Nothing was ever stored under the old key, because no backend has had native push on. `DELETE /api/push/native` keeps its body `{ event, platform, token }` and deletes the requester's registration for that platform at that conference only while it still holds the given token: the token is not indexed, so the route reads the document by id, compares, and deletes with `if_seq_no`/`if_primary_term`, so a `PUT` of a fresh token in between wins. Deleting by platform alone would let a stale client (an old install's last call, a retried request) remove the registration a newer token had just replaced it with.
- **The nudge reads targets per receiver** (since review round 2 in one search, see below). The shared `size: 100` search for every receiver's subscriptions and registrations let one person's many subscriptions crowd others out of the page. `pushTargetsFor` now runs one search per receiver, in parallel (at most 21: the writer and the 20 candidates, and only when the rule found a pair), each capped at the newest 10 (`created_at` descending), with one log line, without an id, when a receiver has more. Raising one shared size instead would still let one person fill the page, and would push to every one of an abuser's subscriptions; the per-receiver cap bounds both, at the cost of a few small searches.
- **Validation.** `npm test` runs 497 tests, all passing (484 at 3e456a8): the exact bytes of the APNs and FCM payloads and the absence of any zone, passage, name, ref, profile id, slug or spot line in them, at the channel and through the nudge; the metadata server token, its caching and the 60-second back-off; the five-failure switch per channel, what counts and what does not (sandbox 403s, `SENDER_ID_MISMATCH`, `THIRD_PARTY_AUTH_ERROR`, token request failures), and `GET /api/capabilities` and `PUT /api/push/native` once it has tripped; the retry with a token another push renewed; GOAWAY with two pushes in flight and a refused connection against a real HTTP/2 server on 127.0.0.1; one registration per device, platform and conference, a rotated token, the delete's token check and its `if_seq_no` guard; the per-receiver target query and its cap; and the nudge without the VAPID keys and with a platform off. `scripts/smoke.mjs` gains np1 to np3 (the push flags are booleans, false without the keys, and `PUT /api/push/native` answers 404 `push_unavailable` for a platform whose flag is false); they were run only against a local stand-in, never against the live service.

### Native push review round 2 (2026-11-10)

- **One search for every receiver's targets again.** The per-receiver searches of the first round ran up to 21 searches per nudge, and so changed the live Web Push path, which made one. `pushTargetsFor` now makes one search per nudge, where `main` made it (once, before the pairs are written, whatever their records answer): `size: 0`, the same filters with `terms: { profile_id }`, a `terms` aggregation on `profile_id` with one bucket per distinct receiver (at most 21), and under it a `top_hits` of the newest 10 (`created_at` descending, `unmapped_type: date`). The per-receiver cap and its log line stay, so one person's many subscriptions still cannot crowd another out; with ten or fewer subscriptions each, the receivers and pushes of a nudge are those `main` sent. Fetching each receiver's targets only after its pair's record was created was the other option, but the record's `receivers` field needs to know who has targets before the create, so it would have meant a second lookup or a changed record. Both Elasticsearch stand-ins learned `top_hits` under a `terms` bucket (sort, size, `_source`, and `_seq_no` only when asked), with tests of their own.
- **A gone registration is deleted only while it is unchanged.** A registration is one document per device, platform and conference, so deleting by `_id` when APNs or FCM reported a token gone could remove the token the device registered while the push was out. The `top_hits` asks for `seq_no_primary_term`, each native target carries its `_seq_no` and `_primary_term`, and `deleteRegistrationIfUnchanged` deletes with `if_seq_no` and `if_primary_term`, treating 404 and 409 as done, like the `DELETE` route. A Web Push subscription is still deleted by id: its id is the hash of its endpoint, and a gone endpoint stays gone.
- **A late retry of an old registration is documented, not refused.** There is no cheap sound way for the server to stop a delayed retry of an old `PUT` from overwriting a newer token. The server can only order a device's requests by when they reach it, and a retry that arrives last is, to the server, the newest registration; storing `created_at` and refusing an older write does not help, because the retry's `created_at` is its own arrival. Only the client knows which token is newer, and a client-supplied timestamp or counter is not trustworthy (device clocks jump, and nothing could verify it) and would add a field to a frozen v1 route. So the contract now has the app send its registration calls one at a time, each after the previous one was answered, and never a `PUT` for an older token after a newer one; a client that does so cannot be overtaken by its own retries. What remains (a client that gives up on a `PUT` and sends the next while the first is still being written) lasts until the app's next start, when it registers its current token again, as the contract already asks; if the old token is dead, its first push deletes that registration (guarded as above) and the next start registers the current one. A test pins that the last `PUT` wins until the device registers again.
- **Native push is on only when a deploy asks for it.** `scripts/deploy.sh` turned FCM on whenever the deploying shell had `FCM_PROJECT_ID` exported, and APNs whenever `caddie-apns-key` existed, so a routine or test deploy (`SERVICE=conference-caddie-test`) could start pushing to real devices without anyone choosing it. Each channel now needs its own switch in the deploying shell, `NATIVE_PUSH_APNS=1` and `NATIVE_PUSH_FCM=1`; APNs got one too, for the same reason and so the two read alike. Unset or `0` deploys the channel off, whatever secrets or project id exist (`--set-env-vars` and `--set-secrets` replace the whole set, so off is off on the new revision); any other value stops the script, and a switch that cannot be honoured (no `caddie-apns-key`, no `FCM_PROJECT_ID`) fails the deploy rather than deploying the channel off. Every deploy prints one line, `Native push: APNs ...; FCM ...`, with on or off for each and, when on, the secret versions, the bundle id and the Firebase project, never a key. The cost: the official deployment must pass both switches on every deploy that should keep native push on, and the printed line shows when one was forgotten.
- **Both APNs secrets are pinned to the versions read together.** The key was pinned to its newest enabled version while the ids were read at `latest`, which can be a disabled version or one that does not belong to the mounted key. `newest_enabled_version` (version metadata only, never a payload) now resolves both, and the ids are read from that version explicitly; the Bluetooth keyring uses the same helper. Rotating means adding both new versions before the deploy; disabling both rolls back.
- **The FCM token has the `firebase.messaging` scope only.** The FCM channel asks the metadata server for `.../service-accounts/default/token?scopes=https://www.googleapis.com/auth/firebase.messaging` instead of taking the default `cloud-platform` token, so a leaked token reaches FCM and nothing else. It is cached by the FCM channel alone; the classifier in `server/moderation.mjs` keeps its own token with the default scope.
- **The APNs key is a file, not an environment variable.** An env var secret is in the environment block the process starts with (`/proc/self/environ` on Linux) for the life of the process, whatever `process.env` later says. `deploy.sh` now mounts the pinned key version as `/secrets/apns/AuthKey.p8` of a secret volume (a `--set-secrets` key that starts with `/`, beside the env secrets) and sets the plain env var `APNS_KEY_FILE` to that path. `server/native-push.mjs` reads the file once at import, only once the other APNs settings are usable, refuses one over 16 KB, and keeps the key as a `KeyObject`. An `APNS_KEY_FILE` with no readable file behind it (nothing mounted) turns APNs off with the one line `APNs push is off: APNS_KEY_FILE names no readable file.`, which names neither the path nor the content, and never stops the server. The tests write their generated keys to a temporary directory of their own that is removed at exit.
- **The two people of a pair are pushed 0 to 3 seconds apart.** Pushed back to back, two phones side by side lit up at the same moment, which tells two people standing together that the nudge is about each other. When both people of a pair get the nudge, the pushes to the second wait a random 0 to 3000 ms (`crypto.randomInt`) after all of the first's, on every channel. The pause is part of the work that already runs after the presence write was answered; the writer receives at most 3 nudges an hour, so one run pauses at most 3 times. The pause is injectable for tests. The Cloudflare Worker's Web Push port of the nudge (`worker/src/push/nudge.js`) is not part of this change.
- **APNs 403s from the sandbox host still do not count toward the switch-off (no change).** The environment, and so the sandbox host, is chosen by the client on its registration, so a 403 from `api.sandbox.push.apple.com` says nothing this server can trust about its own key: counting it would let any client with a sandbox registration turn APNs off for everyone with five pushes. The cost is accepted: a key that Apple refuses only on the sandbox host, or a revoked key while every registration is a sandbox one, never trips the switch; each such push fails with one line `Native push failed: apns 403 {reason}` and keeps its registration, while production 403s still count. A client choosing sandbox also makes this server open a session to Apple's sandbox host, bounded like any push by the nudge's limits.
- **Validation.** `npm test` runs 510 tests, all passing (497 at d621830): one search for every receiver with the cap of ten, through `pushTargetsFor` and end to end through the nudge, and the second run of a day still making one search; the stand-ins' `top_hits` and guarded delete; a gone token after a rotation keeping the new APNs and FCM registrations, and every gone delete guarded; the last `PUT` winning until the next registration; the `firebase.messaging` scope in the token request; the key file read at import, missing, a directory, oversize, not a key, read only after the other settings, and never in the environment; and the pause between the two people of a pair, its range, and the real timer by default. `scripts/deploy.sh` passes `bash -n`; its native push and Bluetooth blocks were exercised only by extracting them into a scratch harness with a stub `gcloud` shell function (defaults, `FCM_PROJECT_ID` exported alone, each switch on, both on, every refusal), never by running the script or `gcloud`.

## The ingest run publishes the talk bundles (2026-11-11)

- **One publisher of fresh schedules.** The ingest run (`ingest.yml`) builds and deploys the Pages talk bundles of the conferences it has just pushed to the Worker, from the same fetched files, by calling `pages.yml` with them as an artifact. Every build passes `--live`, and keeps a live bundle whose schedule is newer than `data/` (or whose latest fetch failed) instead of rebuilding it. Rejected: comparing content hashes only (cannot say which side is newer) and building the bundles from the Worker's API (a second source of truth with another shape).

Because the Pages CDN serves the previous deploy's files for up to ten minutes, each build waits until the live index and sidecar carry a `Last-Modified` at least as new as the latest successful Pages deployment (Deployments API), and fails after 15 minutes. Ended events drop off the upcoming list, and pushing every `data/` folder would put their old seed back on the Worker while the bundles kept the newer ingest.

## Native apps phase 3: people core (2026-11-10)

- **The people features live in the shared layer, behind one controller.** `native/shared/.../people` ports `web/src/people` (sync, storage, presence, connect, nudges, watch and the parts of push that apply to native push) and talks People API v1 through `PeopleApi`. The screens see only `PeopleController`: one `StateFlow<PeopleUiState>` for the selected conference and suspend actions. Copy that the web keeps in its logic files (sync.ts's delete messages, `presenceProblem()`, the nudge sentences, `friendly()` and `explainBadRequest()`) is ported word for word; copy the web keeps in its screens stays with the screens, which map `PeopleError.Kind`. The controller follows `CaddieCore.state` (`bind`), so `CaddieCore` is unchanged.
- **Device state in a key-value store, not a migration.** The records of `storage.ts` are JSON values under `people:v1:{backend base}#...`: the profile, "Delete my profile", the list of conferences, and one record per conference (visibility, presence, push, blocks, people met, the watch list, nudge records, the unfinished delete). Keys use the normalised base, which never contains '#', so two backends that share an origin under different paths never share a record. A schema change later is a JSON change. Records are read once per backend and written through; a delete mark is stored before its request is sent. They were first kept in `CaddieDatabase`'s `settings` table; the review fixes below move them to a file of their own that no backup carries.
- **The device credential per backend base, in the secure store.** 16 and 32 random bytes from `secureRandomBytes()`, base64url, stored under `SecureStore.scopedKey(backend, "people.device.v1")`. `PeopleApi` sends it only to the backend it belongs to; it never appears in `toString()`, and neither does a `ble_key` or a push token. "Delete my profile" removes it only once the server has confirmed every delete, as the web does.
- **HTTP.** `ApiHttp` (method, headers, JSON body, a per-request time limit that covers reading the answer, a 1 MB read cap) sits next to the GET-only `Http`, and `KtorHttp` implements both. No `Origin` and no cookies are ever sent: no cookie plugin, OkHttp keeps none, and the iOS engine's session is set up without cookie storage. `HttpResponse` gained an optional headers map, so the bundle code is unchanged.
- **Errors follow the contract's client rule.** A stable code maps to its own kind only under its own status; any other `error` falls back to its status class (400 refused, 403 and 404 not possible now, 409 conflict, 410 over, 429 wait, 5xx unavailable). A free-text 409 is retried once on the routes whose route-table entry says so (profile and presence writes, the legacy rotate) and on the meet actions and details. Refusals on the device are kinds of their own: no credential (`no_device`), a delete that covers the conference (`delete_pending`) and a feature the capabilities do not offer.
- **Timeouts, pacing and retries as on the web.** Profile writes and deletes and the presence delete wait 20 s (`WRITE_TIMEOUT_MS`), every other request 30 s. Profile writes and deletes share one write lock (a save waits up to 25 s for it, a delete 15 s, after which it is sent as unconfirmed and repeated). Unfinished deletes are retried from 30 s doubling to 30 minutes, or after a longer Retry-After (at most an hour), at start-up, on every return to the foreground and on their timer; after three refusals of the key, five failures or a day the user may stop. The inbox is polled every 45 s and the Around page every 2 minutes, both stretched by `X-Caddie-Pace`; a Retry-After from the inbox also holds back the next poll, which the web does not do. Positions go at most every 30 s at pace 1. These are the web's numbers, which docs/contracts/people-api.md now names too.
- **Requests send exactly the keys they are given.** The server answers an unknown key with 400, so request types have no defaults of their own: a key the schema allows to be absent or null is an `Opt` (absent, `null` or a value), and the common tests decode every request body of `contracts/fixtures/people-api` into its type and compare the encoded JSON with the fixture byte for byte. Answers are read leniently (unknown keys ignored, unknown enum values read as a default).
- **Privacy rules in one helper.** `PeoplePrivacy` returns a person's zone and band only while both are around, a meet's zone only while it is active (or a same-zone ask waits with both around), spot lines only inside an active meet, and a distance only from `GET /api/meet/{id}` of an active meet; every other answer drops `distance_m` and `bearing_deg` as it is read. The screens use only these.
- **Nudges and push.** The in-app nudge is the web's rule (a strong, never broad, match in my zone; else someone I watch who is around; once per person per day, recorded on the device by the device's local date). When the app is not in the foreground, a strong-match nudge is also shown as a local notification whose body is exactly the server's sentence and names nobody; a watch-list nudge names the person and stays in the app. Native push registers only when the build's channel is one the capabilities advertise, with the final route of the server branch (`PUT`/`DELETE /api/push/native`, `environment` for APNs only, tokens checked against the server's formats); a 404 means no native push on that backend until its capabilities change. Web Push routes are in the client for completeness and unused.
- **Presence.** Zones are the installed bundle's talk rooms (kind `talk`, deduplicated without regard to case, sorted) followed by the five fixed zones in the server's order. Hour mode ends at its `until` and after five minutes in the background, and "Extend" starts a fresh hour; the web has no automatic renewal, so neither has the app. The position is sent only with the person's yes, precise location access and `gps_bands`; approximate access keeps presence zone-only.
- **Ported and deferred.** Ported: profile and visibility sync with every delete path, presence, matches and search paging, Who's around, circles, asks, waves and meets, the inbox, blocks, reports, nudges, the watch list, people met, share-new, banner and notice flags, `hidden_for_owner` and `spot_hidden`. Deferred: Bluetooth (phase 4; presence writes accept `ble`, the client models `ble_key`, the legacy rotate and sightings, and `BleSession` is the seam the controller stops on deletes), For you (phase 2b), the GitHub import, the topic picker's server search, and constructing the controller in `AndroidCore` and `IosCore`.
- **A live harness instead of running the smoke.** `LivePeopleSmokeTest` (jvmTest, only with `-Pcaddie.liveBase`) runs the people checks of `scripts/smoke.mjs` through `PeopleApi`. Test profiles are named "Caddie Native Test ..." with the smoke's synthetic run-tagged words, and every one is deleted and checked to be gone (`GET /api/people/blocks` answers 403 `profile_required`). Checks that need an admin token or an Elasticsearch key, the CORS checks, the unknown-key requests the typed client cannot send, and ble2 are skipped.
- **A secure store that fails is not a missing credential.** A Keychain or Keystore failure (an iPhone before its first unlock, a build without the Keychain entitlement) used to throw out of the credential lookup and crash the app. `DeviceCredentials.lookup()` tells "none" from "cannot read": a read that fails counts as no credential for what is shown and sent, a first visible write answers "This phone's secure storage isn't available right now. Try again in a moment." instead of generating a new credential (which would strand the old profile on the server), and a delete that cannot read the credential stays pending and runs again rather than being taken for a device that never had a profile.
- **People requests read and time out as the bundle GETs do.** `KtorHttp.send` reads the answer through the same `readBounded` as `get` (a declared length above the cap is refused before anything is read, an undeclared one stops at the cap), and its time limit is Ktor's per-request `requestTimeoutMillis`, as for `get`, set to the caller's 20 or 30 s rather than `requestTimeoutFor(size)`, because a People API answer is small and the web waits that long; the connect and socket timeouts are the ones every request has. The request timeout lasts until the body has been read, so an answer that stalls halfway ends at the limit, and it reaches the caller as `RequestTimeout`, also when an engine reports it as the cancellation that carries `HttpRequestTimeoutException` while the caller is still active. The coroutine `withTimeoutOrNull` around the request and the per-request socket timeout are gone. Nothing of the people layer runs under a core lock: the controller follows `CaddieCore.state` and sends from its own serial dispatcher, and its records are never in the cache database.
- **While the stored data cannot be opened, nothing is created that this phone would lose track of.** The base runs such a launch in memory (`CoreState.storageInMemory`) and tells the person that marks made now will not be kept. The device credential is in the secure store and is not affected, but the people records (which conferences hold a profile, unfinished deletes) would be gone at the next start, so the controller, told through `PeopleContext.storageInMemory`, refuses two things. A first visible write (open to meet, a share, sharing that follows Interested) says "The data saved on this phone could not be opened, so your profile can't be shared now..." before a credential is made or anything is sent: a profile created now could neither be shown nor be deleted from this phone after the app closes. "Delete my profile" says nothing was deleted and keeps the key: the empty records of this launch would find nothing to delete and then forget the key, stranding any profile the stored records know about (a database from a newer version of the app is kept for that version to open again). Everything else works for the session (editing the profile on the device, browsing, the device's own lists, reports) and is gone when the app closes, as marks are. Turning every people write off was the other option; refusing only what would leave something on the server that this phone could not find again is as safe and keeps the rest usable.
- **Tests wait for the core and close the database when it is idle.** Every people test that builds a `CaddieCore` stops its scope with `cancelAndJoin` and closes the database with `closeWhenIdle()`, as the base's tests do, and the controller test that follows a real core waits for it with `awaitIdle()` instead of watching for the bundle.

## Native apps phase 3: platform services (2026-11-10)

- **Android secure storage: an Android Keystore key and AES-256-GCM, not EncryptedSharedPreferences or Tink.** Jetpack Security's `EncryptedSharedPreferences` is deprecated, and Tink would be a new dependency for what the platform already does. `AndroidSecureStore` keeps one non-exportable AES-256 key in the Android Keystore (alias `caddie-secure-store`, no user authentication, so it works whenever the app runs, like the Keychain's "after first unlock") and stores each value encrypted with a fresh 12-byte IV that the Keystore generates, in the private SharedPreferences file `caddie_secure_store`. The scoped key is the GCM associated data, so a value copied to another entry does not decrypt, and entries are named by the SHA-256 of the scoped key, so the file does not list the backends the person used (the database holds their base URLs anyway). A value that can never be decrypted again reads as missing; a Keystore error is thrown, so a passing failure never deletes a device secret or replaces the key (review fixes below). Backups and device transfer stay excluded for every SharedPreferences file by the existing `data_extraction_rules.xml` and `allowBackup="false"`.
- **Android location: the platform's LocationManager, not Google Play services.** The APK is distributed on GitHub and later on F-Droid, without Play services. `AndroidLocationProvider` uses the platform's own fused provider on Android 12 and newer when the device has it, and GPS and network positions otherwise, every 5 seconds while collected, on the main looper, and only with precise access. It asks for `ACCESS_FINE_LOCATION` and `ACCESS_COARSE_LOCATION` together, as Android 12 requires, so the person picks precise or approximate; approximate sends no position, because the server keeps none worse than 200 m. Android cannot tell "never asked" from "refused for good" without an activity, so the provider records that it asked (`caddie_permissions`) and asks the activity whether the system would still show the prompt.
- **Permission prompts go through the activity.** Android shows them only from an activity, through an ActivityResult launcher registered before it starts. `AndroidPermissions` in `shared` is the bridge: `MainActivity` registers the launcher and attaches it while it exists, and the bridge outlives activity re-creation, so an answer that arrives after a rotation still completes the waiting request.
- **Android notifications: one "Nudges" channel and taps through the launcher activity.** The channel takes the web's word for these notifications; a tap starts the launcher activity with `CLEAR_TOP` and `SINGLE_TOP` and the deep link as an extra, so a running app gets it through `onNewIntent`. The activity hands only the exact links of the app's notifications, carrying this install's tap key, to `IncomingHandoff`, the same hand-off every `caddie://` link takes, and only for a fresh start or a new intent, never for a re-created activity or one opened from Recents. The intent filter keeps listing only `connect` and `e`: the notification hosts are not public links, and the screens they open are reachable through the web's routes on `e`. The small icon is the launcher icon's calendar with a check, redrawn as a white vector. `POST_NOTIFICATIONS` is asked for on Android 13 and newer.
- **No Firebase in the Android app; Android gets no native push for now.** `firebase-messaging` is proprietary, brings Google Play services, needs a `google-services.json`, and would keep the app out of F-Droid (decision 4 in `docs/NATIVE_PLAN.md`, section 14), so the Android `PushRegistrar` is `NoPush`. People nudges reach Android users in the app, as local notifications while the app runs, and from a periodic background check (review fixes below). The official server can still get an FCM sender for a later build flavour with Play services, which would then register for `push.fcm`.
- **Permissions stay minimal.** The Android manifest adds only `ACCESS_COARSE_LOCATION`, `ACCESS_FINE_LOCATION` and `POST_NOTIFICATIONS`, with `android.hardware.location` not required. There is no background location and no foreground service; Bluetooth brings its own permissions in phase 4.
- **iOS services in Kotlin.** The Keychain, Core Location and UserNotifications are reached from Kotlin in `shared/src/iosMain` through the platform bindings; Swift handles only the `UIApplicationDelegate` and notification centre callbacks, which it hands to `IosPush` and to composeApp's `openNotificationTap`; that reads the link with `IosNotificationTaps.deepLink` and offers it to `IncomingHandoff` on the main thread, which keeps it until the app takes it, so a tap that launches the app is not lost. `IosSecureStore` keeps generic password items under the service `app.conferencecaddie.secure-store` with the scoped key as the account, `kSecAttrAccessibleAfterFirstUnlockThisDeviceOnly` and never synchronisable, so the secrets are in no backup that could be restored elsewhere and never in iCloud Keychain. Keychain errors carry their status code only.
- **The Keychain is checked by the test runner and in the app.** The Keychain tests in `iosTest` run under Gradle in a booted simulator with linked test entitlements (review fixes below; they used to print SKIPPED and pass in the standalone simulator process, which has no Keychain), and debug builds run the same checks in the app with `-caddie.selftest securestore`, which also confirms the protection class and that items are not synchronisable.
- **APNs on iOS, behind the Push Notifications capability.** `IosPushRegistrar` (channel `apns`) asks for notification permission, registers with iOS and waits up to 20 seconds for the token, which it sends as lowercase hex. The app's `iosApp.entitlements` requests `aps-environment` `development`; Xcode sets the signed value from the profile, so App Store and TestFlight builds get `production`. The token's environment is the one the app was signed for, never a guess from the build type: `ApsEnvironment` reads `aps-environment` from the provisioning profile embedded in the app (`development` means `sandbox`), and an App Store or TestFlight install has no embedded profile and always reports `production` (review of PR #42). The App ID and the App Store profile must include Push Notifications before the next TestFlight archive can be signed; the `ios-sign` job checks the profile for `aps-environment` first and names that action when it is missing (review fixes below). A notification's deep link is under `deepLink` in its `userInfo`, for local and remote notifications alike; notifications that arrive while the app is open are shown as banners.
- **Location usage text and privacy manifest.** `NSLocationWhenInUseUsageDescription` says, in the web's words, that the position is used only while the person is around and chose "Use my position too", what it is for, that nobody else sees it and that it is not kept afterwards. It does not mention rounding: the server rounds to 5 decimals, about a metre, which protects nothing. The privacy manifest now declares what the people features send to the official backend, all linked to the profile, none for tracking, all for the app's function: name (the display name), other user contact info (the LinkedIn link and the contact note), other user content (profile texts, topics, shared talks, spot lines, ask notes, meeting points and reports), precise location (only with presence and the person's say-so; cleared when presence ends), user ID (the random per-backend profile id) and device ID (the APNs token; Apple's categories have no closer one, so it is declared rather than argued away). No background modes are declared.

### People core and platform services review fixes (2026-11-10)

- **People records in a file no backup carries.** The records were JSON in the settings table of `caddie.db`, which iOS keeps in iCloud and device backups, while the device credential is a Keychain item for this device only. Restored to a new phone, the records said a profile was on the server that the phone could no longer reach, and the next "make me visible" created a second profile and orphaned the first. The records also name other attendees (people met, watched, blocked), which have no place in a backup. They now live in `PeopleDatabase`, a small SQLite file with one key-value table, through the same bundled driver and opened lazily on its own I/O dispatcher: on iOS `caddie/people/people.db`, a directory excluded from backup like `cache/` and `bundles/`, and on Android `no_backup/people/people.db`. Android's backup rules already exclude every domain from cloud backup and device transfer, but the no-backup directory keeps the records out even if the main database is backed up one day, and both platforms use the same store so the records have the credential's lifetime everywhere. A corrupt file is deleted and created again, and no copy is kept because it names other people. A file from a newer app, or any other failure to open it (no space, no permission, iOS data protection before the first unlock), is left alone, because none of those says the records are gone; that launch keeps the records in memory, `PeopleKeyValue.inMemory` says so, and the controller then refuses to create a profile or forget the credential, as it does when the main database is in memory. The records do not go in the cache database, which is thrown away whenever it is cleared or broken. Existing `people:v1:` keys in `caddie.db` are not migrated, because the people features have never shipped.
- **Records restored without their key are set right, with a notice.** Records that say the server holds this phone's profile while the secure store holds no key describe a profile this phone can neither change nor delete. When the records are opened, and again before a visible write, the device stops treating any conference as holding that profile: it turns the choices, presence and push off, drops the delete marks it can never finish, and tells the person that the earlier profile may stay visible until the conference ends and that turning visibility on makes a new one (a notice that offers the profile). An unfinished "Delete my profile" in that state finishes on the phone with the no-key message. A secure store that cannot be read changes nothing.
- **"Delete my profile" does not trust the device's records alone.** The records and the key are stored apart and either can be lost without the other (a database replaced after corruption, an iOS reinstall that keeps the Keychain). When the key is at hand, the delete also reaches the selected conference and every conference of the backend's list that has not ended (`ConferenceWindow`, the server's `visibleUntil`: 23:59:59 on the last day in the conference's time zone); the server answers a delete with nothing to delete with 200. The list is marked once per "Delete my profile", so retries send only what is still unconfirmed, and a pass stops at the first 429 because the server limits writes per device. The key is forgotten only after at least one delete was confirmed. While the list is not known or the key cannot be read, the delete stays unfinished and the app says so instead of claiming the server copy is gone.
- **A Keystore error is not a missing key.** `KeyStore.getKey` returns null only when the key does not exist; every other failure, passing ones such as a SYSTEM_ERROR, a binder failure or a keystore daemon restart included, arrives as `UnrecoverableKeyException`, exactly like a key that is really broken. `AndroidSecureStore` used to treat that exception as "no key", so a read deleted the entry and a write replaced the key, losing the device credential for good. Now any failure to load the key is thrown and `DeviceCredentials` reports the store as unavailable; a new key is made only when `getKey` returns null; and an entry is removed only when it can never be decrypted (its bytes are malformed, or its tag fails under the key the Keystore did load). A value whose key is missing or permanently invalidated reads as missing and stays until the next write replaces it. The key source is a constructor parameter, so the instrumented tests make the Keystore fail.
- **The Keychain tests run under Gradle.** They used to run as a standalone simulator process, which has no Keychain, and printed SKIPPED while counting as passed. The simulator test executable now carries the entitlements of `src/iosTest/simulator-tests.entitlements` in its `__TEXT,__entitlements` section, which is where Xcode puts a simulator build's entitlements (an ad-hoc signature with those entitlements is refused at launch), and the simulator test tasks boot their simulator first with `simctl bootstatus -b` and run in it. A missing Keychain now fails these tests, and a new test checks that items are this-device-only and never synchronised.
- **Writes outlive their caller; reads do not.** Every people action that changes something on the server or the device runs on the controller's own scope and is awaited by the caller (`scope.async { }.await()`). If the screen goes away, only the waiting is cancelled: the write finishes and the device records the server's answer, so "I'm around", visibility and shares cannot end up on at the server and off on the phone. Actions still run one at a time, in call order, on the controller's serial dispatcher, and one called from the controller's own work runs in place. Searches, meet reads, circle members and counts still stop with their caller. No action throws: an unexpected failure, such as records that cannot be written, comes back as the action's failure value (the generic message, a failed `ApiResult`, false or nothing). Work the controller starts on its own ends quietly through a scope exception handler that logs nothing, because exception messages can carry people data, and the sync's own background work catches a failing store, so a save ends as an error and a retry is tried again later rather than waiting forever.
- **One people session per backend.** The controller keeps one session per backend base for its whole life and takes it up again when a backend is selected again. A child job per session, cancelled on a switch, would cut off a person's write after the server had taken it, and a fresh session per switch would give the same records two in-memory copies with separate write locks. Leaving a backend stops its sync timers, presence timers, position watch and inbox poll; writes and deletes already under way finish and record their answers in that session (deletes would be safe to interrupt anyway, since their mark is stored first). A session whose records cannot be read is never kept half made: it is tried again on the next context, the next action, the return to the foreground and a 30-second timer, and opening is serialised so it is never opened twice. The profile write lock is taken with an owner, so a wait that runs out just as the lock is handed over gives it back.
- **Circle counts are batched like the web's.** Per-card calls within 60 ms share one `/api/circles/counts` request per 100 talks (web/src/people/util.tsx). Answers and failures are kept for a minute, stretched by the API's pace, and a 429, or a 503 with Retry-After, holds every counts request back until that time, capped at an hour. This keeps a venue's shared address under the server's 60-a-minute public limit.
- **Smaller controller changes.** Turning push on asks for a visible profile at the conference before the system's notification prompt, so nobody is asked for a permission that cannot be used yet. People I met are removed by entry, not by position, so a double tap cannot remove the next person. The controller's notice is typed (`PeopleNotice`) and says whether it offers "Open profile", by the web's rule (the message is about the profile) rather than a string match in the screen.
- **People API requests follow no redirect; the public GETs still do.** Ktor removes only `Authorization` when a redirect leaves the host, so a redirected People API GET (the inbox, the block list, a meet) would have sent `X-Caddie-Device` to whatever host the `Location` header named. `KtorHttp.send` now goes through a client derived from the same engine with `followRedirects` off; a 3xx reaches `PeopleApi` as the answer and becomes a failed call, which the profile and delete code treats like a 5xx. The People API never redirects, so a 3xx can only come from something between the app and the server. The GETs of the bundle code and capabilities discovery carry no credential and keep following redirects within https, because a static host may move a file. Neither engine follows a redirect on its own. The iOS session also has no URL cache any more, so the system writes no People API answer to disk; OkHttp has none configured.
- **Notification taps: an exact allowlist, and on Android a per-install key.** The launcher activity is exported, so any installed app could start it with a deep link extra. A tap's link must now be exactly `caddie://people?around=1`, `caddie://inbox` or `caddie://meet/{id}` (id `[A-Za-z0-9_-]{1,128}`), compared character for character on both platforms. On Android the tap's intent must also carry the install's tap key: 32 random bytes as hex, made when the first notification with a link is shown and kept in `noBackupFilesDir`, which no backup or device transfer copies. Only the app's own PendingIntents carry it, and other apps cannot read their extras; `MainActivity` compares it in constant time and otherwise just opens the app. If the key cannot be stored, the notification is shown without its link. iOS needs no key, because only the app and the backend holding the APNs key can post a notification there. A future FCM integration must post through `AndroidNotifier`, since a tap on an FCM notification message would carry its data extras without the key. A push token never appears in text: `PushToken.toString()` shows the channel, the environment and the token's length only.
- **Location.** Android asks the platform's fused provider for high-accuracy positions on Android 12 and newer (`LocationRequest.Builder(5_000).setQuality(QUALITY_HIGH_ACCURACY)`), matching the web's `enableHighAccuracy`, and GPS and network positions below that. It records that it asked only when the permission launcher actually answers, concludes "refused for good" only from a system answer with no rationale left, and asks once more from a state that reads Denied, since Android answers at once when the refusal is permanent; with no activity attached nothing is known, so the state stays "not asked". On iOS the location manager is created on the main thread when the provider is built, and the delegate keeps a snapshot of the authorization state that `access()` reads from any thread, which removes the lazy initializer that blocked on the main queue and could deadlock against it. `IosPeopleServices.create()` must be called on the main thread.
- **APNs environment and release signing.** A simulator build reports the sandbox; a device build still takes the environment from the embedded provisioning profile, and one without (App Store or TestFlight) reports production. The `ios-sign` job checks that the App Store profile carries `aps-environment` before installing it and fails with a message naming the maintainer actions (enable Push Notifications on the App ID, regenerate the profile, update `IOS_APPSTORE_PROFILE_BASE64`); it prints only pass or fail and stays skipped until the TestFlight secrets exist (docs/OPERATOR_CHECKLIST.md, step 7b).
- **Android nudges are checked in the background.** While the person has a visible profile (open to meet) at a conference that still takes people writes (`ConferenceWindow`, in the conference's own time zone), presence is on in a zone, nudges are on for the conference and the system lets the app show notifications, the app keeps one periodic `JobScheduler` job (15 minutes, the platform minimum) scheduled; the decision is the pure `BackgroundNudges.wanted`. Presence is part of the condition because the nudge check does nothing without it, so only day-mode presence keeps the job going (hour mode ends five minutes after the app goes to the background). The job calls `PeopleController.backgroundCheck()`, which shows at most one local notification, only for a strong match in the person's own zone, and whose text names nobody. It is cancelled when the profile goes invisible or is deleted, presence ends, the conference ends or notifications go off, and it re-checks the decision when it runs and cancels itself, so a change the app cannot observe (the system notification switch, a backend without people features) ends it at the next period. A job may start a cold process with no activity: it takes the process's one controller from `CaddiePeople` (which the activity uses too), tells it the app is in the background, waits up to 30 seconds for it to be ready, never runs on the main thread, and a failure ends that run, not the process. The critic asked for a network constraint; it is left out because a connectivity constraint needs `ACCESS_NETWORK_STATE`, which the manifest removes on purpose (phase 2b, ONNX Runtime's telemetry), and offline the job's single request fails and it ends. It is not persisted across a reboot, which would need `RECEIVE_BOOT_COMPLETED`; it is scheduled again the next time the app starts. WorkManager was not needed. There is still no background location and no foreground service.
- **One native push registration per conference, profile and platform.** The server keeps one registration per `(event, profile_id, platform)` (Native push review fixes above), and the profile id is the device credential's. Two phones that share one device credential, which nothing in the apps does today, therefore share that registration, and only the phone that registered last gets native nudges; the other keeps its in-app and local ones. This is accepted for now, and should be looked at again if sharing a credential between devices ever becomes a feature.
- **One link path for people screens.** Notification taps used to reach the people screens through their own channel (`NotificationTaps`), next to phase 2c's `IncomingHandoff` and `AppLink`. There is now one path: every `caddie://` link, a tapped notification's included, goes to `IncomingHandoff`, `AppLink.parse` reads it, and `CaddieApp` turns it into a `ShellRequest`, which carries an `AppLink.PeopleRoute` for the People tab. The web's people routes on `e` are read as the web's router reads them (web/src/lib/route.ts): `#/people` (with "Around now" for `?around=1`), `#/inbox`, `#/meet/<meet_id>` with the id taken only as written, `#/profile`, and `#/here/<zone>` with the zone percent-decoded, at most 120 characters (the records' own cap) and free of control characters, as a candidate the screen matches against the conference's zones; a meet id or zone that does not fit is dropped and the People tab opens. The notification links `caddie://people?around=1`, `caddie://inbox` and `caddie://meet/<meet_id>` go through the same parser, accepted only in the exact shapes `isNotificationDeepLink` allows; plain `caddie://people` is refused, because no notification writes it. A link from a notification is trusted no more than one from another app: every screen it names is reachable through the web's routes, opening a screen sends nothing, and a `here` link only preselects the zone, so presence is turned on only by the person's tap.

### People core review round 2 (2026-11-11)

- **The v0.3.0 device credential and profile come over with the Interested lists.** The Capacitor app kept its people identity in the same WebView storage as its lists: `caddie.device.v1` (`profile_id`, `secret`) and `caddie.profile.v1` (web/src/people/storage.ts). Left there, a person visible at a live conference would keep a server profile this phone could neither edit nor delete, and turning visibility on would make a second one. `CapacitorMigration`'s page now hands those two keys over too, and `PeopleController.adoptLegacy` stores them for the backend the Capacitor build was made against (`VITE_API_ORIGIN`, which is `Defaults.BACKEND`, normalised the way the app keys every secure store entry). The credential is read strictly (`LegacyPeople.credentialHeader`: both parts strings of exactly the contract's 22 and 43 base64url characters) and stored under the same `SecureStore.scopedKey` the app uses, so with it "Delete my profile" reaches every live conference (`markReachable`); the profile is read leniently and cut to the app's limits, so the person types nothing again. What this app already holds wins: `DeviceCredentials.adopt` keeps an existing credential, and an existing profile or an unfinished "Delete my profile" keeps the profile. The hand-over goes first and the lists after it, under the one existing marker: a secure store that fails now leaves the whole run, lists included, for the next start, and the marker is still written with the marks in one transaction, so every step can be made again. The per-conference visibility records (`caddie.visibility.v1.*`) are not brought over: with the credential at hand, turning visibility on updates the same server profile rather than making another, and a delete reaches every running conference whatever the records say. No value read is logged anywhere, and the instrumented tests check the process's log for their fake secret.
- **A background check that times out cancels its job.** When the people state is not ready within 30 seconds (still loading, no conference, or no people features), the job service now cancels the job instead of only doing so when the backend offers no people features. `BackgroundNudgeScheduler` schedules it again on the next ready state that wants it, so a process stuck in loading no longer wakes every 15 minutes for nothing.
- **The job service reads the foreground flag again after clearing it.** An activity can start between the check of `hasStartedActivity` and `setForeground(false)`, and its own `setForeground(true)` would be overwritten. The service now checks again after the write and sets the flag back when an activity has started.
- **Scheduling the nudge job is serialised and cannot kill the collector.** `BackgroundNudgeScheduler.apply` runs under a mutex, because the state collector and `recheck()` can run together, and `JobScheduler` calls run inside `runCatching`, since `schedule` throws when the system's job limit is reached. A failed call is tried again on the next ready state.
- **Opening a session cannot be cut off half way.** `openSession` runs `applyContext` on the controller's own scope (`scope.async { }.await()`, as `write` does), so a read whose caller is cancelled can no longer stop it between `session = s` and the timers, watch and poll being installed. The context lock is still held for the whole of it.
- **One counts request per round trip.** A batch of circle counts used to go out every 60 ms window, so a fling through a lazy list, where each card asks for its own talk as it is composed, sent roughly one request every 60 ms and reached the venue's 60-a-minute limit in seconds. While one counts request is under way for a backend, the next batch keeps forming and goes out only when that one has answered (`formingBatch` waits on the batch under way), so a scroll costs at most one request per round trip, whatever the list's length. The list screens also ask for their results' counts up front (the people screens' change), so the cards find them cached.
- **A changed session ends a counts batch.** When the session differs from the batch's in the middle of a batch, `fetchCounts` returns instead of skipping one chunk and asking the server for the rest, which belong to the old session too.
- **An empty conference list is a known list.** `PeopleContext.listKnown` is true when the core's conference list is loaded, and `listedConferences()` returns the list, empty or not, only then. A backend that lists no conference used to leave "Delete my profile" unfinished for good, because the list was never counted as reached.
- **A wipe that fails half way keeps the delete mark.** `clearAllPeopleData` now clears the conference records first, then the profile, and removes the "Delete my profile" mark last, so a failure leaves the mark and the delete is tried again instead of the profile coming back without it.
- **An unreadable secure store is its own delete failure.** `DeleteFailure.Store` (`store`) replaces `Offline` where the device credential cannot be read, so the person is told about the secure storage (`PeopleError.SECURE_STORE_MESSAGE`) and not that they appear to be offline. It ranks with `Offline` and, like it, leaves the delete mark in place.
- **The iOS CI run keeps its test results, and a flaky core test waits for what it asserts.** The Android job also uploads the XML results, and the iOS job uploads the shared and composeApp reports when a simulator test fails. `aNetworkThatNeverAnswersStillShowsEverythingStoredAtOnce` now waits for the whole expected snapshot and for the first capabilities request instead of asserting them the moment the bundle is ready.

## Native apps phase 3: people screens (2026-11-10)

- **The web's people screens, on the shared controller.** `native/composeApp/.../ui/people` draws People (the presence-off home and the Around home), Profile, Requests, Meet up, the people groups of Settings, the talk circles, the Ask and Report sheets and the nudge banner from `web/src/people`, with the web's words (one strings file per group of screens, each group citing its web file) and the sizes of `people.css`. Every screen takes the `PeopleUiState` it draws and a `PeopleHost` (the controller, moving between pages, the toast, the shared sheets); Profile, Requests and Meet up are pages of the shell's page stack, with the web's Back buttons.
- **Privacy rules in one place.** No screen reads a zone, a band, a spot line, a spot-me line or a distance from an answer directly: they go through `PeoplePrivacy`, which applies `docs/CONTRACT.md` (a zone only when both people are around, a band never as a number, spot and spot-me lines only in an active meet, a distance only on Meet up while it is active). UI tests feed the screens answers that carry too much and assert that nothing outside the rules is shown.
- **What differs from the web on purpose.** Touch targets are the platform's (48 dp on Android, 44 pt on iOS) where the web uses 32 px; text wraps instead of clipping at large font sizes; pickers are sheets of radio rows instead of a select. Meet up shows the distance but no compass or bearing arrow (the web's "Point me" needs a compass; it is left for later). The topic picker searches the conference's topics in the installed bundle on the device instead of `GET /api/topics`. A LinkedIn link opens only when it matches the server's own rule for `linkedin_url` (`https://(www.)linkedin.com/in/{name}`), so no backslash, user name, port or look-alike host gets through. The web's Add to Home Screen and browser push panels have no native counterpart; where the web names the browser (a refused location or notification permission), the apps say so in their own words and offer the system settings. "Open meet-up" also shows on the card of someone whose ask I accepted, not only for my own asks; the review agreed that this is better than the web's. The GitHub profile import is not in this phase.
- **Controls follow the capabilities.** Without `people.meets` there is no Ask, Wave or meet action; without `people.presence` no presence card, Around now, watch toggle or nudge settings; without `people.circles` no circles, share-all or ended-talk banner; without `people.reports` no Report. The web reads no such flags, because its server offers everything.
- **The People tab is picked once the tabs are known.** On a first start nothing is stored, so the shell draws its tabs before the capabilities say whether People is there. `ShellState.tabsKnown` is false until the core's capabilities are no longer loading and, when they offer people features, the people controller has answered; until then no tab shows as selected unless the person picked one, and then the first tab is selected, People on a tier 3 server. A later start shows the stored capabilities at once. A tab the person picked (a tap, a link, a notification or a launch option) is never replaced: the shell's navigation keeps "nothing picked" apart from a picked tab, where the shell before this phase fixed the first tab offered at the first composition, which stayed on For you when the capabilities arrived later. `StartTabUiTest` checks both on the iOS simulator and on Android: a capabilities document held back opens People once it arrives, and a tap on Search before it keeps Search.
- **Text keeps the web's line boxes.** Compose trims the space above a text's first line and below its last, where CSS keeps half the leading on each side, so stacked people texts sat about 4 dp tighter than the web's. The people screens use the web's line boxes (`withCssLineBoxes`), which makes their cards line up with the web row for row; the rest of the app is unchanged. The confirmation dialog takes the screen width minus 24 dp on each side, at most 400 dp, with the web's scrim, which also applies to the Settings and server confirmations.
- **Parity is checked with screenshots of the real screens.** `PeopleParityShots` (composeApp common tests) runs the whole app on `FakePeopleServer`, seeded with the people, profile and conference of the web's mock, and saves each state at 390 and 320 dp, light and dark (plus 2x text, landscape and the wide layout for People, Profile and Meet up), at three pixels per dp like the web screenshots. Normal test runs skip it; native/README.md says how to run it.
- **With phase 2c's schedule views, import and links.** Both stay as they were built. The shell keeps the people screens' page stack (`ShellNavigation`), and phase 2c's `ShellRequest` (a `caddie://` link, and Import my schedule's "View my schedule" and "Switch conference") moves it: a tab leaves every page, as a tap on the tab does, Settings opens as the gear opens it, and the switcher opens only when a request asks for it. Settings' You group lists Profile and then Import my schedule, as the web's does, and the people groups follow it. My schedule keeps its List or Day switch and the Day timeline; the people controls sit on its List cards only, since the web's talk card has them and its timeline does not. The app bar shows Requests on the People tab and the Interested options on Interested. Every `caddie://` link, a tapped notification's included, reaches the people screens as the shell request's `AppLink.PeopleRoute` (see "One link path for people screens" above). The People layer holds a route until people features are on and then shows it once, tab and page together: People (with Around now), Requests or Meet up over the People tab, the profile page over whatever shows, or the presence setup on a zone. ## `caddie-admin` C1: the tier 2 adapter (2026-11-11)

- **A 404 reads as "already done" only when the Worker may have run the request.** An attempt may have run when the Worker answered a 5xx (marked before its body is read; a `daily_limit` 503 stops at once anyway), when the body of a 2xx could not be read, or when the connection broke after undici had written the whole request. The last is known from `node:diagnostics_channel`: undici publishes `undici:client:sendHeaders` and `undici:request:bodySent` with the request, whose headers carry the attempt's `X-Caddie-Admin` value (unique per attempt, by its nonce), and the attempt counts as sent only when both fired for it. A refused connection, a DNS failure, a connect timeout and a reset during the TLS handshake fire neither (checked on Node 22.23 and 26.11, against a real TLS-handshake reset), so their network errors never count, whatever their code; a fetch other than undici's fires neither either, so the rule falls back to the 5xx and lost-2xx cases. The tests inject the probe (`trackSend`). A 429 never counts. Only after such an attempt is a retried delete or unhide that answers `404 not_found`, or a retried unblock that answers `not_found` or `no_operator_block`, a success with a note (`already_deleted`, `already_unhidden`, `already_unblocked`). Otherwise both stay exit 4.
- **A write that fails after an earlier failed attempt says so.** When an earlier attempt of a write failed with a network error or a 5xx, the 404 that ends it (refusal or missing target), the give-up after four attempts and any other final error add "an earlier attempt failed (<code>); if it reached the Worker it may have done the work". A read never says it.
- **The daily limit stops at once.** A 503 whose `error` or `cause` is `daily_limit` is never retried. `PUT /admin/conferences` answers it as `503 {cause: "daily_limit", error: "unretire_incomplete", ...}` when a fan-out hit the limit; the CLI reports `unretire_incomplete` with "run the unretire again after 00:00 UTC". A 502 `unretire_incomplete` is retried (signed afresh, bounded), and its `cause` (`unretire_superseded`, `conference_retired`) is shown with the status.
- **A refusal is not a missing target.** The Worker answers `{"error": "Not found"}` to a refused signature, the failed-signature limiter, an unknown route and a missing nonce, and `not_found` or `no_operator_block` to a missing target. Both are exit 4; the message says "no such target" for the second and "refused: check the admin key, the failed-signature rate limit or the route" for the first. A refusal never reads as "already done".
- **A success must say so.** Every 2xx must carry a JSON object, and `POST /admin/moderation`, `POST /admin/people/block` and `DELETE /admin/conference` must answer `"ok": true`. Anything else is exit 1 with "the request may have taken effect, check before running it again", never a success.
- **Counts after a retry can be short.** A retried purge or removal whose earlier attempt may have run says that the earlier attempt may have deleted more, and audits `note: earlier_attempt_may_have_run`. The audit's `note` key holds one of five enum values and never the `--note` text.
- **An absent conference is exit 4, code `conference_unavailable`.** `400 conference is not available` comes back for a slug the directory does not list (never added, a typo, or removed) and for an admin write to a listed conference whose object holds no document (wiped by a removal that an unretire overtook). The message says "check the slug; if it was removed, run conferences unretire". `stats usage` treats only that code as "no pace" and stops at any other failure.
- **When a tier 2 unretire is sent.** `PUT /admin/conferences` takes `"unretire": true` on a document for any slug, tombstoned or live (`worker/src/directory.js` `#upsert`): the document replaces the directory row, the tombstone is dropped when there is one, and the fan-out carries the unretire's number in the directory's order sequence (`unretired: <n>`), which the conference's object accepts, removed or not, whenever it is above the number of its last wipe (`worker/src/conference.js`, `/internal/conference`, #69 at c74612d). So the CLI decides:
  1. With a removed entry in `data/conference-operator.json` it may send. Tier 3 requires that entry, because the operator file is its only record of a removal.
  2. Without one (tier 2 only, for the repairs below) it sends only with `data/<slug>/conference.json`, never the slug alone, which the directory would store as an unavailable conference. Neither entry nor document is exit 4 ("check the slug"), and nothing is sent.
  3. In both cases it first reads the Worker's public listing (`GET /api/conferences`). A slug that is not listed is sent. A listed slug is sent only when the document's status (searchable, or unavailable for any other value) equals the listed one; otherwise the unretire is refused with exit 1, code `unretire_refused`, because it would take a live conference offline or bring a hidden one back (`conferences hide`, `unhide` and `refresh` change a status). A listed slug with the same status is each repair case: after `removal_superseded` at step `directory` (the overtaking unretire kept the row; the object is wiped, and keeps its removal marker when that unretire's fan-out failed), after `unretire_incomplete` (the row is upserted, and the object kept its removal marker), and after `removal_incomplete` at step `directory` (tombstone and row both present). The check is best-effort: the listing and the `PUT` are two requests, so a removal or an unretire that lands between them is not seen; a server-side `expect_status` on the document, proposed for #69, would close that gap. The Worker serves the listing with `Cache-Control: public, max-age=60`, so the CLI asks for it with `Cache-Control: no-cache` and a `fresh=<ms>` query key the Worker ignores, which no cache on the way can answer from an earlier copy. A listing without a `conferences` array is an error, never "not listed".
  4. The preview and the run both print the status sent and the listed one, as `sending <status> (Worker now <status | not listed>)`.
- **Terminal escaping covers every control, format and default-ignorable character.** Human output escapes `\p{Cc}` but tab, `\p{Cf}`, `\p{Default_Ignorable_Code_Point}` (the Hangul fillers U+115F, U+3164 and U+FFA0, the variation selectors, the combining grapheme joiner U+034F and the rest, which render as nothing), `\p{Zl}`, `\p{Zp}`, lone surrogates and the backslash, so text that spells `\u{1B}` cannot pass for an escaped ESC. JSON output escapes the same classes as `\uXXXX` units, as a surrogate pair above U+FFFF. Human output keeps two characters inside emoji only, so a name with emoji stays readable: the zero-width joiner U+200D inside an emoji ZWJ sequence (a pictograph, optionally U+FE0F or a skin tone, the joiner, a pictograph), and the presentation selector U+FE0F right after a pictograph or in a keycap (a digit, `#` or `*`, U+FE0F, U+20E3). Neither moves the cursor or changes direction. Anywhere else both are escaped, and in JSON they always are. All of these files are ASCII; tests build such characters with escapes.
- **`removal_superseded` comes from either removal step** (#69 at c74612d, where a removal and an unretire are ordered by a directory sequence and the later one wins). At step `wipe` the conference's object had already taken a later unretire and refused the wipe: `wiped` is false, nothing was deleted, and the conference is live as the unretire left it. At step `directory` the object was wiped first and the directory kept the row the later unretire wrote: `wiped` is true with the counts, and the object took the unretire unless its fan-out failed. `retired` is whether the directory holds a tombstone now (true only when a later removal wrote one; null when the Worker could not say). The CLI says which case it is, names the tombstone state, does nothing further, and prints both commands: remove it after all, or keep or restore it with an unretire. A failed wipe is `removal_incomplete` at step `wipe`.

- **The Worker builder returns an empty list.** `buildTopics` in `worker/ingest/topics-local.mjs` no longer throws when no term reaches three talk titles, even with merges. It returns no topics, a talk-to-topics map in which every talk has none, and a warning, as the bundle builder and tier 3 do. A test checks both builders, with and without a merge whose target no title holds.
- **An empty list never replaces a stored one by accident.** `PUT /admin/topics` answers 409 and changes nothing when the request holds no usable topic (an empty array, or only rows of another conference) and the conference has stored topics, unless the body carries `"allow_empty": true`. A replacement that is not empty needs no flag, and an empty list for a conference with nothing stored is accepted. The flag travels in the body only, like `allow_shrink`.
- **The ingest stops first, but only when it can.** A stored list is frozen, so it can become empty only through `--rebuild-topics`. In that case `resolveTopics` reads the stored list and throws before any talk or topic is sent (`PUT /admin/conferences` has already run) when the rebuilt list is empty and topics are stored, so a run refused this way leaves the talks' topics and the list as they were. `push-ingest.mjs --allow-empty` and the ingest workflow's `allow_empty` input pass the flag to both, and `pushEvent` puts `allow_empty` in the `PUT /admin/topics` body only when the flag is set and the list is empty. `topics-local.mjs` only reads, so it reports an empty list instead of refusing it. `pushEvent` also logs the builder's warnings, prefixed with the slug, when the list is empty, so the reason reaches the log.
- **No topic shrink guard on the Worker.** Tier 3 also refuses a list that drops more than 10 topics and 10% of the stored ones. The Worker does not need that rule: without `--rebuild-topics` every stored topic is kept (a topic whose count falls to zero stays at the end of the list), and a rebuild is an explicit request for a new list, so the operator checks the feed before asking for one. The finalize guard covers only part of a short feed: it refuses when more than 10 talks and more than 10% of them would go, and it runs before the topics are stored, so such a feed never stores its rebuilt list. A smaller shortfall passes finalize, which matters for small conferences: PyTorch Day Japan (19 sessions) losing 10 or fewer, or MCP Nairobi (60) losing 10 or fewer, would store a list rebuilt from the short feed. The tier 3 rule (more than 10 topics and 10%) would not catch those either, since those lists hold 2 and 10 topics. Even where it fires, the finalize guard protects the stored list and not the talks' tags: `pushEvent` posts the talks with their new topic ids before finalize, so a rebuild that gets past the empty check (a non-empty list, or an empty one with `allow_empty`) on a short feed re-tags the talks, and then finalize answers 409. The old list stays stored with re-tagged talks until the next ingest without `--rebuild-topics` tags them from the stored list again. A rebuild on a schedule that really shrank therefore also needs `allow_shrink`.
- **The smoke is left as is.** `scripts/smoke.mjs` check t2 fails "<slug> has no topics" for a conference in `SMOKE_EXTRA` (by default MCP Nairobi and PyTorch Day Japan) with an empty list, which is now a valid state. Today every committed conference has topics (KubeCon 96, MCP Nairobi 10, PyTorch Day Japan 2, grpconf 6). PyTorch Day Japan is the one most likely to reach it, since both its topics have exactly three talks, but only a rebuild with `allow_empty` could empty its stored list, so the smoke is not changed.

## Signed admin requests on the Worker (W1, W2, W4) (2026-11-11)

- **The bearer is gone from `/admin/*`.** Every admin request carries `X-Caddie-Admin: v1 <ts> <nonce> <bodySha256> <sig>`, the HMAC-SHA256 of `scripts/lib/admin-sign.mjs`, and the Worker no longer reads `Authorization` there. The verifier is a WebCrypto port in `worker/src/lib/admin-auth.js`, a pure module with the constant-time compare passed in (`crypto.subtle.timingSafeEqual` on Workers, `crypto.timingSafeEqual` in the Node tests), tested against every sign and verify case of `test/fixtures/admin-sign.v1.json`. The canonical string uses the header's `ts` as the header spells it.
- **The order of the checks is fixed, and the body comes last.** Origin header, a usable `ADMIN_TOKEN`, the header's shape, the empty-body hash on GET, HEAD and DELETE, the failed-auth bucket, the signature, then the clock: each answers 404 except the clock (`401 admin_skew`). Only after that does the Worker read the body (4 MB cap), check the clock again, because a body can be held back for any time, and compare the body's SHA-256 in constant time (`401 admin_body`). A 401 therefore needs a valid signature: a key holder's, or a captured header's while its timestamp is still fresh, whose holder can see `admin_skew`, `admin_body` or `admin_replay`; everyone else gets 404. The Worker reads the body as bytes (`readCappedBytes`; `readCapped` is now its text wrapper for the API routes) and forwards exactly those bytes, because a text round trip would change a byte-order mark or an invalid UTF-8 sequence and the object would see other bytes than the ones the signature covers.
- **`ADMIN_TOKEN_NEXT` only beside a valid `ADMIN_TOKEN`.** Both keys are tried on every request, each compare runs even after a match, and each secret is trimmed. Without an `ADMIN_TOKEN` of at least 32 characters the admin routes fail closed, whatever `ADMIN_TOKEN_NEXT` holds, so a half-finished rotation never opens them with the newer key alone.
- **One admin token per deployment.** The host is not part of the signed string, so a request signed for one deployment is valid on any other that holds the same token. Each deployment (a fork, a staging Worker) gets its own token.
- **Nonces per Durable Object, at the signed time.** `admin_nonces (nonce TEXT PRIMARY KEY, ts_ms INTEGER NOT NULL)`, with the index `admin_nonces_ts` on `ts_ms`, lives in every ConferenceDO (schema version 3, new in this change, so the index is part of it; both statements also run at every start outside the version gate, as in the DirectoryDO, so an object that reached version 3 without the index gets it) and in the DirectoryDO. The Worker's 300-second window and the object's 305 seconds go through the same `withinSkew()` with a different limit, so the two checks cannot drift apart. Before any `/admin/*` handler runs, and also for a path or method it does not serve, the object refuses a forwarded timestamp more than 305 seconds from its own `Math.floor(Date.now() / 1000)` (`401 admin_skew`; 300 plus 5 seconds of forwarding slack), then runs `INSERT … ON CONFLICT DO NOTHING RETURNING 1` with `ts_ms = ts * 1000`; no row returned is `401 admin_replay`. Every insert then deletes the rows older than 15 minutes by that signed time, through the index. The object's own clock check is what makes the retention safe: without it, a replay whose body the client held open for longer than 15 minutes reached the object after the first use of its nonce had been pruned, and ran the handler a second time (the security review's proof of concept, now a test). With it, every nonce the object accepts is one it would still remember. The event slug is in the signed path, so a request can only be replayed against the object that served it and no table is shared. A request without both headers, or with values the verifier would never forward, is a 404: the Worker sets them only after verifying, builds every forwarded header set from scratch (a client's copies are dropped), and no internal caller uses an `/admin/*` path (the cron and the conference fan-out use `/internal/*`; a test runs the cron and checks).
- **Admin requests fail closed at the daily written-rows limit.** Recording the nonce writes a row, so once the account's limit is reached every admin request, `GET /admin/stats` and `GET /admin/moderation` included, answers `503 daily_limit` until 00:00 UTC; a read does not skip the nonce. The DirectoryDO maps a daily-limit error to that answer too (it was a 502), so `adminClient` stops at once instead of retrying three times. `src/lib/meter.js` says that under the limit only the cron still gets a reading.
- **Failed-auth bucket that never charges valid traffic.** `peek(key, perMin)` refills a bucket exactly as `take()` does (the two share `refill()`) and takes nothing; a key without a bucket counts as full and is not added to the map. Step 5 peeks `admin-fail:<cf-connecting-ip>` at 10 a minute, and step 6 takes from it only when no key reproduces the signature. A malformed header or a missing key never touches the bucket. 100 valid signed requests a minute from one address all pass. The buckets are per isolate and protect CPU, not the key. Accepted and not fixed: `peek` and `take` are not atomic across the HMAC's await, so bad signatures sent concurrently from one address can each compute an HMAC before any of them takes a token (CPU cost only), and the bucket map is cleared whenever it would pass 10,000 keys.
- **Every client signs, and every retry signs again.** `adminClient` (push-ingest, topics-local, migrate-from-backup) and `worker/scripts/moderation.mjs` sign with `signAdminRequest` and send no `Authorization` header; the client signs each attempt afresh, so a retry carries a new nonce and a later timestamp and the existing admin handlers, which are idempotent, may see it twice. The one exception is `POST /admin/moderation` with `"action": "delete"`, which answers 404 when the target is already gone, so a delete whose first answer was lost reports 404 on the retry. A signer refusal (an API base with a path, a query outside the signer's charset, a token shorter than 32 characters) is a usage error before anything is sent. `moderation.mjs` builds its query without percent-encoding (a slug and an ISO instant fit the charset) instead of `URLSearchParams`, which would encode the colons, and it now takes its base through `normalizeApiBase`, so plain `http:` is accepted for localhost only. Both clients send `CF-Access-Client-Id` and `CF-Access-Client-Secret` through one helper (`accessHeaders` in `worker/ingest/lib.mjs`) when both `CF_ACCESS_CLIENT_ID` and `CF_ACCESS_CLIENT_SECRET` are set; `ingest.yml` passes two optional repository secrets of those names, empty by default, and the Worker does not validate an Access token. In `ingest.yml` the admin token and the Access secrets are set only in the environment of the configuration check and the push step, so the discovery step, which fetches third-party feeds, does not receive them in its environment; the steps of a job still share the runner and its workspace, so this narrows the exposure rather than isolating the secrets. Neither client follows a redirect (`redirect: 'manual'`; a 3xx is an `AdminError` or exit 1 at once, never retried), because fetch drops only `Authorization` on a cross-origin redirect and would hand `X-Caddie-Admin` and `CF-Access-Client-Secret` to the other origin.
- **Deploy the Worker right after the merge.** The clients on `main` sign from this change on, and a Worker without it reads only the bearer, so the weekly ingest and the moderation script get 404 from an old Worker; the smoke keeps the bearer by default until its own change, so it runs with `SMOKE_ADMIN_AUTH=signed` against the new Worker meanwhile. No Durable Object migration tag is needed: the new table and index are created by the schema code at the next start of each object.
- **Rolling back means reverting the clients too.** A Worker rolled back to before this change reads only the bearer again, so the clients must go back with it: revert the merge on `main` for the weekly ingest, run the ingest, migration and moderation scripts from the commit before it, and run the smoke with `SMOKE_ADMIN_AUTH=bearer`. Otherwise every ingest and moderation call gets a 404 that looks like a wrong token. The version 3 table and its index are harmless to the older code. After a rollback the conference objects stay at `schema_version` 3, so the next schema change must use version 4: a later change that bumps to 3 again would be skipped silently, because `migrate()` (`worker/src/schema.js`) does nothing when the stored version is at least `SCHEMA_VERSION`.
- **The spec author's answers (review round 1).** The clock is `Math.floor(Date.now() / 1000)`, as in the fixture; the spec's step 7 now says so. The Worker may check for a usable key before the header's shape (its steps 2 and 3), although the fixture's reference verifier lists `malformed` first; any applying reason is acceptable. The object checks the forwarded timestamp within 305 seconds of its own clock. `admin_nonces` gets the index on `ts_ms`. The W4 runbook wording is confirmed: a stale secret empties the failed-auth bucket, while a clock far off shows up as `401 admin_skew`, because the clock is checked only after a valid signature.
- **Not in this change.** The wipe route and its nonce (W7.4), `GET /admin/stats` without `event` on the DirectoryDO (W7.5), `setup-secrets.mjs --rotate-admin-token` (W3; the manual rotation with `ADMIN_TOKEN_NEXT` is in `docs/FREE_HOSTING.md`), the `/admin/test/*` gate (W5) and the moderation wrapper that points at the CLI (W8) follow in the next pull request.

## Operator routes on the Worker (W6, W7, W8 skipped_retired) (2026-11-11)

- **New admin routes, all signed and nonce-checked like the others.** `GET /admin/people/search`, `GET /admin/people/view` and `POST /admin/people/block` run in the ConferenceDO (they are in `CONFERENCE_ADMIN_PATHS`), `POST /admin/moderation` gains `action: "hide"`, `GET /admin/stats` without `event` is served by the DirectoryDO, and `DELETE /admin/conference` is served by the Worker in three steps (below). The shapes are in `worker/README.md` (Operator routes).
- **No internal id and no position in any answer.** Search rows carry `ref`, `display_name`, the three flags, `sample` and `visible_until`; the view adds `updated_at`, presence as on or off, and counts, plus profile text (`fields=text`) and `linkedin_url` (`fields=contact`) only on request. A test walks every key of every `fields` mode against a list of forbidden keys and looks for the profile ids, the secret hashes, the push endpoint and keys, the zone, the position, the Bluetooth values and the meet note of its fixtures in the answer text.
- **Search text travels as `q64` and matches literally.** The signer allows no free text in a query, so the text is base64url of 1 to 200 bytes of UTF-8, decoded strictly: a bad character, a length of 4n + 1, more than 200 bytes, invalid UTF-8 or a NUL is 400, and so is an empty text, so the route never lists a whole conference by accident. It is matched with `instr(lower(display_name), lower(?)) > 0`, which takes every character literally. The first version used `LIKE ? ESCAPE '\'`, under which a NUL in the text ended the pattern early (`q64=AA` matched everyone) and a NUL in a stored name hid the rest of it from a search; `instr` has neither problem, and new names cannot hold a NUL anyway (below). `lower()` folds ASCII letters only, which is listed as a known gap. Unknown or repeated query parameters are 400 on the new GET routes, and `limit` and `include_hidden` are checked with `ref` too. `matched` (a window count before the limit) lets the CLI say how many more there were.
- **People text is stored without control characters.** Every write of a display name, about, interests, expertise, a contact note, a spot line, a meet note or a how-to-spot-me line drops the C0 controls except tab and newline, DEL and the C1 controls (U+0080 to U+009F), after turning CRLF and a lone CR into a newline (`stripControls` in `worker/src/lib/text.js`). It is done where people text enters (`validateProfile` in `people/routes.js`, `line()` in `connect/common.js`, and the text columns of `insertPerson`, `savePerson` and `setPresence` in `store.js`), not in the `text()` helper the talk routes share. Stripping rather than refusing was agreed with the CLI owner: a pasted line with a stray control still saves. Bidirectional marks stay, because right-to-left text needs them. The line filter now sees the text after stripping, so a control character can no longer split a listed word and slip past it; that holds for control characters only, and any other character the filter turns into a space (punctuation, a zero-width space, a line separator) still splits a word, as before. Rows written before this change may still hold controls, so the operator's routes (search, view, and the moderation queue) also strip every stored string they answer with, values and keys such as report reasons alike; the Worker's answers therefore carry no control character. That is the Worker's layer only: the CLI escapes what it prints, which is what protects a terminal from anything else (the first version of this note claimed the terminal could never get an escape sequence, which overstated the Worker's part).
- **The meet counts map the stored states onto the spec's five.** `requested`; `accepted` is the stored `active` (accepting moves a meet straight to active); `declined`; `ended` is `found` (how a meet that worked ends), `cancelled`, `expired`, the `accepted` state older versions stored, and an open meet past its `expires_at_ms`, which its participants already see as expired; `other` is any other state. Report counts cover the profile, the spot line and the meets the person took part in (`target_profile_id`), so a meet report about them counts against them. Blocks and push subscriptions that have run out are not counted.
- **One operator report hides on its own.** The hide rule moved into the store (`HIDE_AT`, `reportHides`, `reportFlags` in `worker/src/store.js`) so the people routes and the admin routes share it: hidden once two distinct people reported a target, or as soon as a report with `reporter_id` `operator` exists. `insertPerson` also applies the operator's reports, whatever the document says, so a migration re-run, a fixture or a re-creation of the same `profile_id` stays hidden; the count rule stays where it was (a profile being created through the people API). The block and the moderation hide of a profile file the same report (`profile:<ref>:operator`), so either one undoes the other's, and an unhide, which deletes every report of the target, lifts it too. A device cannot report under the id `operator`, because profile ids are 22 characters. A block does not stop a new device.
- **Unblock answers what it did, and deletes only the operator's report (the spec owner's shapes).** A person with an operator report: the report goes, `hidden` becomes what the remaining reports say, `{ok, hidden, found: true, removed: true}`. A deleted profile whose operator report is left: the report goes, `{ok, hidden: null, found: false, removed: true}`, so a profile made again from that device is not hidden by it. A person without one: `404 no_operator_block`, and nothing changes, so a profile hidden some other way (a migrated flag, a fixture) is not unhidden. Neither: `404 not_found`. A retried unblock therefore answers 404 the second time, the third idempotency exception beside `delete` and `unhide`. The first version told the operator to lift the block of a deleted profile with `unhide profile:<ref>`, which also deleted the genuine reports of other people; that advice is gone.
- **Unhide of a gone target (W6).** `unhideTarget` deletes the reports of a target it did not find, as before, but the route now answers `200 {ok, found: false, removed}` when there were some and 404 only when there were neither a target nor reports; a found target answers `{ok, found: true, removed}`. A retried unhide of a gone target therefore answers 404 the second time; `adminClient`'s comment and the README say so.
- **The removal writes the tombstone first.** `DELETE /admin/conference` runs: (1) the DirectoryDO records the nonce (a replay is `401 admin_replay` before any write) and writes or refreshes the tombstone in one transaction, keeping the conference row, and answers the earlier tombstone's time; (2) the object records the nonce in its own table and wipes itself; (3) the DirectoryDO deletes the row, in one transaction, only while step 1's tombstone still exists, and never writes a tombstone itself. The first version wiped first and wrote the tombstone last, so a directory step that failed (for example on `503 daily_limit`, which `adminClient` does not retry) left no tombstone and the next weekly ingest revived the conference. Now a failure of step 2 or 3 answers that step's status with `{error: "removal_incomplete", step, retired: true, wiped, cause?, deleted?}` and its `Retry-After`; `cause` comes before the counts, so `adminClient`, which looks for `daily_limit` in the first 200 characters of a 503, stops instead of retrying. The tombstone holds, and the same removal sent again finishes the work idempotently. When a removal and an unretire of the same conference overlap, the later of the two by the directory's order sequence wins everywhere (review round 3, below): the conference ends either removed or live, and a removal that loses answers `409 {error: "removal_superseded", step: "wipe" | "directory", retired, wiped, deleted?}`. Before round 2, step 3 deleted the row anyway and wrote a tombstone back, which left a live object (cleared by the unretire) that no directory row named and no cron visited; round 2's check of the tombstone at step 3 still let an unretire committed before the removal reach the object after the wipe, with the same result. The runbook says never to unretire during a removal, and to check the conference's state and run the intended operation again after an overlap, because an automatic retry of either is a new, later request. A test makes each step fail once. A retried removal whose first answer was lost reports all-zero counts, so the answer carries `already_retired_at` (ISO, or null for a first removal).
- **The wipe keeps the schema; `meta` keeps `schema_version` and gains `retired_at`.** It deletes every row of every table of `schema.js` and the meter's `usage_days`, through a fixed list in `conference.js`, never the FTS5 shadow tables and never `storage.deleteAll()`, so the object can take the conference again. `meta` keeps its `schema_version` row, which describes the database and not the conference; without it the next start would re-run every migration step on whatever a re-add had written meanwhile. The spec asked for every row of `meta`; this is a deviation, and the test checks that `meta` holds exactly `schema_version`, `retired_at` and the removal's order number `wipe_seq` afterwards (`unretire_seq` is kept too when the object took an unretire). The test also fills every table first and fails if one is left empty, so a new table must be added to the fixture and then to the wipe list. The wipe also clears the object's rate-limit buckets, whose keys hold client addresses, and its query-vector cache. The usage meter stays: its in-memory totals are refreshed by its next write, which also creates a new `usage_days` row for the requests that still reach the object.
- **The `retired_at` marker stops a late fan-out and every admin write.** A `PUT /admin/conferences` that read the directory before a removal could send its conference document to the object after the wipe; the object then became searchable again for as long as the Worker's directory cache named it (up to 5 minutes), and the cron, which visits only listed conferences, never purged anything written there. The first version accepted this; it is fixed. While `retired_at` is set, `PUT /internal/conference` answers `409 conference_retired` unless the directory's fan-out entry carries `unretired` (the unretire's order number since round 3, `true` before), which drops the marker when the number is above the object's last wipe's. The DirectoryDO sets that flag on every entry of a slug the request unretires, whether or not a tombstone was left to delete: in the first round it was set only when a tombstone was deleted, so an unretire whose fan-out failed once left the object refusing for good, because the repeat found no tombstone and sent no flag, and the weekly ingest then failed on that conference every week. The Worker also answers `502 {cause, error: "unretire_incomplete", unretire_failed, upserted, searchable, synced, skipped_retired}` when the document of an unretired slug did not reach its object or was refused, so `adminClient` repeats the request and the repeat repairs it; when any fan-out of the request hit the daily limit, the answer is `503` with `cause: "daily_limit"` first and `Retry-After`, so `adminClient` stops until the reset instead of retrying in vain. The flagged entry is sent whatever the document's status, and the row's `has_object` is set, so even an unretire with an unavailable document clears the marker and a later searchable upsert reaches the object. Separately, an object without a conference document, or with the marker, refuses every admin write (any method but GET and HEAD) with `400 conference is not available`, so a migration or a fixture that lands between the wipe and the row delete cannot leave people no cron would purge; admin reads still answer. An object that was never given a document refuses admin writes too, for the same reason. This changes two cases that used to work: a conference pushed for the first time whose fan-out failed (its object never got the document) now gets `400 conference is not available` on its talk push, where before the talks were stored in an object no route served; and a migration that reaches such an object gets the same 400. `push-ingest.mjs` counts that conference as failed, as for any other refused push, and the next run, whose fan-out reaches the object, pushes it; `migrate-from-backup.mjs` names the conference, skips the rest of it and carries on with the others, where before the first such answer stopped the whole run.
- **A request in flight during a wipe writes nothing afterwards.** A request that was waiting on an await (an embedding call, a secret hash) when the wipe ran still holds the old store and its own `ctx`. The wipe closes that store, whose every later statement throws `400 conference is not available` and whose caches are dropped, and every `ctx` remembers the object's wipe count, so `ctx.sql` throws the same once it has moved.
- **The tombstone and `unretire`.** The DirectoryDO's `retired (slug, at_ms)` table is created with the other directory tables on every start, so it needs no version and no migration tag. `PUT /admin/conferences` skips a retired slug unless a document of that slug in the request carries `"unretire": true` (collected in a first pass, so a slug sent twice, plain then with the flag, is unretired and never reported as skipped), strips the key from every document before storing it, and answers `skipped_retired` (always present, empty when nothing was skipped). The route prefixes are computed first, then every write runs in one transaction against the tombstones as they are at that moment, and a tombstone is deleted only after its conference row is written, in the same transaction, so a removal that ran meanwhile is honoured and a failed upsert leaves the tombstone. A non-boolean `unretire` refuses the whole request with 400 before anything is written, like `allow_shrink` and `allow_empty`. A removed slug unknown to the directory still gets a tombstone and its object wiped.
- **The ingest scripts treat a skipped slug as neither stored nor failed.** `push-ingest.mjs` logs each `skipped_retired` slug by name with the command that brings it back, leaves it out of `upserted` in its `--report` and adds a `skipped_retired` list there, and does not push its talks, which the Worker would refuse (`400 conference is not available`) and which would turn every weekly run red for a conference that was removed on purpose; the planning is the pure `planPush`, which a test runs with `pushEvent`. `migrate-from-backup.mjs` likewise sends no talks, topics, facets, people or reports for a skipped slug and names it. `push-ingest.mjs` strips `unretire` from every conference document it sends (`conferenceForWorker`, applied inside `upsertConferences`, the one function that sends them), so no ingest run, in CI or by hand, can unretire a conference whatever a committed `conference.json` holds; only the operator's own request does. `migrate-from-backup.mjs` strips it from the backup's conference documents in `plan()` for the same reason, ends with a summary naming every conference it skipped, and exits 3 when a conference was skipped as not available (its data was not all sent), 0 when only removed conferences were skipped. Only well-formed slugs from the answer are logged.
- **`GET /admin/stats` without `event` reports what the cron stored.** The day's totals per conference and the conferences whose object still held personal data, from the DirectoryDO's `meta.usage` and `conferences.holds`; a conference's totals of another UTC day than the cron's are left out rather than shown under the wrong day, and before the first cron run `day` is null. Any query parameter is 400, so a misspelt `event` never answers the totals instead. Nothing is recomputed, so the reading costs the nonce and a few rows.
- **Schema versions.** No ConferenceDO table changed (`retired_at`, `wipe_seq` and `unretire_seq` are `meta` rows), so its `SCHEMA_VERSION` stays 3 and no Durable Object migration tag is needed; the next ConferenceDO table change uses version 4. The DirectoryDO's order rows are `meta` rows too.

The other fixes: the meet buckets for `found` and legacy `accepted`, the planning helper and its test in `push-ingest.mjs`, the migration's skip, the stats query check, the first pass for `unretire`, the checks of `limit` and `include_hidden` with `ref`, `already_retired_at`, and the bucket clearing.
- **Review round 2.** The re-review approved with fixes. One blocked: an unretire whose fan-out failed could not be repaired (now the flag goes with every unretire, and the Worker answers 502). The others: control characters stripped from the operator routes' answers too; step 3 deletes the row only under its tombstone (`removal_superseded`); the migration skips a conference whose object has no document instead of stopping; `push-ingest.mjs` never sends `unretire`; `cause` before `deleted` in `removal_incomplete`; and the scope of the word-filter claim.
- **Review round 3: the later of a removal and an unretire wins, by the directory's order sequence.** Round 2 sent `unretired: true` on every unretire with no ordering, and the object took it unconditionally. So an unretire that committed in the directory, then a removal's tombstone and wipe, then the unretire's fan-out, then the removal's step 3 (which found the tombstone and deleted the row) ended with a tombstone, no row and a live object, both requests answering 200: a stale Worker isolate (directory cache up to 5 minutes) still forwarded public profile writes to it, no cron visited it, and its owners could not reach it to delete. The DirectoryDO now keeps a counter in `meta` (`order_seq`, which a live directory without it starts at 0) that only grows. Step 1 of a removal takes the next number in its tombstone transaction; the Worker passes it in the body of `POST /internal/wipe` (`{seq}`, never from the client) and in the query of step 3. Every slug an upsert unretires takes the next number in the upsert transaction, recorded as that slug's latest unretire (`meta` `unretired_seq:<slug>`), and its fan-out entries carry it as `unretired: <number>`. The object keeps the highest wipe number and the highest unretire number it took (`meta` `wipe_seq` and `unretire_seq`, kept through the wipe): it takes an unretire only when its number is above the last wipe's (otherwise `409 unretire_superseded`, which the Worker counts as a failed fan-out, so `PUT /admin/conferences` answers 502 `unretire_incomplete` and the client's retry, with a new number, wins), and it refuses a wipe whose number is below the last unretire it took (`409 removal_superseded`, nothing deleted; the Worker answers `409 {error: "removal_superseded", step: "wipe", retired: <tombstone as stored>, wiped: false}` and does not run step 3). Step 3 deletes the row only while a tombstone exists and no unretire of the slug took a higher number than the removal's, so a removal that finds another removal's tombstone after an unretire yields to that later removal instead of deleting the row under the unretire's live object; its 409 now carries `retired` as stored (true in that case). Objects and a directory without these rows read them as 0, so nothing changes for them at deploy, and no `SCHEMA_VERSION` bump is needed. During the deploy, a request between an old Worker and a new object, or the other way round, can be refused (the new objects answer 400 or 415 to `unretired: true`, a wipe without a body and a step 3 without `seq`; an old object answers 409 to a numbered flag on a marked object) and is then answered as `unretire_incomplete` or `removal_incomplete`; sending it again once the deploy is done finishes it. A test runs every interleaving of the unretire's two steps (directory commit, fan-out) with the removal's three, from a live and from a removed conference, with no failure and with the fan-out, the wipe or step 3 failing once, followed by the clients' retries; it checks after every step that a live object never coexists with a missing row, and that each run ends removed or live as the later operation says. Further tests cover two removals around an unretire, the daily limit, and the number checks one by one; each of the checks, removed by hand, fails them. The same round: a fan-out that hit the daily limit makes `PUT /admin/conferences` answer 503 with `cause: "daily_limit"` first (it used to be a 502 without a cause, which `adminClient` retried), every `unretire_incomplete` body starts with its `cause` when the failing fan-out gave one, and `adminClient`'s error message names the cause, the slugs of `unretire_failed` and that the rest of the batch was stored; the migration strips `unretire` and reports its skips with exit code 3; and the tests now cover the cleaning of meet names, of a hidden spot line's name and the adding up of reasons equal after cleaning, push-ingest's real send path, and a 400 that must stop the migration.
- **A retried removal or unretire advances the order counters, so the idempotency rule leaves them out (spec deviation).** Spec W7 asks that a route applied twice leave the same stored state. A retried removal or unretire is a new, later request in the order sequence: it advances the DirectoryDO's `order_seq` and, for an unretire, `unretired_seq:<slug>`, and the object's `wipe_seq` or `unretire_seq`. The "same stored state" rule therefore covers every other row and leaves those counters out; the tests that apply these routes twice compare the state without them.
