# Conference Caddie build contract

This file pins the decisions that every task builds against. A task may add to it in its own output, but must not change a field name or its meaning. The brief (`SPEC.md`) states the goals and the four non-negotiable rules. Phase 2 extended the MVP to any Linux Foundation conference whose schedule is on Sessionize, and the product direction of 2026-11-09 made it people first: "Who here should I talk to?" comes before "Which talks would I like?", and the app is not a scheduling tool. Where an older document disagrees with this contract, this contract wins.

## Facts

- Elasticsearch 9.5.6 runs on Elastic Cloud Hosted (GCP us-west1) at `https://fc875c88f9f44f159f1a359ee724d82b.us-west1.gcp.cloud.es.io:443`. The URL is not a secret.
- The admin credential is in env var `ELASTISEARCH_API_KEY`, already encoded, sent as `Authorization: ApiKey $ELASTISEARCH_API_KEY`. It is never deployed.
- An API key cannot create a derived API key that has privileges. Scoped keys are minted by creating a role and a native user, authenticating as that user, and minting the API key as that user. The password is generated in-process and never printed or stored.
- The only model the app uses is the embedding model behind `semantic_text`: the inference endpoint `caddie-e5-small`, the multilingual E5 small model deployed on the cluster's own ML node (it replaced the trial-limited cluster default, `.jina-embeddings-v5-text-small`, on 2026-11-09). **Never call a chat, completion or rerank endpoint.** Unchanged documents are still never re-embedded.
- Schedule data comes from the Linux Foundation events list and each event's Sessionize feed, fetched only by the ingestion CLI on an operator's machine. Raw responses are committed under `data/raw/`. The deployed app never calls a feed.
- Google Cloud project id is `project-9205d6eb-366e-4844-b77` and the region is `us-west1`.

## Indices

Every index is versioned behind an alias. The server reads alias names from env: `ES_INDEX` (default `caddie-talks`), `ES_CONFERENCES_INDEX` (default `caddie-conferences`), `ES_TOPICS_INDEX` (default `caddie-topics`), `ES_PEOPLE_INDEX` (default `caddie-people`), `ES_PEOPLE_BLOCKS_INDEX` (default `caddie-people-blocks`), `ES_PEOPLE_MEETS_INDEX` (default `caddie-people-meets`), `ES_PEOPLE_REPORTS_INDEX` (default `caddie-people-reports`), `ES_PEOPLE_PUSH_INDEX` (default `caddie-people-push`) and `ES_PEOPLE_NUDGES_INDEX` (default `caddie-people-nudges`). Every people-side index is named `caddie-people-*`, so the people key covers it. Development indices are named `caddie-dev-<task>*` and are deleted when the task ends. The topics command uses a temporary work index `caddie-topicwork-{slug}` and deletes it in all cases.

### Conferences: `caddie-conferences-v1` behind `caddie-conferences`

`_id` is the slug. Mapping (`dynamic: false`): `slug`, `name`, `status`, `status_reason`, `source`, `time_zone`, `parent_slug` as keyword; `start_date`, `end_date` as `strict_date`; `ingested_at`, `raw_fetched_at` as date; `time_zone_windows`, `sessionize_api_code`, `sessionize_public_slug`, `lf_url`, `official_schedule_url` as keyword with `index: false`; `sessionize_site_published` boolean and `lf_event_id` long, both `index: false`; `location`, `category_mapping` and `counts` as objects with `enabled: false`.

| Field | Rule |
|---|---|
| `slug` | `slugify(name)` plus `-{year}` from `start_date` unless already present; regex `^[a-z0-9][a-z0-9-]{0,119}$`. |
| `name` | LF `name`, trimmed. |
| `status` | `searchable` only when every talk document of the event was indexed in this run (or skipped as unchanged) and a time zone was resolved; else `unavailable`. |
| `status_reason` | `no_schedule_url`, `no_sched_config`, `shares_feed`, `time_zone_missing`, `time_zone_unmapped`, `fetch_failed`, `embedding_limit` or `partial_index`; null when searchable. |
| `source` | `sessionize`, the only value. It is kept so other sources can be added later. |
| `start_date`, `end_date` | `YYYY-MM-DD` from the LF list. |
| `time_zone` | From `data/windows-zones.json[api-data.timezone]`, else `data/conference-overrides.json[slug].time_zone`, else null. Must pass `Intl`. |
| `location` | `{ city, region, country, virtual }` from the LF list. |
| `sessionize_api_code`, `sessionize_public_slug` | From the page's `data-sched-config` only. Never guessed. |
| `sessionize_site_published` | True when `api-data.timezone` is a non-empty string. |
| `official_schedule_url` | LF `cta_schedule_url`, else the LF `url`. |
| `parent_slug` | Set on an entry whose apiCode duplicates an earlier entry's. |
| `category_mapping` | `{ track_group, level_group, tag_groups, hidden_groups, slides_question }`, names copied from the feed. |
| `counts` | `{ sessions, talk, ambient, break, housekeeping, with_slides, sponsor }`. |

### Talks: `caddie-talks-v3` behind `caddie-talks`

`_id` is `talk_id` = `{conference}:{session_id}`. One document per feed session of every kind. Mapping (`dynamic: false`):

| Field | Mapping | Rule |
|---|---|---|
| `talk_id`, `conference`, `kind`, `room`, `track`, `level`, `tag_keys`, `day`, `topics` | keyword | |
| `session_id`, `slides_url`, `url`, `content_hash`, `text_hash` | keyword, `index: false` | `session_id` is never returned by the API. |
| `title`, `abstract` | text (english), `copy_to: semantic` | Trimmed, CRLF to LF, null description to `""`. |
| `semantic` | `semantic_text`, `inference_id: caddie-e5-small` | |
| `speakers` | text | Resolved names, in session order. |
| `speaker_taglines` | text (english) | |
| `tags` | object, `enabled: false` | `[{ group, value }]` for every item in every non-track, non-level, non-hidden group. `tag_keys` is `group + "\u001f" + value`. |
| `speaker_profiles` | object, `enabled: false` | `[{ name, tagline, links: [{ title, url }] }]` from the feed's speakers, http(s) links only. Public feed data, used to list a circle's speakers. |
| `sponsor`, `has_slides` | boolean | |
| `start`, `end` | date | ISO 8601 with the event zone's offset at that instant, through `Intl`. |
| `start_minutes`, `end_minutes` | integer | Venue-local clock. |
| `ingested_at` | date, `index: false` | |

- `kind` is `housekeeping`, `break`, `talk` (at least one speaker) or `ambient`, first match wins; the rules are in `DATA_NOTES.md`.
- `track` is the first item of the group named by the config's `primaryFilterTitle` (else the first visible group), or `"Not specified"`. `level` is null when the conference has no group whose title contains "level".
- `url` is the session page on the public Sessionize site when it is published, else the conference's official schedule URL.
- `topics` holds the `topic_id`s found in the title. Only the topics command writes it, through a Bulk partial `update`.
- `text_hash` = `sha256(title + "\n" + abstract)`. `content_hash` = `sha256` of the canonical JSON of every built field except the hashes, `ingested_at` and `topics`.

### Topics: `caddie-topics-v1` behind `caddie-topics`

`_id` is `{conference}:{topic_id}`. Mapping (`dynamic: false`): `conference`, `topic_id`, `label_exact` keyword; `label`, `aliases` `search_as_you_type`; `talk_count`, `rank` integer.

- Built by `node scripts/topics.mjs --event <slug> [--talks-index name]` from that conference's `kind: talk` titles. Analysis in Elasticsearch: standard tokenizer, lowercase, stop (`_english_` plus `config/topic-stoplist.txt`), no stemming, unigrams and bigrams that never span a removed word, and no numbers or single characters.
- A terms aggregation counts talks per term. Terms in at least 3 talks are kept, at most 150, ranked by `talk_count` descending, then label. `topic_id` is the term with spaces replaced by `-`. The label is the most common original casing.
- `data/topics/{slug}.json` is `{ "rename": { id: label }, "merge": { alias_id: canonical_id }, "remove": [id] }`. A fix-up never adds a topic.
- The command replaces the conference's topic documents only when they differ, and updates `topics` on talks only where the value changed. The ingestion CLI runs it after every successful event.

### People: `caddie-people-v2` behind `caddie-people`

`_id` is `{event_id}:{profile_id}`. Mapping (`dynamic: false`):

| Field | Mapping |
|---|---|
| `event_id`, `profile_id`, `learn_topics`, `speak_topics`, `shared_talk_ids` | keyword |
| `display_name` | text with a `keyword` subfield |
| `about`, `interests`, `expertise` | text, each `copy_to` `about_semantic`, `interests_semantic` or `expertise_semantic` (`semantic_text`, `inference_id: caddie-e5-small`) |
| `open_to_meet`, `sample` | boolean |
| `visible_until`, `updated_at` | date |
| `linkedin_url`, `contact_note`, `secret_hash`, `text_hash` | keyword, `index: false` |
| `pending_about`, `pending_interests`, `pending_expertise` | text, `index: false`, no `copy_to`. The text of a profile save that could not be embedded (see `degraded` under `PUT /api/people/profile`); present only together with `text_pending: true` (unmapped) and `text_hash` null, and removed by the owner's next write that embeds it. Never searched, embedded or returned. |
| `ref` | keyword. The result reference (see below), stored on every write so a block or a meet request can name a person by it. |
| `presence_zone` | keyword. The zone the person said they are in; absent or null while they are not around. |
| `presence_spot` | text. Their optional "how to spot me where I am" line, 60 characters, filtered. |
| `presence_spot_pending` | boolean. True while the classifier holds the spot line: it is stored and returned to its author only. Cleared with presence. |
| `presence_since`, `presence_until` | date. Presence is live while `presence_until > now`. |
| `presence_location` | geo_point `{ lat, lon }`, rounded to 5 decimals. Set only while the person is around and chose to send their position with an accuracy of 200 m or better, and the fix was not an implausible jump from the previous one (see `PUT /api/presence`); otherwise null. Read by the server only for the owner's own jump check and, inside an active meet, to compute a distance and bearing between its two participants; never read for a search and never returned. |
| `presence_accuracy` | integer, metres, the reported accuracy of `presence_location`; null with it. Never returned. |
| `presence_cell` | geo_point `{ lat, lon }`, the centre of the grid cell `presence_location` falls in, written in the same partial update and null with it: latitude snapped to 0.001° (about 111 m), longitude to the step that spans the same distance at the snapped latitude, 6 decimals. The only position the ranking leg and the proximity bands read. Never returned. |
| `presence_located_at` | date, when `presence_location` was stored; null with it. Read only by the owner's own jump check. |
| `ble_token` | keyword. The Android companion's Bluetooth token (see Find people near me by Bluetooth): 16 random bytes, base64url; absent or null unless the owner turned that on. |
| `ble_token_until` | date. The token resolves while `ble_token_until > now`; at most 10 minutes, never past `presence_until`. |

- A document exists only while `open_to_meet` is true or `shared_talk_ids` is not empty; otherwise the server deletes it, together with the person's meets and the blocks they made. A delete that failed part-way leaves the document hidden in between until a retry or the hourly purge finishes it (see "Profile deletes: the pending state and blocks" below).
- `visible_until` is 23:59:59 on the conference's `end_date` in its `time_zone` (UTC-12 when the zone is unknown). Every people query filters on `event_id` and `visible_until > now`.
- Expired documents are deleted, not only hidden: the server runs a delete-by-query on `visible_until < now` (and on documents without `visible_until`) when it starts and once an hour, and `npm run people:purge` runs the same delete from the CLI. The same pass clears the presence fields of `PRESENCE_OFF` (the position, its cell and its time, the held flag and the Bluetooth token among them) where `presence_until < now` (a Bulk partial `update`), deletes meets whose `expires_at < now`, and deletes push subscriptions, nudge records and blocks whose `expires_at < now`; before all of that it finishes pending profile deletes.
- `secret_hash` is `sha256(secret)` in hex. `text_hash` is `sha256(JSON [about, interests, expertise])`. Writes whose text is unchanged use a Bulk partial `update` without the text fields, so nothing is re-embedded. Presence writes are Bulk partial `update`s of the presence fields only (zone, spot, spot_pending, since, until, location, accuracy, cell, located_at, and the Bluetooth token when asked); the one exception is a presence write by an owner whose last profile save was degraded, which re-indexes the document once to embed the pending text (see `PUT /api/people/profile`).
- `ble_token` and `ble_token_until` are cleared with presence (`DELETE /api/presence`, the hourly purge, visibility off) and carried through a reindex like the presence fields; they are read only from the owner's own document, never with another person's.
- `ref`, the presence fields, later `presence_location` and `presence_accuracy`, the two `ble_*` fields, then `presence_cell`, `presence_located_at` and the `pending_*` text fields were added to an existing index with an additive `PUT _mapping`; `npm run people:setup` does that idempotently, and `node scripts/backfill-ref.mjs` writes `ref` on documents from before the field existed (run it with the server's `REF_SALT`).

### Blocks: `caddie-people-blocks-v1` behind `caddie-people-blocks`

`_id` is `{event_id}:{blocker_id}:{blocked_id}`, one document per direction. Mapping (`dynamic: false`): `event_id`, `blocker_id`, `blocked_id`, `blocked_ref` keyword; `created_at`, `expires_at` (the conference's `visible_until`) date. `blocked_ref` is the blocked person's `ref`, so a block can be lifted after they deleted their profile. Every people query (matches, circle members, the meet inbox) leaves out anyone the requester has blocked or who has blocked the requester. A block is deleted with the blocker's profile (never the blocked person's), by unblock, and by the purge once `expires_at` has passed.

### Meets: `caddie-people-meets-v1` behind `caddie-people-meets`

`_id` is `meet_id`, 16 random bytes base64url. Mapping (`dynamic: false`):

| Field | Mapping |
|---|---|
| `event_id`, `meet_id`, `participants` (the two `profile_id`s), `requester_id`, `topic_id`, `state` | keyword |
| `note`, `rendezvous` | keyword, `index: false` |
| `spot_me` | object, `enabled: false`: `{ profile_id: line }` for each participant who set one |
| `note_pending` | boolean. True while the classifier holds the note: everyone but the requester reads it as `""`. |
| `spot_me_pending` | object, `enabled: false`: `{ profile_id: true }` for each participant whose spot-me line the classifier holds; the other participant then gets `spot_me: null`. |
| `same_zone` | boolean. True when both were around in the same zone when the ask was made; recomputed on accept. |
| `created_at`, `active_since`, `expires_at`, `ended_at` | date |

- `state` is `requested`, `active`, `found`, `cancelled`, `declined` or `expired`. `requested` and `active` are the open states. **Asks are now-only**: there is no accepted-for-later state. `accepted` is a legacy value from before that rule; it is never written, and a document still carrying it is read as `expired`.
- `expires_at` is `created_at + 15 min` (never later than `visible_until`) while the meet is requested, and `active_since + 20 min` once active. `ended_at` is set when the meet leaves the open states.
- A meet becomes `active` at the moment it is accepted, which needs both participants around. It becomes `expired` when `expires_at` passes or, while active, when either presence ends; the server applies these transitions when the meet is read or acted on. When a meet ends, `note`, `rendezvous` and `spot_me` are cleared, so only participants, topic, state and times remain until the purge deletes the document.
- Meets are deleted with either participant's profile.

### Push subscriptions: `caddie-people-push-v1` behind `caddie-people-push`

`_id` is `sha256(endpoint)` in hex, so one browser subscription is one document whatever the profile, and it can be removed by its endpoint alone. Mapping (`dynamic: false`): `event_id`, `profile_id` keyword; `endpoint`, `keys_p256dh`, `keys_auth` keyword with `index: false` (stored, never searchable, never returned); `created_at`, `expires_at` date. `expires_at` is the conference's `visible_until`. Created by `npm run push:setup` (`scripts/es-setup-push.mjs`, idempotent). Deleted with the profile (`deleteConnections`), by the purge (`expires_at < now`), by `DELETE /api/push/subscription`, and when the push service answers 404 or 410.

The same index holds the native push registrations (`PUT /api/push/native`): `_id` is `sha256("{event}:{profile_id}:{platform}")` in hex (one per device, platform and conference, so a rotated token replaces the old one), and the document has `event_id`, `profile_id`, `platform` (`apns` or `fcm`), `token` (an APNs token lowercase), `environment` (`production` or `sandbox`, APNs only), `created_at` and `expires_at`. The mapping does not name `platform`, `token` or `environment`, so with `dynamic: false` they are kept in `_source` only: stored, never searchable, never returned. No mapping change was needed. Registrations are found and deleted by the mapped fields exactly like subscriptions: with the profile, by the purge, and when APNs or FCM reports the token gone; `DELETE /api/push/native` reads the requester's document by its id and deletes it with `if_seq_no` only when it holds the given token. The nudge reads a receiver's subscriptions and registrations with one search per receiver, at most 10 of them, newest first (`created_at`), and logs one line when a receiver has more.

### Nudges sent: `caddie-people-nudges-v1` behind `caddie-people-nudges`

`_id` is `{event_id}:{day}:{min_profile_id}:{max_profile_id}` where `day` is `YYYY-MM-DD` in the conference's time zone, written with `op_type: create`, so the write itself is the once-per-pair-per-day dedupe. Mapping (`dynamic: false`): `event_id`, `day`, `profile_ids` (the pair), `receivers` (the subset actually pushed) keyword; `created_at`, `expires_at` (the conference's `visible_until`) date. A `_count` on `receivers` over the last hour is the per-receiver rate limit. Deleted with either profile and by the purge.

### Profile deletes: the pending state and blocks

- **The pending state.** A profile delete (`DELETE /api/people/profile`, or `PUT` with both choices off) first hides the document with one Bulk partial `update` (`open_to_meet: false`, `shared_talk_ids: []`, every `PRESENCE_OFF` field null (presence, position, cell and Bluetooth token); `retry_on_conflict: 3`, `refresh=wait_for`, no upsert), then deletes meets, push subscriptions and nudge records (the three concurrently), then the blocks the person made, and the document last. A failure answers 502 and leaves the document in that hidden state, still holding `display_name`, `about`, `expertise`, the contact fields and `secret_hash` so a retry can authenticate. No other write produces that state, because a profile write with both choices off deletes the document, so the state itself marks a pending delete: `open_to_meet: false` and no `shared_talk_ids` value (`PENDING_DELETE_QUERY` and `isPendingDelete` in `server/people-shared.mjs`, a module without side effects that the server and the purge and export scripts share with `PRESENCE_OFF` and `visibleUntil`). It needs no new field.
- **While pending.** No people query finds the document. Every route but the profile write and the delete answers as if there were no profile (`authenticated()` returns null, so 403 `profile_required` and the like); meets and the blocks list treat the person as gone (`peopleByIds` leaves them out: the inbox skips their meets, `display_name` is null); `npm run people:export` leaves the document out. The owner can still make it visible again with a profile write, which keeps every block they made.
- **Finished by the purge.** The hourly purge in the server and `npm run people:purge` look for pending documents, sorted by `updated_at` and `profile_id` and paged with `search_after` (pages of 100 and at most 50 pages a run in the server, pages of 1000 in the CLI). For each one: a realtime `GET` of the document, and nothing is touched unless it is still a pending delete with the `_seq_no` and `_primary_term` the search returned, so a profile its owner made visible again keeps its meets, push subscriptions, nudge records and blocks; then its meets, push subscriptions and nudge records; then the document, with `if_seq_no`/`if_primary_term` from that read; then a second realtime read, and the blocks the person made only when it finds no document. A guarded delete answers 409 both when the document changed in the few milliseconds since the read (it is kept, blocks included; still pending, it is found again by the next run) and when it is gone (the owner's own retry deleted it, and its blocks are deleted). A profile re-created from the same device right after the delete keeps every block; between the second read and the blocks delete a re-creation still has a window of a few milliseconds. A failure before the document delete leaves it for the next run; one after it leaves blocks that run out with the conference.
- **Blocks belong to their blocker.** A profile delete removes only the blocks the person made. Blocks others made of them stay until the blocker lifts them, deletes their own profile, or the conference ends, so deleting and re-creating a profile from the same device (the same `profile_id`, the same `ref`) never lifts a block. `expires_at` is the latest of the conference's `visible_until` and the `visible_until` of the two profiles when the block is written, and the purge deletes the block after it. A later end date set after that reaches the block only when it is written again (blocking the same person again rewrites it); until then the block runs out at the end it was written with. `npm run people:setup` maps `expires_at` on an existing blocks index, re-indexes the blocks in place so the field is indexed where they already carry it, and gives every block still without it the end of its conference (`visible_until` from `end_date` and `time_zone`); blocks of a conference with no document or no `end_date` are left without and never purged. Until the setup has run, the purge's range query on the unmapped field matches nothing, so no block is deleted early.
- **Own-document writes are guarded.** `PUT /api/presence` and `POST /api/presence/ble/rotate` write with `if_seq_no`/`if_primary_term` from the profile read. On a conflict (or a document gone in between) the profile is read and checked again once, so a write that read the profile before a delete hid it answers 403 `profile_required` instead of putting presence or a Bluetooth token back; a second conflict answers 409 `{ error: "The profile changed at the same time; try again" }`, and a document gone by the second write answers 403 `profile_required`. The web app keeps sending positions after a 409 and shows "That did not go through. Try again." for a presence switch that got one. Meets also count a person as around only while they are visible conference-wide (`open_to_meet: true`) and their presence is live.

## Indexing rules

- Before bulk operations for an event, the CLI reads the stored `content_hash` and `text_hash` of that conference (at most 10000) and aborts the event above that.
- Per document: absent gives bulk `index`; equal `content_hash` is skipped; equal `text_hash` only gives a bulk `update` without `title` and `abstract`; otherwise bulk `index`. Stored ids missing from the feed are deleted. The Update API is never used, because it re-runs inference.
- Batches of 50, exponential backoff on 429, and a stop at the embedding limit with the conference marked `embedding_limit`.
- A second run over unchanged raw files makes zero model calls. The CLI prints a `bulk ops:` line to prove it.

## Ingestion CLI

`node scripts/ingest.mjs <mode> [options]`. Modes: `--list`, `--event <slug>` (repeatable), `--all-upcoming`. Options: `--index`, `--conferences-index`, `--dry-run`, `--no-fetch` (build from the committed raw files with no network call), `--skip-topics`.

- User-Agent `ConferenceCaddie-ingest/0.2 (+https://github.com/KurtLehnardt/conferenceCaddie)`, one fetch per URL per run, a 1000 ms pause after each call and a 30 s timeout.
- Co-located events whose feed duplicates another event's apiCode become `unavailable` with `shares_feed`.
- Exit 0 when every event ended searchable or unavailable for a non-error reason; 1 on a fatal error; 2 on an embedding stop, `partial_index` or `fetch_failed`.

## API

Every search, aggregation and lookup the server runs filters on one conference. Errors are `{"error": "..."}`: 400 for invalid input, 403 for a missing or wrong device secret or a cross-origin write, 413 for a body that is too large, 415 for a wrong content type, 429 with `Retry-After` over a rate limit, and 502 with a fixed message when Elasticsearch fails. Elasticsearch error bodies are never forwarded.

### `POST /api/search`

```json
{ "conference": "mcp-dev-summit-nairobi-2026",
  "query": "securing MCP servers",
  "filters": { "day": null, "start_after": null, "start_before": null,
               "track": [], "level": [], "tags": [], "has_slides": null,
               "hide_sponsor": false },
  "saved_talk_ids": [], "size": 10 }
```

- `conference` is required and must be a `searchable` conference; otherwise 400 and no search runs.
- `query` is at most 200 characters. An empty query is browse mode, sorted by `start`, then `talk_id`.
- `size` is an integer from 1 to 50 (default 10). `from` is optional, an integer from 0 to 1000 (default 0), and is accepted only in browse mode: with a non-empty query (after time phrases leave it) a `from` above 0 gets 400. It pages through the browse sort, so the app's Schedule view can list a day of more than 50 talks; `total` and `facets` are the same on every page.
- `filters.level` must be empty for a conference without a level group. `filters.tags` holds at most 50 `{ group, value }` pairs, each a known `tag_keys` value; pairs in one group are ORed and groups are ANDed. Known values come from one aggregation per conference, cached for 10 minutes.
- `filters.happening_now` is an optional boolean. When true, only talks in progress or starting within the next 60 minutes remain, judged by Elasticsearch against its own clock. Every response carries `happening_now: { available }`, true when the conference has a talk today in its own time zone; the app disables the chip when it is false (see `DECISIONS.md`, "Happening now").
- `filters.include_events` is an optional boolean, default false. When true, items of kind `ambient` (co-located events and showcases) are searched along with talks; breaks and housekeeping never are. Every result carries `kind`, `"talk"` or `"ambient"`, and the app draws an ambient result as an event card with no interest toggle, no talk circle and no related talks. Talks for you, people matches and circles read only kind `talk`, whatever this filter says.
- `saved_talk_ids` holds up to 100 ids of the request's conference (`{conference}:{session id}`). It is validated and **never filters anything**. It is kept so older clients do not break.
- `ignore_phrases` is optional: at most 20 strings of at most 30 characters, naming time phrases the person removed (see `DECISIONS.md`, "Time phrases in search"). Time phrases in `query` ("morning", "afternoon", "before lunch", "after lunch", "day N", weekday names) are removed from the text and applied as filters; the response then has `search_text` (the text the retrievers saw) and `time_phrases: [{ key, label, days, applied }]`, and a debug response's `ranking.filters` gains `time_phrases` (labels of the applied ones).
- `debug` is optional and must be a boolean. With `"debug": true` and a non-empty `query`, each result also has `ranking: { rank, keyword_rank, semantic_rank }` and the response has `ranking: { rank_window, semantic_k, filters }`, where `filters` echoes the validated filters every query applied (`kind`, `day`, `start_after`, `start_before`, `track`, `level`, `tags`, `has_slides`, `hide_sponsor`). `keyword_rank` and `semantic_rank` are the talk's positions in the rrf retriever's two child retrievers, each run on its own in the same `_msearch` with the filter rrf passes down to it; `null` means outside that child's window, which rrf also treats as not found. The main query does not change, and requests without `debug` carry none of these fields. Browse mode ignores `debug`.
- Body limit 4 KB.

Response: `{ total, conference, results, facets }`. Each result has `talk_id`, `conference`, `title`, `speakers`, `room`, `start`, `end`, `track`, `level`, `tags`, `topics: [{ topic_id, label }]`, `speaker_profiles`, `slides_url`, `url` and `evidence`. `facets` has `day`, `track`, `level` (only when the conference has a level group), `has_slides` and `tags: [{ group, values: [{ value, count }] }]` in `category_mapping.tag_groups` order. Each facet group, including each tag group, ignores its own selection. Ranking is an `rrf` retriever over a lexical `multi_match` and a `knn` query on `semantic`; `evidence` is never empty and contains only `<mark>` tags as markup.

### `GET /api/conferences`

Sorted by `start_date`, then `name`, with `Cache-Control: public, max-age=60`. Each entry has exactly `slug`, `name`, `start_date`, `end_date`, `time_zone`, `location: { city, region, country, virtual }`, `status` (`searchable` or `unavailable`), `official_schedule_url`, `source`, `has_level`, `track_group`, `tag_groups` and `talk_count`. API codes, LF ids, `status_reason` and the other counts are never returned. Methods other than GET or HEAD get 405.

### `GET /api/schedule?event={slug}` (offline mode)

The conference's `kind: talk` documents, read with the read-only key and sorted by `start`, then `talk_id`, for the app's offline keyword search. Returns `{ conference, talks }`; each talk has exactly `talk_id`, `conference`, `title`, `speakers`, `room`, `start`, `end`, `track`, `level`, `tags`, `topics: [{ topic_id, label }]`, `url`, `slides_url` and `abstract`, trimmed to about 400 characters. No people data and no other kinds. `Cache-Control: public, max-age=300`, gzip when the client accepts it, and 20 requests per minute per IP. The only accepted parameter is `event`; an unknown or unavailable slug gets 400, methods other than GET or HEAD get 405.

### `GET /api/related?event={slug}&talk_id={id}`

Up to five other talks of the same conference that are closest in meaning to one talk. Elasticsearch fetches the talk's title and abstract, then runs a knn query on the `semantic` field with that text as `model_text`, filtered to the conference and `kind: talk` and excluding the talk itself. No time or schedule filter applies. Returns `{ results: [{ talk_id, conference, title, speakers, room, start, end, track, level, tags, slides_url, url }] }` in the order Elasticsearch returned them. Only `event` and `talk_id` are accepted; an invalid value or an unknown parameter gets 400, an unknown talk 404, methods other than GET or HEAD 405, and more than 60 requests per minute per IP 429. `Cache-Control: private, max-age=300`.

### `GET /api/topics?event={slug}&q={prefix}&size={n}`

With an empty `q`, the conference's topics sorted by `rank` (default size 150). Otherwise a `bool_prefix` multi_match on `label`, `aliases` and their subfields (default size 10). `size` is at most 150 and `q` at most 60 characters. Returns `{ topics: [{ topic_id, label, talk_count }] }`.

### `POST /api/topics/suggest`

Body `{ event, talk_ids, text }`. Returns at most 12 topics: first those on the given talks (a terms aggregation on `topics`), then those whose label matches the text.

### `POST /api/recommendations` (talks for you)

Body `{ event, learn_topics, interests, interested_talk_ids, size }`. It stores and logs nothing from the body. `speak_topics` and `expertise` are still accepted, and are validated as before, so clients cached before 2026-11-09 keep working, but they are ignored: talks are recommended only from what the user wants to learn or the problems they face, never from what they can speak to. `interests` is the learn and problems free text.

- One `rrf` retriever over the conference's talks, filtered to `kind: talk`, `end > now` and not in `interested_talk_ids`. Two retrievers, each skipped when its input is empty: `learn_topics` against `topics` (weight 1) and `interests` against `semantic` (weight 1). There is no retriever for speak topics or expertise, and a talk that also matches a speak topic is not penalised. Weights use the rrf per-retriever `weight` of Elasticsearch 9.5.
- When both `learn_topics` and `interests` are empty the answer is `{ results: [], needs_profile: true }`, even if `speak_topics` or `expertise` are set.
- Results use the search result shape plus `why` and `circle_count`. `why` is `{ topics, learn_topics, passage }`. `learn_topics` holds the labels of the request's `learn_topics` that the talk has, so only topics sent in this request are named and a topic the user has removed never is. `topics` is kept equal to `learn_topics` for clients that predate the split. Speak topics are never returned in `why`. A client shows "You want to learn: ..." and the passage.

### People and circles

Every request may carry a same-origin `Origin` header or none. Writes and circle reads need the header `X-Caddie-Device: {profile_id}.{secret}`, where `profile_id` is 16 random bytes and `secret` 32 random bytes, both base64url, generated on the device. Bodies are JSON, at most 8 KB, and unknown keys get 400. The secret is compared with `crypto.timingSafeEqual` against `secret_hash`. The first write uses `op_type: create`, so an existing document can never be taken over.

- **`PUT /api/people/profile`**: body `{ event, profile: { display_name, about, interests, expertise, learn_topics, speak_topics, linkedin_url, contact_note }, open_to_meet, shared_talk_ids }`. Upserts with `refresh=wait_for`, or deletes the document when both choices are off. Returns `{ ok, open_to_meet, shared_talk_ids }`. Caps: `display_name` 1 to 60 characters, `about` 280, `interests` and `expertise` 500 each, `contact_note` 120; `linkedin_url` matches `^https://(www\.)?linkedin\.com/in/[A-Za-z0-9_-]{3,100}/?$` or is null; at most 30 known topic ids per set; at most 50 `kind: talk` ids of that conference in `shared_talk_ids`. Writes that turn visibility on are refused after the conference ends.
  - **`degraded: { semantic: true }`** is added when the text could not be embedded: the Bulk item answered 429, or its error (or a failed request's) was an inference failure (`isInferenceFailure` in `server/semantic.mjs`: `status_exception`, `inference_exception`, `model_deployment_*`, a type or reason naming inference or a trial limit). Semantic matching then pauses for 60 s and the document is written without `about`, `interests` and `expertise`, with `text_hash` null, `text_pending: true` and the text in the unindexed `pending_*` fields; while the pause lasts, saves with changed text go the same way. The owner's next profile save (a full reindex) or presence write (`PUT /api/presence`, once semantic matching is available) embeds the text and removes the pending fields. A 409 version conflict, a 400 mapping error and any other failure are answered as before (409, 502), never degraded. The web app sends the profile once more 70 s after a degraded answer.
- **`DELETE /api/people/profile?event={slug}`**: deletes at once with `refresh=wait_for`. Returns `{ ok }`.
- **`POST /api/people/matches`**: body `{ event, interested_talk_ids, query, when, from, size }`. `query` is free text of at most 300 characters (optional); `when` is `anyone` (default) or `around_now`; `from` is 0 to 1000 (default 0) and `size` 1 to 20 (default 20). The requester must have a live document with `open_to_meet: true`, else 403 `visibility_required`. One `rrf` retriever over: my `learn_topics` against their `speak_topics`; my `speak_topics` against their `learn_topics`; `query`, or my `interests` when there is none, against their `expertise_semantic`; with a `query`, the same text against their `about_semantic`; my `expertise` against their `interests_semantic`; with a `query`, a lexical `multi_match` on their `expertise` and `about`; and, when the requester is around with a stored position, a `distance_feature` on `presence_cell` (pivot 100 m, origin the requester's own `presence_cell`) filtered to `presence_until > now`, so nearby people rank higher. Like the bands, the leg sees cells only; a people search never reads another person's `presence_location`. Each semantic leg keeps only the profiles whose best chunk has at least a floor of cosine similarity to its text (the knn query's `similarity`), so a profile that has nothing to do with the text joins no semantic leg: 0.82 in a search with a `query`, which also has the keyword leg (`PEOPLE_SEMANTIC_MIN_SIMILARITY`), 0.84 without one and in circle members (`PEOPLE_SEMANTIC_PROFILE_MIN_SIMILARITY`), and 0.87 in the push nudge and Bluetooth sightings (`PEOPLE_SEMANTIC_PUSH_MIN_SIMILARITY`). `off`, `none` or `false` sends no floor; the server logs the floors in effect at start. Legs whose text is empty are skipped; the distance leg counts neither for nor against specificity. Filter: `event_id`, `open_to_meet: true`, `visible_until > now`, not the requester, not anyone blocked in either direction; `around_now` adds `presence_until > now`. `rank_window_size` grows with `from + size`, so there is no cap. Returns `{ results, from, size, has_more }`; `has_more` is true when the page was full, and a page can hold fewer than `size` results because of the specificity rule, so the client pages by `from + size`. Each result has `ref, display_name, about, sample, learn_topics, speak_topics, reasons, opener, contact: { linkedin_url, contact_note }, evidence, around, zone, proximity, broad`.
  - `evidence` is the passage of their `expertise` or `about` that matched, with `<mark>` tags as the only markup (HTML-escaped otherwise): a lexical fragment when the query's words matched, else the best semantic chunk of a field whose semantic leg found them (Elasticsearch returns a chunk for every result, so the others are dropped), else the first 160 characters of their `expertise` (or `about`); null for a profile with no text and for a broad match.
  - `around` is true while they have live presence. `zone` is their `presence_zone` only when both the requester and they are around; otherwise null. Their spot line is never in a result.
  - `proximity` is a band only, set only when both the requester and they are around, else null: `same_zone` (the same `presence_zone`), otherwise, when both have a stored `presence_cell`, `near` (the same cell) or `around` (cell centres under 300 m apart), otherwise `venue`. The band is computed from the two cells only, never from a precise location, so a requester who sends whatever positions they like learns at most which ~100 m cell someone is in: two people anywhere in the same cell get the same band from every requester position. No result, inbox entry or any other response carries a distance or a coordinate; the only numbers derived from positions are `other.distance_m` and `other.bearing_deg` on `GET /api/meet/{id}`.
  - **Specificity rule.** A result found only by the topic legs whose every shared topic is one of the conference's 10 most common (by `talk_count` in `caddie-topics`, cached 10 minutes) is a **broad** match (`broad: true`). Broad matches are left out of a text search and of the `anyone` view; the `around_now` view keeps those who are around in the requester's own zone, after every specific match of the page, with `evidence: null` and the reason "Also interested in {topics}." Which legs found a hit is read from the rrf node of the explanation (`explain: true`): the node "rrf score: [..] computed for initial ranks [..]" with one detail per leg, which Elasticsearch 9.5 puts one level below the top on the people index, next to the filter that keeps nested chunk documents out (`FieldExistsQuery [field=_primary_term]`), and which is looked for down to three levels; a detail that names its retriever must name the leg at its position. When the legs cannot be read (the cluster refused the explanation, or its shape is not recognised), matches count every hit as specific, while the push nudge and Bluetooth sightings count a hit as broad unless it shares a topic outside the 10 most common; the server logs a warning that names only the conference and the number of legs, at most once in ten minutes for each of the two causes.
  - Reasons add "They've worked on {evidence}." (first, in a text search) and "They're in {zone} right now." (last, when `zone` is set) to the fixed templates.
- **`POST /api/circles/counts`**: no device header. Body `{ event, talk_ids }` (at most 100). Returns `{ counts: { talk_id: n } }` from a terms aggregation on `shared_talk_ids`. Never members.
- **`POST /api/circles/members`**: body `{ event, talk_id }`. Only a requester whose live document has `talk_id` in `shared_talk_ids` gets `{ talk: { title, start, end, url }, speakers, count, members }`; everyone else gets 403 `{ error: "share_required", count }`. Members are ranked by the same four retrievers plus a match-all retriever, filtered to the talk's sharers and leaving out blocked pairs; `open_to_meet` is not required. Members carry the same `evidence`, `around`, `zone` and `proximity` fields as matches (the members query has no distance leg).
- Reasons use fixed templates only: "They've worked on {evidence}.", "They can speak to {topics}, which you want to learn about.", "They want to learn about {topics}, which you can speak to.", "You are both interested in {talk title}.", "Ask them about {their passage}.", "Also interested in {topics}." (broad matches only) and "They're in {zone} right now." A talk is named only when the requester also shared for it. The opener is the first reason.
- `ref` is the first 16 hex characters of `sha256(event_id:profile_id:REF_SALT)`. It is the UI key of a result and the way a block or a meet request names a person; the server resolves it through the stored `ref` field. `profile_id`, `secret_hash`, `text_hash` and the hashes of others are never returned.

### Find & connect: blocks, presence and meets

Every route here needs the device header and a same-origin `Origin` header or none, like the people writes, and a live document of the requester at that conference: without one, 403 `{ error: "profile_required" }` (a wrong secret is 403 `forbidden`). Lines other people will read (`spot`, `note`, `spot_me`) pass the wordlist filter of `server/moderation.mjs` (`config/moderation-words.json`, LDNOOBW English list, CC-BY 4.0): lowercase, NFKC, diacritics stripped, leet substitutions 0→o 1→i 3→e 4→a 5→s 7→t @→a $→s, then whole-word or phrase matches; any web address other than `linkedin.com` is refused too. A hit is 400 `{ error: "filtered", message: "That was held back by the filter. Edit it and try again." }`. Zones are the conference's room names (the `room` of its `kind: talk` documents, cached 10 minutes) plus `Expo hall`, `Registration`, `Food and coffee`, `Hallway` and `Outside`, matched exactly.

- **`POST /api/people/block`**: body `{ event, ref }`. Writes the block (idempotent, `refresh=wait_for`) and ends any open meet between the two: as `declined` when the blocker was the one asked, as `cancelled` when the blocker asked. An unknown or expired `ref` is 404 `not_found`. Returns `{ ok }`.
- **`DELETE /api/people/block`**: body `{ event, ref }`. Removes the requester's block of that `ref`, whether or not the blocked profile still exists. Returns `{ ok }`.
- **`GET /api/people/blocks?event={slug}`**: returns `{ refs: [ref], blocks: [{ ref, display_name, created_at }] }`, newest first; `display_name` is null when the blocked profile is gone or being deleted.
- **`PUT /api/presence`**: body `{ event, zone, spot, location, until }`. Needs `open_to_meet: true`, else 403 `profile_required`. `zone` must be one of the conference's zones (else 400); `spot` is at most 60 characters, filtered, and may be empty. `location` is optional: `{ lat, lon, accuracy }` (degrees and metres, numbers; other keys or shapes are 400) or null. With `accuracy` of 200 m or better the server stores `presence_location` rounded to 5 decimals, `presence_accuracy` as whole metres, `presence_cell` (the centre of its cell) and `presence_located_at`; with worse accuracy, or without `location`, all four are stored as null, so a zone-only write also clears an earlier position. A fix is also stored as null, without an error, when the device's previous stored fix is under 10 minutes old and the great-circle distance between them over the time between them (at least one second) is above 7 m/s: a phone does not cross a venue in a moment, and a client claiming to is probing. `until` is `hour` (default) or `day`: `hour` sets `presence_until` to 60 minutes from now, `day` to 23:59:59 of the current conference day in the conference's time zone (the client's zone confirmation is the safeguard in that mode); both never past `visible_until`. Turning it on again while on extends it and keeps `presence_since`. Returns `{ ok, zone, spot, until, presence_since, presence_until, located }`, where `until` echoes the mode and `located` says whether a position was stored; the coordinates are never echoed.
- **`DELETE /api/presence?event={slug}`**: clears the presence fields (the position, its cell and its time among them) and the Bluetooth token (`PRESENCE_OFF`), with `retry_on_conflict: 3` and no sequence number guard since it only clears, and ends (`expired`) any active meet of the requester. Returns `{ ok }`.
- **`POST /api/meet`**: body `{ event, ref, topic_id, note }`. `topic_id` is a topic of the conference or null; `note` at most 140 characters, filtered, may be empty. `ref` must point at a live person the requester could see (visible conference-wide, or sharing a talk the requester shares for), else 404 `not_found`; not themselves. A block in either direction is 403 `{ error: "blocked" }`, the same body whichever side blocked. **Asks are now-only**: the requester must have live presence, else 403 `{ error: "presence_required", message: "Turn on 'Around and up for a conversation' first." }`; the person asked must have live presence, else 409 `{ error: "not_around", message: "They're not around right now." }`. An open meet between the two is 409 `{ error: "meet_open", meet_id }`. Three `declined` meets requested by this device since the start of the conference day are 429 `{ error: "paused", message, retry_at }` with `Retry-After` until the end of the day. Limited to 10 requests per device per hour (429). Creates the meet as `requested` with `expires_at` 15 minutes from now and `same_zone` true when both are in the same zone, and returns `{ ok, ...meet }` (the meet shape below).
- **`GET /api/meet/inbox?event={slug}`**: returns `{ incoming, outgoing }`. `incoming` holds the open meets someone else asked for, each the meet shape plus `from: { ref, display_name, about }`; `outgoing` the open meets the requester asked for, each the meet shape plus `to: { ref, display_name }`. Asks past `expires_at` (older than 15 minutes) are not returned. Declined requests stay in `outgoing` as `requested` until they run out. Meets with blocked people are left out. Newest first, at most 100.
- **`GET /api/meet/{id}`**: participants only (403 `forbidden` for anyone else, 404 when there is no such meet). Applies the time and presence transitions first: an open meet past `expires_at`, or an active one with either presence gone, becomes `expired`. A meet that is no longer open is 410 `{ error: "over", state }`. Otherwise returns the meet shape; this route alone adds `other.distance_m` and `other.bearing_deg` when the meet is `active` and both participants have a stored `presence_location`: the great-circle distance in metres rounded to 10, and the initial bearing from the requester to the other person, 0 to 359 degrees clockwise from north, rounded to whole degrees. When either is missing, both keys are absent. The inbox and the action responses never carry them.
- **`POST /api/meet/{id}/accept`** and **`/decline`**: the person asked only (403 for the requester); the meet must be `requested` (410 when over, else 409 `{ error: "state", state }`). **Accept means now**: the person accepting must be around, else 403 `presence_required` (same body as above, the ask stays open); if the requester's presence has meanwhile ended, the ask ends and accept is 410 `{ error: "over", state: "expired" }`. Otherwise accept gives `active` at once, with `active_since = now` and `active_until = now + 20 min`, recomputes `same_zone`, and for a same-zone meet sets `rendezvous` to the shared zone unless one is already set. Decline gives `declined`, which the requester never learns. **`POST /api/meet/{id}/found`**: either participant, `active` only, gives `found`. **`POST /api/meet/{id}/cancel`**: either participant, any open state, gives `cancelled`. Each takes an empty body (or none) and returns `{ ok, ...meet }` with the real new state.
- **`PUT /api/meet/{id}/details`**: body `{ spot_me, rendezvous }`, each optional; the meet must be open (`requested` or `active`). `spot_me` (60 characters, filtered; empty or null clears) is stored under the requester's own id and reaches the other person only while the meet is active; `rendezvous` is one of the conference's zones, or null to clear. Returns `{ ok, ...meet }`.
- **Meet shape**: `{ meet_id, state, requested_by_me, same_zone, topic: { topic_id, label } | null, topic_label, note, created_at, active_since, active_until, expires_at, rendezvous, mine: { spot_me, around }, other: { ref, display_name, about, around, zone, spot, spot_me } }`. `state` is as stored, except that an open meet past `expires_at` reads `expired` and a declined meet reads `requested` to its requester until it runs out. `active_until` equals `expires_at` while active, else null. `other.zone` is set while the meet is active (which needs both around), and also while a `same_zone` ask waits and both are still around in that zone (it is the reader's own zone); `other.spot` and `other.spot_me` only while active; otherwise null. `other.distance_m` and `other.bearing_deg` appear only on `GET /api/meet/{id}` as described there. Nobody outside the meet ever receives a zone, spot, spot-me line, distance or bearing, and nobody at all receives a coordinate.
- Bodies are JSON of at most 8 KB and unknown keys get 400, as for people writes.

### `POST /api/import/schedule` (import my schedule)

Finds one conference's talks in a personal schedule the attendee exported from anywhere. It stores, indexes and logs nothing from the request; the upload lives in memory for that one request.

- Body `{ event, filename, mime, content_base64 }` for a file (`filename` and `mime` optional, at most 255 and 127 characters), or `{ event, text, filename, mime }` for pasted or browser-extracted text (at most 200,000 characters; `filename` and `mime` are optional format hints only, with the same limits, exactly as the Worker accepts them: they pick CSV, TSV or plain text by extension or type, and never cause anything to be fetched or decoded). `event` must be a searchable conference. Unknown keys, both or neither of `content_base64` and `text`, and invalid base64 get 400. A file over 5 MB once decoded, or a body over about 7.2 MB, gets 413; the body limit applies to this route only.
- The type is sniffed from the content: `%PDF` in the first kilobyte, a zip or legacy Office header, or `{\rtf` is a document for Apache Tika; anything else must be UTF-8 (else 415). UTF-8 text that starts with `BEGIN:VCALENDAR` is iCalendar, text that parses as a JSON object or array is JSON, a `.csv`/`.tsv` name, a CSV type or a header row with a title-like column is CSV, and the rest is plain text.
- Documents go through the `attachment` ingest processor in `POST _ingest/pipeline/_simulate` with an inline pipeline (`indexed_chars` 200000, `remove_binary`), so nothing is indexed. No text gives 422 with a plain reason.
- iCalendar uses `SUMMARY`, with `DESCRIPTION` as speaker text and `DTSTART` (UTC, `TZID` or floating in the conference's zone) as a time hint. CSV uses a title-like column (`title`, `session`, `name`, `talk`, `summary`, `subject` and similar), a speaker column and a start, date or time column when present, else every cell. JSON reads Sessionize (`view/All`, `view/Sessions`) and Sched exports and generic arrays, taking each object's title-like field, speakers and start. Text and documents are split into items at blank lines, times and date headers; wrapped lines are merged; times, dates, rooms, URLs, "Add to calendar"-style lines and `Speakers:` labels are stripped or kept as speaker text.
- Reading is bounded, and text past a bound is ignored rather than refused: each line, CSV cell and iCalendar property is read up to 1,000 characters; plain text and iCalendar up to 100,000 lines; CSV up to 5,000 rows or 100,000 cells; a JSON speaker field up to 100 names; and every format up to 3,000 items. Runs of spaces are collapsed before any splitting.
- Candidates: each item offers its text, the part before a ` - ` speaker suffix and its single lines. A candidate needs three words with two content words (two words for the title of a structured entry or of an item that starts with a time). Candidates are de-duplicated and capped at 300.
- Matching is one `_msearch` over the conference's `kind: talk` documents, one search per candidate, size 1. Each is a bool of named queries: `must` one of `exact_title` (`match_phrase` on `title`, sent only with three content words) and `title_words` (`match` on `title`, `minimum_should_match` `3<75%`); `should` `speaker` (`match` on `speakers` with the item's speaker text, two words minimum) and `time` (a one-minute `start` range from the hint). The server keeps the best hit per talk by Elasticsearch score and never re-ranks.
- Returns `{ matched: [{ talk, confidence, matched_text_excerpt }], unmatched_count, extracted_chars }`, in the order the talks appear in the file. `talk` has the search result shape. `confidence` is read from `matched_queries` across every candidate that found the talk: `exact_title`, else `title_and_speaker`, else `title_and_time`, else `title_words`. `matched_text_excerpt` is at most 160 characters of the requester's own line. `unmatched_count` counts items that offered a candidate but matched no talk.
- 10 requests per minute per IP and at most 4 imports at once per instance (503 with `Retry-After` beyond that). Same-origin `Origin` or none, and `Content-Type: application/json`.

### Rate limits

In-memory token buckets per instance, keyed by device (`profile_id`) and by client IP: people writes 20 per minute per device and 60 per IP (blocks, presence and every meet write share these buckets); matches, circle members, the blocks list, the meet inbox and meet reads 30 per minute per device and 90 per IP; search, circle counts, recommendations, topics and suggestions 60 per minute per IP; schedule exports 20 per minute per IP; schedule imports 10 per minute per IP; the conference list 120 per minute per IP; the health check 600 per minute per IP (generous for monitors, but not exempt); and unknown `/api/*` paths 60 per minute per IP. Meet requests also take 10 per device per hour, and three "Not now" replies in one conference day pause the requester until the next day (429 `paused`, counted in Elasticsearch, so it survives a restart). Every `/api/*` route is therefore limited, and each returns 429 with `Retry-After` over its limit. The client IP is the last `X-Forwarded-For` entry, which Google's front end appends, capped at 45 characters; without the header it is the socket address. Earlier entries are chosen by the client and are ignored.

### Reports and moderation (Then)

Reports live in `caddie-people-reports-v1` behind `caddie-people-reports` (env `ES_PEOPLE_REPORTS_INDEX`), created by `node scripts/es-setup-reports.mjs`, which also adds `hidden` (boolean) and `spot_hidden` (boolean) to the people mapping and `hidden` (boolean) to the meets mapping through `PUT _mapping`. `_id` is `{kind}:{target_id}:{reporter_id}`. Mapping (`dynamic: false`): `event_id`, `target_kind`, `target_id`, `target_profile_id`, `reporter_id`, `reason` keyword; `created_at` date. The people key covers the index.

- **`POST /api/people/report`**: body `{ event, ref, context: { kind, id }, reason }`. Needs the device header and a live profile of the reporter at that conference, else 403 `profile_required`. `kind` is `profile`, `meet` or `spot`; `reason` is `harassment`, `hate`, `sexual`, `spam` or `other`; any other key or value is 400. For `profile` and `spot`, `id` is the reported person's `ref` and must equal `ref`; the person must be live, else 404 `not_found` (reporting oneself is 404 too). For `meet`, `id` is a `meet_id` the reporter takes part in (else 404) and `ref` must name the other participant (else 400). The report is written with `op_type: create` and `refresh=wait_for`; a second report of the same target by the same reporter changes nothing and still answers 200. Returns `{ ok, hidden }`.
- **Hiding.** After every report the server counts the target's reports (one document per reporter). At 2 or more the target is hidden from everyone but its owner, by a Bulk partial update that never touches the text fields: a `profile` gets `hidden: true` on the people document; a `meet` gets `hidden: true` and `hidden_owner_id` (the reported participant's `profile_id`, stored unindexed and never returned) on the meet document; a `spot` gets `presence_spot` cleared and `spot_hidden: true` on the people document. The owner of a hidden profile still sees it, flagged "Hidden after reports" (`hidden_for_owner: true` in the `PUT /api/people/profile` response). Every people read and every meet read excludes hidden documents for everyone but the owner: in `server/people.mjs` the `peopleQuery` filter (matches, "Around now", circle members) and `circleCounts` add `must_not: { term: { hidden: true } }`, `personByRef` (the meet request target) returns null for a hidden person while `docByRef` stays unfiltered so a hidden person is still blockable and reportable, and `putProfile` writes `hidden` and `spot_hidden` on every create and full reindex from the flags the document carries and from the reports on file, which outlive the document: one size-0 search of the reports index with a terms aggregation on `target_kind` for the person's `ref`, and at 2 or more reporters of `profile` (or of `spot`) the flag is set again, so a profile deleted by turning both visibility choices off and made again stays hidden, and `hidden_for_owner` says so. It fails closed: when that search fails, a reindex keeps the stored flags (never unhides) and a create answers 502; in `server/connect.mjs` `putPresence` stores no spot while `spot_hidden` is set (and answers `spot: null, spot_hidden: true`), `requestMeet` answers 403 `{ error: "hidden" }` to a hidden requester, `inbox` skips a hidden meet for everyone but `hidden_owner_id` and treats a hidden other participant like a missing document, and `participantMeet` (every `/api/meet/{id}` route) answers 404 for a hidden meet to everyone but `hidden_owner_id`.
- **Web.** "Report" sits next to "Block" in a person card's overflow menu (kind `profile`), in the overflow menu of the other person's card on the meet screen (kind `meet`) and on their spot line there (kind `spot`): a small sheet with the five reasons and one confirming step, then the toast "Thanks. We'll look at it." The owner of a hidden profile sees the "Hidden after reports" banner on the profile screen.
- **Rate limit.** 20 reports per device per hour, on top of the people write limit per IP. Neither the reporter nor the target learns who reported; `profile_id`, `reporter_id` and report ids are never returned.
- **Operator CLI** `node scripts/moderation.mjs --event <slug> <action>`, with `ELASTISEARCH_API_KEY` (the admin key; `--unhide` and `--purge` require it, while `--hidden`, `--since` and `--delete` also run with `ES_PEOPLE_API_KEY` alone): `--hidden` lists hidden profiles, spots and meets with report counts and reasons; `--since <iso>` lists the reports made since that instant; `--unhide <kind>:<id>` clears the flag of one target and deletes its reports, so two new reports are needed to hide it again; `--delete <kind>:<id>` deletes a profile document or a meet document, or clears a spot line (never a device's own data; the person can create a profile again, hidden again while two reports of it are on file); `--purge` deletes the conference's reports once it has ended (23:59:59 on `end_date` in its time zone). `<id>` is a `ref` for `profile` and `spot` and a `meet_id` for `meet`. Output shows display names, refs and meet ids only.

### Web Push nudges

The in-app nudge rule of the "Then" phase as a push channel: the pocket case. Routes in `server/push.mjs`; the rule in `server/nudge.mjs`.

- **`GET /api/push/vapid`**: no device header; `{ publicKey }`, the value of `VAPID_PUBLIC_KEY`, or `null` when push is not configured (the app then explains that nudges are not set up). `Cache-Control: public, max-age=3600`; the public rate limit per IP.
- **`PUT /api/push/subscription`**: body `{ event, subscription: { endpoint, keys: { p256dh, auth }, expirationTime? } }`, the browser's `PushSubscription.toJSON()`. Needs the device header and a live profile at that conference (403 `profile_required`); `endpoint` must be a `https:` URL of at most 2048 characters, the keys base64url strings. Writes the subscription document (`refresh=wait_for`; the same endpoint again overwrites). Returns `{ ok }`. Shares the people write buckets.
- **`DELETE /api/push/subscription`**: body `{ event, endpoint }`. Deletes the document only when it belongs to the requester's profile; answers `{ ok }` either way. Like every route that needs a profile, it answers 403 `profile_required` while the requester's profile delete is pending; that is harmless, since the delete removes the subscription and the purge finishes it within the hour.
- **The rule** runs after every successful `PUT /api/presence`, once the response has been sent, and never changes that response. As the person whose presence was written, with the same `peopleQuery` as `POST /api/people/matches` (`when: around_now`, size 20, blocked pairs excluded, `explain: true`), it keeps the results that are not broad, are around, and are in that person's zone. For each such pair not yet nudged today (the nudges index create above) it sends one push to each person's subscriptions, at most 3 pushes per receiver per hour. When both people of a pair get one, the second person's pushes follow the first's after a random pause of 0 to 3 seconds (`pairDelayMs` in `server/nudge.mjs`), on every channel, so two phones side by side do not light up together; the pause is part of the work after the response, never of the response. Payload (JSON): `{ title: "Conference Caddie", body: "Someone who's worked on {evidence} is in {zone} right now", data: { url: "/e/{slug}#/people?around=1" } }`, TTL 600 s, urgency normal. `evidence` is, for the person whose presence was written, the other person's `evidence` as the matches query returns it (`<mark>` removed, cut at a word boundary to about 80 characters); for the other person it is the first 80 characters of the writer's `expertise`; either falls back to that person's first speak topic label, and a person with neither gets no push. The payload never carries a name, a distance, a `ref`, a `profile_id` or a spot line. A person hidden after reports (`hidden: true`) or a sample profile (`sample: true`) never takes part: as the person whose presence was written the rule stops before any query, and as the other person the query leaves them out. When the semantic legs fail with an inference failure the rule ranks with keyword legs, like matches. A subscription the push service answers 404 or 410 for is deleted. Every failure is one log line with a status or error class and nothing else.
- **Service worker** (`web/public/sw.js`): `push` shows the payload as a notification (tag `caddie-nudge`, the app icon); `notificationclick` focuses an open window of the app and navigates it to `data.url`, or opens one. `#/people?around=1` opens the People tab with "Around now" on.
- **Client** (`web/src/people/push.ts`, `PushControls.tsx`): the switch "Nudge me even when the app is closed" under the presence switch and in Settings, both reading `caddie.push.v1.{slug}` (`{ on, endpoint, notice_seen }`). First tap: the notice "Nudges tell you when someone whose experience matches yours is in your zone. They never say who until you open the app, and you get at most a few an hour." On iPhone or iPad outside a Home Screen app (`display-mode: standalone` / `navigator.standalone`), an inline explainer (Share, then Add to Home Screen) and the switch stays off; in Chrome with a captured `beforeinstallprompt`, an "Add to Home Screen" button first, then the permission request; then `pushManager.subscribe` with the server's key and `PUT /api/push/subscription`, and the row shows "On". Denied permission shows one line. Turning it off deletes the server's copy and, when no conference uses it, the browser subscription. "Delete my profile" does the same for every conference. Mock builds post a stand-in subscription and expose `window.__caddiePushTest()`.
- **Env and secrets**: `VAPID_PUBLIC_KEY` and `VAPID_SUBJECT` (`mailto:` or `https:`) are plain env vars; `VAPID_PRIVATE_KEY` is mounted from Secret Manager `caddie-vapid-private`. `node scripts/vapid-keys.mjs` writes the pair to two git-ignored `*.key` files and prints the `gcloud secrets` commands (`caddie-vapid-public`, `caddie-vapid-private`) and the `rm`; it never prints a key. `scripts/deploy.sh` reads the public key from `caddie-vapid-public` and deploys with nudges off when the private secret does not exist. Rotating the pair invalidates every browser subscription.

### Native push

The same nudge, sent to the official iOS and Android apps through APNs and FCM as a generic alert (`docs/contracts/people-api.md`, Native push registration). Routes in `server/push.mjs`; the channels in `server/native-push.mjs`; the rule in `server/nudge.mjs`, unchanged. Only the official deployment holds the keys (`docs/NATIVE_PLAN.md`, section 14, decision 3); every other backend leaves them unset and advertises `push.apns` and `push.fcm` false.

- **`PUT /api/push/native`** (optional route): body `{ event, platform: "apns" | "fcm", token, environment? }`. Needs the device header and a live profile at that conference (403 `profile_required`, also while a profile delete is pending). An APNs token is 64 to 200 hexadecimal digits (stored lowercase), an FCM token 32 to 4096 characters of `[A-Za-z0-9_:-]`; `environment` is `production` (default) or `sandbox` and is refused with `fcm`. Closed body, at most 8 KB, the people write buckets. When the server does not push to that platform it answers 404 `{ error: "push_unavailable" }` and stores nothing. Otherwise it writes the requester's registration for that platform at that conference (`refresh=wait_for`; a new token overwrites the old one) and returns `{ ok }`.
- **`DELETE /api/push/native`**: body `{ event, platform, token }`. Deletes the requester's registration for that platform at that conference only while it still holds that token (read, compared, then deleted with `if_seq_no`, so a `PUT` in between wins); answers `{ ok }` either way, also when the platform is not configured.
- **Sending.** The rule picks receivers and writes the nudge record exactly as for Web Push, and the limits cover every channel together: a receiver is anyone with a Web Push subscription or a native registration on a channel the server sends on, one nudge is one push to each of the receiver's subscriptions and registrations, and it counts once against the 3 per hour. When neither VAPID nor a native channel is configured, the rule stops before any query, as before. The payload is not the Web Push one: APNs and FCM payloads reach Apple and Google in plain text, while Web Push payloads are end-to-end encrypted to the browser, so every native push is the same generic alert (`NATIVE_ALERT` in `server/native-push.mjs`): title `Conference Caddie`, body `Someone whose experience matches yours is in your zone right now`, deep link `caddie://people?around=1`, and nothing about the people, the zone or the conference. APNs: `POST /3/device/{token}` to `api.push.apple.com` (`api.sandbox.push.apple.com` for `sandbox`) over one reused `node:http2` session per host (on GOAWAY the pushes in flight above the server's last stream id are rejected at once, and a push that fails with a connection error, GOAWAY, a refused stream, a reset or a refused connection, is sent once more on a fresh session; `apns-collapse-id` makes a duplicate show once), with `authorization: bearer {provider token}`, `apns-topic` (`APNS_BUNDLE_ID`, default `app.conferencecaddie`), `apns-push-type: alert`, `apns-priority: 5`, `apns-expiration` now + 600 s, `apns-collapse-id: caddie-nudge`, and the body `{ aps: { alert: { title, body }, sound: "default" }, deepLink }`. The provider token is an ES256 JWT (`kid` the key id, `iss` the team id, `iat`) signed with the `.p8` key, used for 40 minutes; a 403 `ExpiredProviderToken` or `InvalidProviderToken` retries once: with the current token when another push renewed it meanwhile, else with a renewed one, unless the token is younger than 20 minutes (Apple refuses renewals more often than that). FCM: `POST https://fcm.googleapis.com/v1/projects/{FCM_PROJECT_ID}/messages:send` with the runtime service account's access token from the metadata server (`GET http://metadata.google.internal/computeMetadata/v1/instance/service-accounts/default/token?scopes=https://www.googleapis.com/auth/firebase.messaging` with `Metadata-Flavor: Google`, so the token carries only the `firebase.messaging` scope that `messages.send` needs, not the default `cloud-platform`; cached by the FCM channel alone, apart from the classifier's token, until a minute before it expires; a 401 renews it and retries once; after a failed token request no other is made for 60 s, and sends in that time fail at once and keep their registrations), and the message `{ token, notification: { title, body }, data: { deepLink }, android: { ttl: "600s", priority: "normal", notification: { tag: "caddie-nudge" } } }`. Every request times out after 10 s. A registration is deleted when APNs answers 410 or 400 `BadDeviceToken`, or FCM answers 404 `UNREGISTERED` or 400 `INVALID_ARGUMENT` with a field violation on `message.token`. Any other failure, APNs 400 `DeviceTokenNotForTopic` included (a wrong `APNS_BUNDLE_ID` gives it for every token), is one log line, `Native push failed: {platform} {status} {reason code}` or the error class, and the registration is kept. `push.apns` and `push.fcm` mean configured and well-formed; five authentication failures in a row (APNs: a 403 from the production host, since a client chooses sandbox; FCM: a 401 that a fresh token did not cure or a 403, except `SENDER_ID_MISMATCH` and `THIRD_PARTY_AUTH_ERROR`, which one registration token causes) turn that channel off until the server restarts: the flag and `GET /api/capabilities` answer false, sends stop, `PUT /api/push/native` answers 404 `push_unavailable`, and one line says `APNs push is off: 5 authentication failures in a row.` (or `FCM`). Any answer past authentication resets the count.
- **Env and secrets**: the `.p8` key is mounted from Secret Manager `caddie-apns-key` as the file `/secrets/apns/AuthKey.p8` of a secret volume, pinned to its newest enabled version at deploy time, and `APNS_KEY_FILE` (a plain env var) names that path; the key itself is never an env var; `APNS_KEY_ID` and `APNS_TEAM_ID` are plain env vars that `scripts/deploy.sh` reads from `caddie-apns-ids` (`"{key id} {team id}"`); `APNS_BUNDLE_ID` is a plain env var. FCM has no key: `FCM_PROJECT_ID` (a plain env var) names the app's Firebase project, in which `caddie-runtime` holds the role Firebase Cloud Messaging API Admin, and turns FCM on. A channel is on only when its settings are all present and usable; a setting that is present but unusable keeps that channel off and logs one line at start naming the setting, never its value, and so does an `APNS_KEY_FILE` with no readable file behind it (`APNs push is off: APNS_KEY_FILE names no readable file.`), which never stops the server. The key file is read once at start. No key, JWT, access token or device token is ever logged. `docs/OPERATOR_CHECKLIST.md` (step 7a) creates the secrets. `scripts/deploy.sh` sets the APNs settings and mounts the key only with `NATIVE_PUSH_APNS=1`, and sets `FCM_PROJECT_ID` only with `NATIVE_PUSH_FCM=1`, in the deploying shell; without them it deploys both channels off, and every deploy prints which channels it turns on and off.

### Find people near me by Bluetooth (Android companion)

The same web app, wrapped with Capacitor (`web/capacitor.config.ts`, `web/android/`, app id `app.conferencecaddie`), plus a native plugin `CaddieBle` (`web/android/app/src/main/java/app/conferencecaddie/ble/`) that lets two opted-in people whose expertise and interests match be told when they are within a few metres, phone in pocket. Web and iOS are unchanged: the row does not exist there. Build steps are in `docs/ANDROID.md`.

- **On the air.** The phone advertises the fixed 128-bit service UUID `BLE_SERVICE_UUID = e52c391c-b926-4856-9a38-d46c3c10c733` (the same constant in `server/ble.mjs` and `BleConstants.kt`) with its current token as service data: Bluetooth 5 extended advertising, non-connectable, non-scannable, low duty cycle, no device name, no TX power. It scans only for that UUID (`SCAN_MODE_BALANCED`, hardware batching where supported) inside a foreground service whose notification reads "Conference Caddie is finding people near you" and carries a Stop action. The service stops by itself when presence ends, when no fresh token has arrived for 11 minutes, when Bluetooth turns off, or on Stop. Nothing about the person is sent over Bluetooth; the token is meaningful only to this server.
- **Tokens.** `PUT /api/presence` accepts one more key, `ble` (boolean, optional). `ble: true` mints 16 random bytes (base64url, 22 characters) and stores them as `ble_token` with `ble_token_until` = now + 10 minutes, never past `presence_until`; the response adds `ble: { token, rotate_at }`. `ble: false` clears both fields; a write without `ble` leaves them as they are. **`POST /api/presence/ble/rotate`** body `{ event }` (device header, people write limits) mints a new token for a requester whose presence is on, else 403 `presence_required`; a requester without a live, visible profile (none, not `open_to_meet`, or a delete pending) gets 403 `profile_required`, and a profile that changed twice while the token was written gets 409 `{ error: "The profile changed at the same time; try again" }` (see "Own-document writes are guarded"); returns `{ ok, ble: { token, rotate_at } }`. Tokens die with presence (`DELETE /api/presence`, the purge, visibility off).
- **`POST /api/presence/sightings`**: body `{ event, sightings: [{ token, rssi }] }`, device header; at most 50 entries (51 is 400), each a 22-character base64url token and an integer RSSI from -127 to 20, no other keys; 6 requests per minute per device and 300 per IP (429), in buckets of their own so a venue's shared address does not starve the people reads. The requester must be live and visible (403 `profile_required`) and must itself be around with a live token (403 `ble_required`): only a phone that is broadcasting may ask who is near it. The server keeps the strongest RSSI per token, drops those below `BLE_NEAR_RSSI` (default -75 dBm, roughly a few metres at medium TX power), resolves the rest to people who are live, around, visible conference-wide, not hidden after reports and not blocked in either direction, then runs the **same ranking as `POST /api/people/matches`** as the requester, restricted to those documents (`peopleQuery` in `people.mjs`, so nothing is ranked twice), and keeps only the strong matches: the specificity rule applies and broad matches are dropped. Returns `{ nearby: [{ ref, display_name, evidence, speak_topics, zone }] }` in rank order. Never a token, a signal strength, a distance or a profile id. Since tier 3 Phase 4 the server resolves both the derived tokens v1 (with the master keyring `BLE_MASTER_KEYRING`; `GET /api/capabilities` then says `ble.mode` `derived-v1`) and these legacy tokens under the rules of `docs/contracts/ble-tokens.md`, which supersede this paragraph where they differ: co-location with the requester, at most 10 new people per device per window and 30 per rolling hour, the zone only within the requester's own zone, `ble_key_id` in a derived-v1 answer, and 403 `ble_rekey` for a session under a retired master.
- **Symmetric by construction, no sighting stored.** Both phones scan and both report, so each side learns on its own, and the server never stores a sighting: no index holds who heard whom, and the log has only method, path, status and duration. The privacy consequence to name plainly: a sightings report tells the server which tokens one device heard, for the duration of that request only. The server resolves them, answers, and keeps none of it. What it does keep, for the per-device caps of `docs/contracts/ble-tokens.md`, is whom it returned to each device in the last hour: a list of `{ ref, at, w }` on the requester's own people document (`ble_caps`, never indexed, never returned and never exported), pruned to the last hour whenever it is written, with `ble_caps_until`, the time its newest entry leaves the hour. The hourly purge, and `npm run people:purge`, clear the list once that time has passed, and it goes with the profile. It names only people the device was already shown. Tokens rotate every 10 minutes, so a token overheard by any other radio cannot be followed from one place to the next, and an old one resolves to nobody.
- **Client.** `web/src/people/ble.ts` and `BleControls.tsx`, mounted by `PresenceControls`. The row appears only when `Capacitor.isNativePlatform()` and the plugin reports a Bluetooth LE adapter: "Find people near me by Bluetooth (phone can stay in your pocket)", off by default, enabled only while "I'm around" is on, with the first-time notice verbatim: "Your phone broadcasts a random code that changes every 10 minutes and listens for others. Nothing about you is sent over Bluetooth; the code means something only to our server, only while you're around. Only people who also turned this on can be found, and you're told only about strong matches within a few metres." On: presence is written with `ble: true`, the plugin starts with the token and the remaining presence time, a new token is fetched 20 seconds before `rotate_at`, and every `sightings` event (at most one per 10 seconds, deduped per token) is sent to `/api/presence/sightings`. The first `nearby` person not nudged today becomes one local notification whose body is exactly "Someone who's worked on {evidence} is right near you" (no name, no distance); it is recorded in `caddie.nudged.v1.{slug}`; tapping it opens the People tab on "Around now" with that card revealed. Off: the plugin stops and the token is cleared; presence stays as it was.
- **Plugin surface** (`CaddieBle`): `isAvailable()` → `{ available, enabled, extended, rationale }`; `checkPermissions()` / `requestPermissions()` → `{ granted, ...states, rationale }` for the permissions this Android version needs; `start({ token, scan, durationMs })`; `rotate({ token, durationMs? })`; `stop()`; `isRunning()`; `notify({ title, body, data? })`; events `sightings` `{ sightings: [{ token, rssi }] }`, `stopped` `{ reason }`, `notificationTap` `{ data }`. Permissions: `BLUETOOTH_ADVERTISE`, `BLUETOOTH_SCAN` (`neverForLocation`), `BLUETOOTH_CONNECT`, `POST_NOTIFICATIONS`, `FOREGROUND_SERVICE`, `FOREGROUND_SERVICE_CONNECTED_DEVICE`; on Android 8.0 to 11 the legacy `BLUETOOTH`, `BLUETOOTH_ADMIN` and `ACCESS_FINE_LOCATION` (a BLE scan needs it there; no position is ever read). Target SDK 34, min SDK 26, compile SDK 36 (Capacitor's floor).
- **Native shell.** The bundled app calls the API at `VITE_API_ORIGIN` (set only for the app build; `web/src/native.ts` prefixes `/api/` fetches when the app runs natively and does nothing otherwise) through `CapacitorHttp`, so requests leave from the native layer with no `Origin` header, like a curl call, and the same-origin check and CSP are unchanged. The service worker is not registered in the app.

## Moderation

The filter for the lines other people read (`spot`, `note`, `spot_me`) lives in `server/moderation.mjs` and has three layers, in order. Copy says "filter", never "safe".

1. **In process.** A web address other than `linkedin.com` is refused. The line is normalised: NFKC, lowercase, diacritics stripped, leet substitutions 0→o 1→i 3→e 4→a 5→s 7→t @→a $→s, punctuation to spaces.
2. **Rules: `caddie-people-rules-v1` behind `caddie-people-rules`** (`node scripts/es-setup-rules.mjs`, idempotent). Mapping (`dynamic: false`): `query` percolator; `text` text with the custom analyzer `rule_text` (a `mapping` char_filter for the same leet table, `standard` tokenizer, `lowercase`, `asciifolding`); `rule`, `kind`, `source` keyword; `created_at` date. `node scripts/moderation-rules.mjs --reload-rules` replaces every rule with one document per entry of `config/moderation-words.json`: a word or phrase becomes `match_phrase` on `text`, an entry starting with `re:` a `regexp` on `text` (single tokens, lowercase); ids are `w-`/`re-` plus a hash of the entry. `--test "<text>"` percolates a line and prints the matching rule ids. The server percolates the normalised line (`percolate` query on `query`, `document: { text }`) and any hit rejects. When the call fails or the index is missing (checked at start and retried a minute after each failure), the in-process wordlist from the same file decides, so the MVP behaviour never goes away. The index must stay `caddie-people-rules*` because the server reads it with the people key.
3. **Classifier.** `POST https://language.googleapis.com/v1/documents:moderateText` with `{ document: { type: 'PLAIN_TEXT', content } }`, a Bearer token from `http://metadata.google.internal/computeMetadata/v1/instance/service-accounts/default/token` (`Metadata-Flavor: Google`, cached until 60 s before expiry). Of the watched categories (`MOD_CATEGORIES`), the highest `confidence` at or above `MOD_REJECT` rejects; at or above `MOD_HOLD` holds; any error or timeout (`MOD_TIMEOUT_MS`) holds. It fails closed. `MOD_CLASSIFIER=off`, or `auto` with no metadata server at start, turns it off and logs `classifier: off` once; `on` keeps it on regardless. It is a classification API, not a generative model, and it is English-centric. Setup: `gcloud services enable language.googleapis.com` once; `caddie-runtime` needs no IAM role for it (see `scripts/deploy.sh`).

Outcomes: **reject** is 400 `{ error: "filtered", message: "That was held back by the filter. Edit it and try again." }`, unchanged from the MVP. **hold** is new: the line is stored with a `*_pending: true` flag, shown only to its author, answered with `{ error: "held", message: "Waiting for the filter; it will appear shortly." }` and reported with reason `classifier` (reporter `classifier`, one report per target, counted like a device's report by the hide-at-two rule). Per route: `PUT /api/presence` stores the spot with `presence_spot_pending: true` and `meetView` shows the other person's spot only while that flag is off; `POST /api/meet` stores `note_pending: true` and the meet shape gives the note as `""` to everyone but its author (the inbox too); `PUT /api/meet/{id}/details` stores `spot_me_pending: { profile_id: true }` and the other participant gets `spot_me: null` while it is set. In each case the 200 body gains `held: { fields: ['spot' | 'note' | 'spot_me'], message }` and the author keeps seeing their own text. A held line is replaced by the author's next write of that field (a new `moderate()` call), cleared with presence or when the meet ends, and otherwise waits for the operator. `isFiltered(line)` (boolean, in process only) and `FILTERED` keep their MVP contract; `moderate(line)` resolves to `{ outcome: 'accept' | 'reject' | 'hold', body, category }` and never throws. The server logs one line per checked text, `filter: accepted|rejected|held <category>`, and never the text, the scores or the device.

## Import from GitHub (public)

The first profile import. No sign-in and no OAuth: the person types a public GitHub handle, the server reads the public GitHub REST API, the app proposes text and topic chips, and the person edits and accepts. The handle and the raw repository data are never stored anywhere (not on the server, not in Elasticsearch, not in device storage) and never logged; only what the person accepts lands in the existing profile fields through `PUT /api/people/profile`. No generative model is used: every sentence is a fixed template over GitHub's own fields.

### `POST /api/import/github`

Body `{ event, handle }`, at most 8 KB, unknown keys get 400. `handle` matches `^[A-Za-z0-9](?:[A-Za-z0-9-]{0,37}[A-Za-z0-9])?$`. No device header, because nothing is written. Rate limit 5 per IP per 10 minutes through the existing buckets (`{ error: "Too many requests" }` with `Retry-After`).

- The server fetches `GET https://api.github.com/users/{handle}` and `GET https://api.github.com/users/{handle}/repos?per_page=100&sort=pushed&type=owner` with `User-Agent: ConferenceCaddie/0.2`, `Accept: application/vnd.github+json`, `Authorization: Bearer <GITHUB_TOKEN>` only when the env var is set, and an 8 s timeout. Forks and archived repositories are excluded.
- From the remaining repositories: primary languages (counted per repository), repository topics and descriptions, with the 15 most recently pushed repositories counting double.
- Response `{ ok: true, proposal }` where `proposal` is:

| Field | Rule |
|---|---|
| `about` | The GitHub bio on one line, at most 280 characters; `""` when there is none. |
| `expertise` | `"Built {repo} ({language}): {description}."` for up to 6 of the most recently pushed repositories that have a description, joined by spaces, at most 500 characters. No adjectives and no invented facts. |
| `topic_candidates` | Up to 20 lowercased strings: the top languages, then the repository topics. |
| `repo_count` | The number of repositories kept. |
| `suggested_speak_topics` | At most 15 `{ topic_id, label }` of the conference's topics whose label equals a candidate or starts with it as a whole word. The lookup is the same `bool_prefix` type-ahead query `/api/topics` runs, in one request, through the topics module. |
| `extra_terms` | The candidates that matched no topic of this conference. |

- Errors: 400 for bad input; 404 `{ error: "not_found" }` for an unknown handle; 429 `{ error: "rate_limited" }` with `Retry-After: 600` when GitHub rate-limits the server; 502 `{ error: "upstream" }` for any other GitHub failure. A failed topics lookup does not fail the call: every candidate is then returned in `extra_terms` and the log says `GitHub import topic lookup unavailable`.
- The log never holds the handle: only the failure class and GitHub's status (`GitHub import rate_limited: 403`).
- Client: the "Import from GitHub" control in the profile's About you card (`web/src/people/ImportGitHub.tsx`). The preview shows the proposed About, the proposed "Things I've built, run or broken" text and the suggested chips pre-selected; "Use this" appends the text after a blank line (never overwriting), fills About only when it is empty and adds the chips to "I can speak to". Error copy: "No GitHub user with that name.", "GitHub is busy; try again in a few minutes." (GitHub's limit and our own), "Could not reach GitHub.". `importProfile('github')` returns `{ ok: true }` because the component handles the flow; `importProfile('linkedin')` still returns `{ ok: false, error: "not implemented" }`.
