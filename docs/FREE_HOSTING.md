# Free hosting: Conference Caddie on Cloudflare, with the talk bundles on GitHub Pages

This page describes the free version of Conference Caddie, which has no expiry and needs no Elasticsearch and no Google Cloud. The people features are the main feature: profiles, people matching, talk circles, asks, waves, meets, presence, block, report, moderation, nudges and push. Talk search, browse, schedule, For you, topics and schedule import come along.

## What you need to do next (read this first)

The free stack is **live** at https://conference-caddie.krlehnardt.workers.dev since 2026-11-11 (UTC). The web app and the API share that one origin; there is no separate API Worker. The deploy, the secrets, the migration, the repository variables, both workflows, the live checks and the new QR code are done (see [Status](#status-on-2026-11-11)). These things are left, and only you can do them:

1. **Delete any Cloudflare API token that is no longer used**, in the Cloudflare dashboard. Keep only the token the deploy uses, and make sure that is the one your shell exports as `CLOUDFLARE_API_TOKEN`.
2. **Open the app on a phone and scan the new QR code** (`docs/demo/qr-kubecon.png`) once this change is merged.
3. **Point the Android build at the Worker** (step 1 of [Approvals needed](#approvals-needed-shutting-down-the-paid-stack)). It is not irreversible, but installed APKs keep calling Cloud Run until it is done.

One decision is also yours:

- **The paid stack keeps running until you approve its shutdown.** Cloud Run, Artifact Registry, Secret Manager, Elastic and billing stay as they are until you approve, step by step, the shutdown steps already listed in [Approvals needed](#approvals-needed-shutting-down-the-paid-stack). Several steps are irreversible. None has been done, and none should happen until the free stack has passed the live smoke for a full day and the Android build points at the Worker.

The detailed findings and checks are in [REVIEW_NOTES_FREE.md](../REVIEW_NOTES_FREE.md).

## Where the app lives, and why

The web app is served by the Cloudflare Worker, on the Worker's own origin, together with the API: https://conference-caddie.krlehnardt.workers.dev. `worker/scripts/deploy.sh` prints this address on every deploy.

It used to be planned for GitHub Pages at `https://kurtlehnardt.github.io/conferenceCaddie/`. That origin is shared by seven other live Pages sites of the same account, and every page on an origin can read that origin's `localStorage`. Any of those sites, or a compromise of any of them, could have read Conference Caddie's device secrets and acted as its users (review finding R18). On 2026-11-10 you chose to serve the app from the Worker instead (`DECISIONS.md`).

GitHub Pages now publishes only public data, which holds no secrets: the talk bundles under `bundles/`, `conferences.json`, the tier 1 `capabilities.json` (its `talks.bundle_base` stays `https://kurtlehnardt.github.io/conferenceCaddie/bundles/`), and a landing page with no script and no storage access. The landing page links to the app (the repository variable `CADDIE_APP_URL`), or says the app is not live yet. It is also the site's 404 page, so old links still lead to the app.

## Architecture

```
Phone browser ──HTTPS, one origin──> Cloudflare Worker "conference-caddie"
                                         ├─ static assets: the Vite/Preact app (free, never runs the Worker's code)
                                         └─ /api/*, /admin/*: the Worker's code, X-Caddie-Device header, no cookies
                                                              │
                                   ┌──────────────────────────┼───────────────────────────┐
                                   ▼                          ▼                           ▼
                        ConferenceDO (one per slug)     DirectoryDO ("global")      Workers AI
                        SQLite: talks, FTS5, vectors,   conference list, usage      bge-small-en-v1.5
                        people, presence, asks, meets,  totals                      embeddings
                        blocks, reports, push, rules
                                   ▲
                        Cron Trigger every 10 minutes (purge, expiry, pending embeddings, usage)
GitHub Actions: weekly ingest ──admin routes──> Worker
GitHub Pages: public talk bundles, conferences.json, capabilities.json and a landing page (no app)
```

- **One Worker, one origin.** The Worker serves the web app as Workers static assets (`[assets]` in `worker/wrangler.toml`, the directory `web/dist-worker/`). Only `/api`, `/admin` and their subpaths run the Worker's code (`run_worker_first`), so app files cost no Worker request and never count in the pace budget. Any other path with no file gets `index.html` (`not_found_handling = "single-page-application"`), so a deep link such as `/e/{slug}` boots the app. `worker/src/index.js` routes the 31 API routes. All heavy work runs in Durable Objects, because the Free plan allows 10 ms of CPU per Worker request.
- **Storage: SQLite-backed Durable Objects only.** There is one `ConferenceDO` per conference slug and one `DirectoryDO` named `global`. D1, KV, Vectorize and Pages (Cloudflare's) are not used.
- **Keyword search:** SQLite FTS5 with the porter and unicode61 tokenizer.
- **Semantic search:** vectors from `@cf/baai/bge-small-en-v1.5` (384 dimensions), called with CLS pooling, L2-normalised, stored as float32 BLOBs, with a brute-force dot product over vectors held in Durable Object memory. The model is set by the `EMBED_MODEL` variable. No generative LLM is called anywhere.
- **Ranking:** reciprocal rank fusion in code (rank constant 60). The old "Elasticsearch does all ranking" rule is lifted. People matching also applies a cosine floor of 0.61 to each semantic leg for bge-small with CLS pooling (re-measured on 2026-11-10, see `worker/src/people/rank.js`), set by `PEOPLE_SEMANTIC_FLOOR`; lower it if recall feels low.
- **Auth:** the device header `X-Caddie-Device: {profile_id}.{secret}`. Only `sha256(secret)` is stored, and the compare is constant time. There are no cookies.
- **Admin auth:** every `/admin/*` request is signed with the admin token: `X-Caddie-Admin: v1 <ts> <nonce> <bodySha256> <sig>`, an HMAC-SHA256 over the method, the path and query, the body hash, the timestamp and the nonce, so the token itself never travels. The Worker answers 404, as for an unknown path, to anything that is not correctly signed with `ADMIN_TOKEN` or, during a rotation, `ADMIN_TOKEN_NEXT`, and it reads the body only after the signature and the clock (within 300 seconds) are good. The Worker checks the clock again after the body has arrived, each Durable Object refuses a timestamp more than 305 seconds from its own clock and a nonce it has already served (`401 admin_replay`), and ten bad signatures a minute from one address make that address get 404 before anything is computed. Recording the nonce writes a row, so once the account's daily written-rows limit is reached every admin request, reads included, answers `503 daily_limit` until 00:00 UTC. The details are in [worker/README.md](../worker/README.md) (Admin requests).
- **Admin signature v2:** the Worker also accepts `X-Caddie-Admin: v2 ...`, which signs the origin the request was sent to as well, so a v2 request that reaches another host cannot be replayed to this Worker. The cross-host replay is closed only once step d refuses v1; until then a captured v1 request can still be replayed across hosts. Since step c of the move (DECISIONS.md, "Admin signature v2") the Worker-side clients, `push-ingest.mjs` (the weekly CI ingest included), `topics-local.mjs` and `migrate-from-backup.mjs`, sign v2 by default, for the origin of their `--api` base, and they refuse a base that is not a plain origin before sending anything. The rollback is `CADDIE_ADMIN_SIG_VERSION=1`: in the environment for a local run, or as the repository variable `CADDIE_ADMIN_SIG_VERSION` for the CI ingest; unset or empty means v2. It works only until step d, which will make the Worker refuse v1. The `caddie-admin` CLI and `scripts/smoke.mjs` still sign v1 until their own step-c change, so step d must wait until they sign v2 as well. The origins a v2 signature may name come from the Worker variable `ADMIN_ORIGIN` when it is set, and otherwise from the request URL the Worker was invoked with; `ADMIN_SIG_MIN` sets the oldest version accepted, and its default lives in the source (`"1"` until step d changes it to `"2"`). Neither is set in `worker/wrangler.toml` today. The details are in [worker/README.md](../worker/README.md) (Signature v2).
- **CORS:** the app is on the Worker's own origin, so it needs no CORS. The Worker accepts its own origin (browsers send `Origin` on same-origin writes too), the localhost development origins in `ALLOWED_ORIGINS`, and requests with no `Origin` header (Node, curl, the native apps), which get no CORS headers. Any other origin gets 403 `cross-origin request`. The admin routes refuse every request with an `Origin` header.
- **Static file headers:** the Worker-mode build writes `web/dist-worker/_headers` with the Cloud Run server's Content-Security-Policy (`connect-src 'self'`, `frame-ancestors 'none'`), `X-Content-Type-Options`, `Referrer-Policy`, `Strict-Transport-Security` and `Permissions-Policy`. Each hashed file under `/assets/` is cached as immutable for a year; `index.html`, `sw.js` and the manifest are `no-cache`, so a deploy reaches every phone on its next load.
- **Push:** VAPID Web Push is sent from the Worker with Web Crypto (RFC 8291 and 8292). The VAPID pair is stored as Worker secrets. A subscription is accepted only on a known push service host (`PUSH_SERVICE_HOSTS` in `worker/src/push/webpush.js`), on the default port: `fcm.googleapis.com` and `android.googleapis.com` (Chrome Stable, Opera, Samsung Internet and other Chromium browsers), the exact host `jmt17.google.com` (Chromium builds on a non-Stable channel: Chrome Beta, Dev and Canary, unbranded Chromium, and some other Chromium-based browsers), `*.notify.windows.com` (WNS, which Chromium-based Edge uses), `*.push.services.mozilla.com` (Firefox) and `web.push.apple.com` and `*.push.apple.com` (Safari). At send time a stored row whose host is not on the list is skipped and logged by host only, and it stays stored; only the push service's own 404 or 410 deletes a row. When the app starts, a browser with notifications allowed and the nudge switch On sends its subscription to the Worker again, at most once every 24 hours per conference (at once if the browser's endpoint changed, after a random 0 to 30 second wait), which restores a row the Worker lost; a conference the Worker reports as ended, unknown or without a profile for the device is turned off on the device and not sent again.
- **Privacy rules are unchanged:** reciprocity, circles gated by sharing, presence and zone visibility, symmetric block, silent decline, expiry, delete everywhere, device-secret ownership, and contact shown only to entitled viewers. The UI shows no raw IDs.
- **Schedule import:** the Worker-mode build (`VITE_CLIENT_EXTRACT=1`) reads PDF, DOCX and ODT files in the browser, with pdf.js and fflate loaded on demand, and sends only text to the Worker. The Cloud Run build still sends files to Elasticsearch. This reverses the 2026-11-09 choice for the free stack only.
- **Web build:** `npm --prefix web run build:worker` (`vite build --mode worker`) builds the app for the Worker into `web/dist-worker/`: base `/`, the API on the same origin, the in-browser document reader, and the `_headers` file. `worker/scripts/deploy.sh` runs it before `wrangler deploy`. The Cloud Run build (`npm run build`) is unchanged (base `/`, same origin, `web/dist/`). The GitHub Pages app build is retired.
- **Embedding parity with the talk bundles.** The Worker embeds under the model block of the bundles ([contracts/talk-bundle.md](contracts/talk-bundle.md), Embedding conventions): CLS pooling, a talk as `title + "\n" + abstract` with no instruction, and talk search queries with the query instruction. Profile text and people queries are embedded as documents on both sides. `worker/ingest/push-ingest.mjs` refuses to push when the Worker's conventions differ from the bundle model block, and a change of conventions re-embeds every stored vector through the cron and `POST /admin/embed-pending`. Checked against `contracts/fixtures/embedding/reference.v1.json` through the Worker's own code: maximum cosine difference 0.0003 (tolerance 0.02).
- **Contracts v1.** `GET /api/capabilities` serves a tier 2 document (`worker/src/capabilities.js`, public, `max-age=300`). With the `BLE_MASTER_KEYRING` Worker secret, Bluetooth is `derived-v1`: presence with `ble: true` returns `ble_key` and `ble_key_id` once, sightings resolve windows w-1 to w+1 through the reference code in `contracts/js/ble-token.mjs`, answer with `ble_key_id`, and give 403 `ble_rekey` for a retired master. Without the secret it is `server-rotate`. The Phase 4 mitigations (co-location, 10 new people per window and 30 per hour per device, kept in the conference object's SQLite, and a zone only in the requester's own zone) apply to both kinds of token. `node worker/scripts/ble-parity.mjs` checks the Worker's code against the golden vectors and resolution cases in `contracts/fixtures/ble/`.
- **Blocks** belong to the blocker, as on Cloud Run: deleting the blocked profile does not lift a block, the blocks list shows it with `display_name: null`, unblocking by `ref` still works, and the purge removes a block at its `expires_at` (the latest end of the conference and of the two profiles).
- **Unavailable conferences.** When a conference turns unavailable (for example after a failed schedule fetch), its owners can still delete their profile, presence, push subscription and blocks, the admin routes still reach it, and the cron keeps purging its object until it holds no personal data. `push-ingest.mjs` keeps a searchable conference searchable when the weekly fetch of its schedule fails.
- **Source layout:** the backend is `worker/` (`src/`, `ingest/`, `scripts/`, `wrangler.toml`). The Cloud Run server in `server/` is unchanged, and `worker/` is excluded from its image.

## How data stays fresh

- **Talks and conferences:** the workflow `.github/workflows/ingest.yml` runs every Monday at 09:17 UTC and on demand. It discovers upcoming Linux Foundation events and their Sessionize schedules with `scripts/ingest.mjs --dry-run`, then pushes them to the Worker with `worker/ingest/push-ingest.mjs`. The Worker embeds only talks whose text changed, so a rerun costs almost no writes and no neurons.
- **Topic order:** every ingest also recomputes the talk count and the rank of each stored topic, with the rule of the topic builder (most talks first, then label, then topic id), so `GET /api/topics` and the "Common at this conference" chips follow the current counts. The topic ids, labels and aliases stay frozen, because people store topic ids in their profiles. This costs no extra rows written: `PUT /admin/topics` already rewrites the conference's topic rows (at most 150) on every ingest, and the new ranks are part of that write. The only other effect is that a talk whose topics now sort in a different order is sent again with its topics in the new order, so it counts as upserted (one talk row) but is not re-embedded; a typical re-ingest moves a few adjacent topics and so rewrites few talks. `--rebuild-topics` still rebuilds the list from the titles.
- **Only what this run fetched.** `scripts/ingest.mjs --report` lists the conferences the run fetched, and `push-ingest.mjs --events-from` pushes only those. Events that have ended drop off the Linux Foundation's upcoming list, and their `data/` folders in the checkout hold only the committed seed, so the Worker and the bundles keep what the last ingest that saw them pushed, rather than going back to the seed.
- **Talk bundles (one publisher):** the same ingest run then publishes the Pages talk bundles from the same fetched files. `push-ingest.mjs --report` records which conferences reached the Worker, `scripts/stage-ingest-data.mjs` stages exactly those conference files as an artifact (and fails if one of them was not fetched in this run), and the run's `publish` job calls `pages.yml`. The called run checks out the current `main`, not the ingest's commit, so a takedown merged while the ingest ran is applied and an older commit never deploys after a newer one; it lays the staged files over `data/`, rebuilds those conferences from them whatever the live site says (`--fresh`), and builds, verifies and deploys the site. A conference whose talk push failed is not staged, so its bundle does not run ahead of the Worker. Nothing is committed to the repository: `data/` stays a seed. `pages.yml` still runs on pushes to `main`, weekly (Mondays 11:47 UTC, a full re-embed) and by hand, and both kinds of run share the `pages` concurrency group, so two deploys never overlap.
- **Cancelled sessions are dropped.** Sessionize has no cancelled flag in its feed, so organisers cancel a session by retitling it ("CANCELED: ...", "Cancelled - ...", "[Cancelled] ..."). `scripts/lib/classify.mjs` (`isCancelled`) treats a session as cancelled when its status says so or its title starts with that word in any case, and `buildTalks` leaves it out of the talk file. The re-ingest then removes it everywhere: the Worker's finalize step, the Elasticsearch delete step on tier 3 (which runs the same normaliser) and the next bundle build.
- **Takedowns reach the Worker too.** `worker/ingest/push-ingest.mjs` applies `data/takedowns.json` to every talk file with the bundle builder's own `applyTakedowns`, so a talk taken down is not sent (finalize deletes it from the Worker) and a speaker taken down is removed from the talks, topics and facets, exactly as in the bundles. A takedown reaches the Worker the next time the conference is pushed; for a conference the scheduled ingest no longer fetches, run `node worker/ingest/push-ingest.mjs --api "$CADDIE_API_BASE" --event <slug>` from `main`.
- **People who shared for a removed talk.** When finalize deletes a talk, the Worker removes everyone's sharing for it, so no circle is left for a talk that no longer exists, and deletes a profile that is then neither open to meet nor sharing for any talk (a profile exists only while one of those holds). A later profile write that still names the removed talk drops it instead of failing.
- **A short feed cannot erase people's sharing.** Finalize refuses (409, nothing deleted) when it would delete more than 10 talks and more than 10% of a conference's talks, because sharing is not restored when a talk comes back. The ingest run then fails loudly and leaves the Worker as it was. If the schedule really shrank, re-run the ingest by hand with the `allow_shrink` input (`push-ingest.mjs --allow-shrink`).
- **No shared terms gives no topics, and an empty list never replaces a stored one by accident.** A conference where no term reaches three talk titles gets an empty topic list and talks without topics, as in the bundles and on tier 3. The stored list is frozen on every ingest, so it can only become empty through `rebuild_topics` (`--rebuild-topics`). That run stops before any talk or topic is sent when the rebuilt list is empty and the Worker holds topics (the conference upsert has already run), and `PUT /admin/topics` refuses the same change (409, nothing changed), because people store topic ids. Only a run stopped this way leaves the talks' topics as they were: the finalize guard protects the stored list, not the talks' tags, because the talks are sent with their new topic ids (or none) before finalize. If the conference really has no topics, re-run with the `allow_empty` input as well (`push-ingest.mjs --rebuild-topics --allow-empty`), and name that conference in `events`, because the flag applies to every conference in the run. Check the feed before any rebuild: the finalize guard only refuses a feed that loses more than 10 talks and more than 10% of them, so a small conference that loses fewer is rebuilt from the short feed and its new list is stored. A rebuild that gets past the empty check on a feed short enough for finalize to refuse re-tags the talks first, then finalize answers 409, which leaves the old list stored with re-tagged talks until the next ingest without `rebuild_topics` tags them from the stored list again; a rebuild on a schedule that really shrank needs the `allow_shrink` input too.
- **Newer bundles are never replaced by older data.** Every build writes `bundles/sources.json` next to `conferences.json`: for each conference, the bundle's content hash and the `raw_fetched_at` of the schedule it was built from. Every build passes `--live` with the live bundle base, and a conference whose live bundle came from a later fetch than `data/` holds is kept byte for byte instead of being rebuilt, unless a takedown still matches it (`scripts/lib/bundle-sources.mjs`, [BUNDLES.md](BUNDLES.md#which-build-publishes-a-conference)). A record dated more than ten minutes in the future counts for nothing, so a bad deploy cannot pin a bundle. A build that cannot read the live site fails rather than guess. The Pages CDN keeps a file for up to ten minutes and a query string does not get past it, so the build first asks the Deployments API when the latest successful Pages deployment was created, and reads the live `conferences.json` and `sources.json` again every 30 seconds until both carry a `Last-Modified` at least that new (Pages sets it to the deploy time), for up to 15 minutes, then fails (`build-bundles.mjs --live-since`).
- **Cron Trigger** (`*/10 * * * *`): purges expired profiles, expires presence and meets, retries pending embeddings, and adds up the day's usage across conferences. This does not depend on GitHub.
- GitHub disables scheduled workflows after 60 days without repository activity. Run `gh workflow run ingest.yml` to enable it again. The people purge keeps running on Cloudflare in the meantime.

## Free limits and how the app degrades

| Limit (Free plan) | What the app does about it |
|---|---|
| 100,000 Worker requests and 100,000 Durable Object requests a day | Each conference object meters its own requests, rows read and rows written per UTC day (`worker/src/lib/meter.js`), and the cron adds them up. The meter stores additive deltas, never totals: it keeps what it counted since its last write in memory and adds it to the day's row in the `usage_days` table with one UPSERT (`requests = requests + ?`), clearing the deltas only after the write succeeds, so a new instance after an eviction or a deploy never overwrites what an earlier one stored. It writes on its first request, then on the first request 15 seconds or more after the last write or after 100 requests, whichever comes first, and on every `GET /admin/stats` and cron call. It never writes from a timer or an alarm (see the duration row below). An object evicted between two writes loses the counts since its last write: fewer than 100 requests, all within 15 seconds of that write, per idle gap. `GET /admin/stats` and the cron write the deltas before they read, so they report stored totals, and a later reading of the same day never shows less; the pace and the soft caps read the stored totals plus the unwritten deltas. Each write is one written row (measured locally) and includes its own cost, so a conference object busy all day writes up to about 5,760 rows a day for its meter, the same as before, and four searchable conferences write up to about 23,000 (27% of the 85,000 written-rows soft cap). These rows count toward that cap like any other write. Requests the Worker answers without a conference object (`/api/conferences`, `/api/capabilities`, `/api/health`, `/api/push/vapid` and requests it refuses itself) are not metered. Every conference API response carries `X-Caddie-Pace`; those Worker-level responses do not. A response without the header leaves the app's pace unchanged, and the pace falls back to 1 after 30 minutes without a reading. The web app stretches all its polling by that factor before the cap. Polling also slows when the tab is hidden. If the cap is hit anyway, the Worker answers `503 {error:"daily_limit"}` with `Retry-After` until 00:00 UTC; the app says when the people features come back, and the static app (served without running the Worker) and the offline schedule keep working. |
| 10 ms CPU per Worker request | The Worker only routes. Heavy work runs in the Durable Object, where the limit is far higher. |
| 13,000 GB-s of Durable Object duration a day, for the whole account | An object is billed for duration while it is active in memory and cannot hibernate, and a pending `setTimeout` or `setInterval` keeps it from hibernating. The conference and directory objects keep no timers that outlive a request, no alarms and no WebSockets, so an idle object costs no duration. The usage meter does not measure duration, so `X-Caddie-Pace` cannot slow clients to protect it; any change that adds a timer, an interval or an alarm to an object needs its GB-s cost measured first. (A timer that wrote the meter 15 seconds after the last request was tried and dropped: by a review's simulation, at 1 request a second to one object it would have used about 10,100 GB-s a day, 77% of the allowance.) |
| 5,000,000 SQLite rows read a day | Keyword results are cached in memory, queries read row ids first, and near the soft cap (`ROWS_READ_SOFT_CAP`, 3,500,000) search falls back to an in-memory keyword match. |
| 100,000 SQLite rows written a day | Profile search rows are rewritten only when text changes, unchanged talks are not rewritten on ingest, and nudges stop near the soft cap (`ROWS_WRITTEN_SOFT_CAP`, 85,000). |
| 10,000 Workers AI neurons a day | When the quota runs out every route answers with keyword matching only and sets `degraded`. Stored profile and talk vectors are kept, embeddings are made only for changed text, and the cron retries pending ones. |
| Shared venue Wi-Fi IPs | The timer-driven "around now" check uses the larger poll limit, so about 100 people behind one address do not lock each other out. |

`DAILY_REQUEST_BUDGET` (70,000) is the request count after which the pace factor starts to rise. The sizing assumed about 2,000 attendees on one conference day. A conference much larger than that needs the paid Workers plan.

   `setup-secrets.mjs` writes the admin token to the token file, mode 0600: the file `ADMIN_TOKEN_FILE` names, or else `admin-token` in the `caddie-admin` config directory (`configDir` in `scripts/admin/config.mjs`), which is `$CADDIE_ADMIN_HOME/admin-token` when `CADDIE_ADMIN_HOME` is set and `${XDG_CONFIG_HOME:-~/.config}/conference-caddie/admin-token` otherwise (an empty variable counts as unset). The `export` above names the same default for the smoke, which has no default of its own. Before this rule the default was always `~/.config/conference-caddie/admin-token`; if you set either variable and your token is still there, the Worker scripts that read the token file (`setup-secrets.mjs` and `readAdminToken` in `worker/ingest/lib.mjs`) read that old file when the new one is missing and print one line on stderr that names both paths and says, if that file holds this deployment's token, to move it to the new place or set `ADMIN_TOKEN_FILE` to it (with `CADDIE_ADMIN_HOME` keeping a second deployment apart, the old place may hold the other deployment's token). `setup-secrets.mjs` writes only the new place, says so when the old file still exists, and never deletes it. When both files hold different tokens, or the old one exists and cannot be read, the new one is read, with one line that names both paths (never the values). `setup-secrets.mjs` uses the token file for the `--only-missing` GitHub sync and for the recipe it prints for an unfinished rotation only when the file is trusted: `ADMIN_TOKEN_FILE` names it, no different file is at the old place, or both hold the same token. In each of the other cases (the fallback to the old file, two files with different tokens, an old file that cannot be read) it stops with exit 1, changes nothing, names both paths and says to set `ADMIN_TOKEN_FILE` to the file that holds this deployment's token. Two paths that lead to one file through a symbolic link or a hard link count as one file. With `ADMIN_TOKEN_FILE` set there is no fallback, so the `export` above turns it off: if a note named the old place and that file holds this deployment's token, move it to the new place first, or point `ADMIN_TOKEN_FILE` at it.

   The secrets live on the Worker, not in the app build, so a later `deploy.sh` keeps them. The smoke runs against the one origin: `BASE_URL` is the app, the API defaults to the same origin, and the admin token makes it a Worker run. The smoke signs its admin calls by default (`SMOKE_ADMIN_AUTH=signed`), which the Worker requires; `SMOKE_ADMIN_AUTH=bearer` is for a Worker, local or deployed, built from before signed admin requests. Commit the two new QR files through a pull request.
3. Check that the smoke ends with no FAIL, then open the app URL on a phone and scan the new QR code. Migration counts of the live run on 2026-11-11, the same as the last local run: 62 conferences, 717 talks, 114 topics, 898 facets, 132 of 136 people, 0 of 26 reports, 15 of 15 moderation rules.

   The smoke takes the talks it expects from the published Pages bundles (`SMOKE_TALKS=bundle`, the default against the Worker), which the ingest run publishes from the same fetch it pushes to the Worker, so a schedule change upstream no longer fails `x`, `o` or `sch1`. ## Operations runbook

**Redeploy the Worker and the web app.** From the repository root: `bash worker/scripts/deploy.sh`. It builds the app in Worker mode and deploys both together; it is safe to repeat and keeps secrets and data. A change under `web/` reaches phones only through this script. Durable Object migrations are declared in `worker/wrangler.toml`; add a new `[[migrations]]` tag for any new class or schema change, and never edit the `v1` tag.

**Republish the talk bundles.** Push to `main` (any change under `data/`, `config/`, `contracts/`, the bundle builder, the landing page script or `tools/bundles/`) or run `gh workflow run pages.yml`. It does not need the Worker, and the landing page links to `CADDIE_APP_URL` (or says the app is not live yet while that variable is empty). It builds the bundles into `dist-pages/` with `scripts/build-bundles.mjs` (the embedding model is cached by its pinned revision, and a cache miss downloads it once), carries forward the bundle directories the live `conferences.json` names (`scripts/carry-forward-bundles.mjs`), writes the landing page (`scripts/pages-landing.mjs`), checks that nothing else is in the site, and uploads `dist-pages/`. A weekly run on Mondays rebuilds every vector with `--reuse-from none`.

**Rotate the Bluetooth master keyring.** Follow the three steps of [contracts/ble-tokens.md](contracts/ble-tokens.md) (Keys): add the new key as not current, make it current, then retire the old one, each with `npx wrangler secret put BLE_MASTER_KEYRING` (value on standard input only, the JSON `{ "current": "<id>", "keys": { ... } }`). `setup-secrets.mjs` only creates the first keyring and never replaces one.

**Rotate `ADMIN_TOKEN`.** The Worker verifies admin signatures with `ADMIN_TOKEN` and, when `ADMIN_TOKEN_NEXT` is also set (at least 32 characters after trimming), with that one too, so the token can be replaced without a window in which the ingest or the operator's scripts are refused: each step of the script leaves the token file and the repository secret holding a value the Worker accepts. That holds when no rotation is in progress; "A rotation left half done" below covers the one case where it does not (the script then stops). One command starts the rotation and two finish it; the script never prints the value.

```sh
node worker/scripts/setup-secrets.mjs --rotate-admin-token --dry-run   # names only, changes nothing
node worker/scripts/setup-secrets.mjs --rotate-admin-token
```

The second command generates 32 random bytes as hex and, in this order:

1. puts them as `ADMIN_TOKEN_NEXT` on the Worker (`npx wrangler secret put`, value on standard input, no trailing newline). From here the Worker accepts the old and the new token.
2. writes them to the token file (mode 0600; step 2 of [Go live](#go-live-about-10-minutes) says where it is), only after step 1 succeeded, so a failed step 1 leaves the old token in the file.
3. sets the repository secret `CADDIE_ADMIN_TOKEN` to the same value (`--skip-gh` leaves it, and the output then says how to set it).

It then prints the two commands that finish the rotation, with the token file's real path in place of `<token file>`, and does not run them. Run them from `worker/`, in this order, once any running ingest or smoke has finished (a client signs with the token it read when it started):

```sh
cd worker
npx wrangler secret put ADMIN_TOKEN < <token file>    # the new value becomes the ADMIN_TOKEN
npx wrangler secret delete ADMIN_TOKEN_NEXT           # asks you to confirm
```

- **Only this secret.** `--rotate-admin-token` touches nothing else (a run without it would also replace the VAPID pair, which ends every push subscription), needs an `ADMIN_TOKEN` already on the Worker, and cannot be combined with `--only-missing` or `--rotate-ref-salt`. A run without `--rotate-admin-token` that finds an `ADMIN_TOKEN` replaces it outright, with no overlap: if its GitHub step fails the ingest is refused until the secret is set, and the output says so. It uses your Cloudflare credentials like every wrangler call here, so `CLOUDFLARE_API_TOKEN` and `CLOUDFLARE_ACCOUNT_ID` must be set.
- **Order matters.** Run the `put` first and the `delete` only after it succeeded: until then the file and `CADDIE_ADMIN_TOKEN` match `ADMIN_TOKEN_NEXT` only. If the `put` fails, run it again; both tokens keep working. There is no way back to the old token once step 2 has run, because the file and the repository secret then hold only the new one: finish with the two commands.
- **If a step of the script fails**, it says what state that left, in plain words:
  - Step 1 (the Worker): the old token, the file and the repository secret are untouched and keep working. The put may nevertheless have gone through before it failed (a timeout, say); then the Worker holds an `ADMIN_TOKEN_NEXT` that is saved nowhere, and the next run stops and prints the recipe below. Run the same command again.
  - Step 2 (the file): the Worker accepts a new `ADMIN_TOKEN_NEXT` that was saved nowhere, and the old token still works everywhere. Fix the token file's path (`ADMIN_TOKEN_FILE`, or `CADDIE_ADMIN_HOME` or `XDG_CONFIG_HOME` for the default) and run the same command again with `--replace-next` (it would otherwise stop, because `ADMIN_TOKEN_NEXT` is now set), or use the recipe below.
  - Step 3 (the repository secret): the file already holds the new value and `CADDIE_ADMIN_TOKEN` holds the old one (or the new one, if the set went through before it failed), and the Worker accepts either. Run `gh secret set CADDIE_ADMIN_TOKEN --repo <owner>/<name> < <token file>` (printed with the real path and repository), and run the two finishing commands only after it succeeds.
- **A rotation left half done stops the next run.** With `ADMIN_TOKEN_NEXT` already on the Worker the script exits 1 before changing anything, because replacing its value would make the Worker refuse a token file and a repository secret that may hold exactly that value. It cannot read the Worker's or GitHub's secrets, so it cannot tell where the earlier rotation stopped (it may have gone through all three steps, stopped at the GitHub step, stored a value and still failed, or been an earlier `--replace-next` that stopped part-way). It therefore leads with one recipe that is safe wherever it stopped: it makes the value in the token file the only admin token, everywhere. It prints it with the resolved repository and the real path of the token file it read, never the value; that is the old `~/.config/conference-caddie/admin-token` when it fell back to that file (step 2 of [Go live](#go-live-about-10-minutes)), after the one-line note that says so:

  ```sh
  gh secret set CADDIE_ADMIN_TOKEN --repo <owner>/<name> < <token file>
  cd worker
  npx wrangler secret put ADMIN_TOKEN < <token file>
  npx wrangler secret delete ADMIN_TOKEN_NEXT
  ```

  Run the three in this order, once any running ingest or smoke has finished, and only if the token file holds the token your clients should use. Afterwards the Worker accepts the file's value as its `ADMIN_TOKEN`, the repository secret holds it too, `ADMIN_TOKEN_NEXT` is gone, and a new rotation starts normally. If the token file is missing, empty or shorter than 32 characters, the script does not print the recipe (with a bad file it would make the Worker refuse every admin request) and says to stop: put the value you last set back into the file from your own copy and run the command again.

  `--replace-next` is the other way on, for someone who wants to keep rotating without finishing the earlier rotation first. It replaces the `ADMIN_TOKEN_NEXT` that is there. From its first step until the third has run, the token file and the repository secret may hold the old `ADMIN_TOKEN_NEXT`, which the Worker then no longer accepts, so a client that uses them is refused; the output says so at every failure point, and after a put that fails it says the put may have gone through and to run the command again at once. It is refused (exit 2) together with `--skip-gh`, because the repository secret has to be set again, and without `--rotate-admin-token`. With no token file it is also the way out when no copy of the value exists.
- **`--only-missing` stays safe** at every point of a rotation. It never looks at `ADMIN_TOKEN_NEXT`, and only because the Worker accepts both keys during the overlap: while the file and the repository secret hold the value that is still `ADMIN_TOKEN_NEXT`, a run that skips `ADMIN_TOKEN` as already set, or sets a missing repository secret from the file, still leaves every client with a token the Worker accepts.
- **Whitespace.** Every value the script writes has none around it, the Worker trims each secret it reads, and the clients trim what they read.
- **A stale `CADDIE_ADMIN_TOKEN`** after the last command makes every ingest admin call answer 404, and ten bad signatures a minute from one runner address empty the failed-auth bucket for up to a minute (see [worker/README.md](../worker/README.md), Admin requests). The fix is the secret, not the Worker.

Do not rotate `REF_SALT` unless you accept that every person's `ref` changes (`setup-secrets.mjs --rotate-ref-salt`).

**Run your own copy (a fork).** The workflows and scripts below no longer carry the original repository's owner, but a few values still have to be set for a copy; this is the list. The live values for `KurtLehnardt/conferenceCaddie` come out of the defaults unchanged.

- `pages.yml` works out its addresses in its first step: the site `https://<owner lowercased>.github.io/<repository>/`, the bundles under it, and `https://github.com/<owner>/<repository>/issues` for takedown requests. The repository variables `CADDIE_SITE_URL`, `CADDIE_BUNDLE_BASE` (both https and ending in `/`) and `CADDIE_TAKEDOWN_URL` (https or `mailto:`) override them when set. A user site (a repository named `<owner>.github.io`) lives at the root, so set `CADDIE_SITE_URL=https://<owner>.github.io/`.
- `deploy.sh` creates a `workers.dev` subdomain only when the account has none. It asks for `CADDIE_WORKERS_SUBDOMAIN` (lowercase letters, digits and hyphens), and without it uses `conference-caddie-<6 random letters>`. An account that already has a subdomain keeps it.
- `setup-secrets.mjs` writes the GitHub secret to `CADDIE_GH_REPO` (`<owner>/<name>`) or, when that is unset, to the github.com repository that the git remote `origin` of the clone names (https or ssh form, parsed strictly), prints which one before it changes anything, and stops, naming the variable, when it can do neither. It does not use `gh repo view`: in a clone made by `gh repo fork --clone`, which has the original as `upstream`, that names the original, and the secret would go to the wrong repository. `--skip-gh` needs neither.
- `TALKS_BUNDLE_BASE` (a Worker variable, an https address ending in `/`) is the `talks.bundle_base` of the capabilities document. It defaults to `https://kurtlehnardt.github.io/conferenceCaddie/bundles/` (`worker/src/capabilities.js`), so a copy sets it in `[vars]` of `worker/wrangler.toml` to its own bundle address, the same as `CADDIE_BUNDLE_BASE` of `pages.yml`.
- `VAPID_SUBJECT` in `worker/wrangler.toml` is the contact the push services receive (an `https:` URL or a `mailto:` address). It is set to this repository's page: edit it before you deploy your copy. Two leftovers name this repository: `native.yml` passes its issues page as the takedown address of the bundles it builds, and `scripts/pages-landing.mjs` links to it as the source.

**Serve admin requests on a custom domain, or behind Cloudflare Access.** Add `ADMIN_ORIGIN` to `[vars]` in `worker/wrangler.toml`, listing every origin that routes to this Worker, for example `ADMIN_ORIGIN = "https://caddie.example.org,https://conference-caddie.<subdomain>.workers.dev"`, commit it and deploy with `bash worker/scripts/deploy.sh`. Without it the Worker expects a v2 signature for the origin of the request URL it was invoked with. On Cloudflare that URL's host is the host the client sent, limited only to the hostnames whose routes match the Worker, so the fallback is safe for the exact `workers.dev` hostname only; any zone route (a wildcard such as `*.example.org/*` lets a client name any matching subdomain) or custom domain needs `ADMIN_ORIGIN`. Never list another deployment's origin, since a request signed for that deployment would then verify here. An entry that is not a plain `http://` or `https://` origin (a path, a `%`, credentials, the empty entry of a trailing comma) makes every admin request answer 404, v1 included, and the Worker logs `admin config invalid: ADMIN_ORIGIN` without the value.

Security warning: set `ADMIN_ORIGIN` and `ADMIN_SIG_MIN` only in `[vars]`, committed. Never set either from the Cloudflare dashboard or with `wrangler deploy --var`, because `deploy.sh` runs `wrangler deploy`, which replaces the Worker's variables with those of `wrangler.toml`; such a value would vanish at the next routine deploy. `ADMIN_SIG_MIN` must be the quoted string `"1"` or `"2"`; anything else, a TOML number included, makes every admin request answer 404 and logs `admin config invalid: ADMIN_SIG_MIN`.

Security warning: never set `ADMIN_ORIGIN` or `ADMIN_SIG_MIN` with `wrangler secret put` either. A secret survives every deploy and nothing in the repository shows it, so a leftover `ADMIN_SIG_MIN` secret of `"1"` would silently keep v1 open after step d, and a forgotten `ADMIN_ORIGIN` secret that lists a staging origin would make requests signed for staging verify on this Worker. Before each deploy that changes the admin signature (step b, and again before step d), run `npx wrangler secret list` in `worker/`, which prints names only, and check that neither name is there; if one is, remove it with `npx wrangler secret delete <name>` and commit the value in `[vars]` if it is needed.

**Roll back the signed admin requests.** A Worker from before them reads only the bearer, and the clients from that change on send only the signature. Rolling the Worker back therefore means reverting the client part too: revert the merge on `main` (so the weekly ingest sends the bearer again), run `push-ingest.mjs`, `migrate-from-backup.mjs`, `topics-local.mjs` and `moderation.mjs` from the commit before it, and run the smoke with `SMOKE_ADMIN_AUTH=bearer`. Otherwise every ingest and moderation call gets a 404 that looks like a wrong token. The `admin_nonces` table and its index stay in the objects and are harmless to the older code. After a rollback the conference objects stay at `schema_version` 3, so the next schema change must use version 4: a later change that bumps to 3 again would be skipped silently, because `migrate()` (`worker/src/schema.js`) does nothing when the stored version is at least `SCHEMA_VERSION`.

**Add a conference.** Conferences the discovery step knows are picked up by the weekly ingest. To add one now, run `gh workflow run ingest.yml -f events=<slug>`, or from a clone run `node scripts/ingest.mjs --event <slug> --dry-run --skip-topics` followed by `node worker/ingest/push-ingest.mjs --api "$CADDIE_API_BASE" --event <slug>` (with `ADMIN_TOKEN_FILE` set). A conference with a hand-made schedule needs its `data/<slug>/conference.json` and talk file committed first. The Worker refreshes its copy of the conference list every 5 minutes.

**Remove a conference.** A signed `DELETE /admin/conference?event=<slug>` first writes a tombstone in the directory, so the weekly ingest cannot bring the conference back (`PUT /admin/conferences` skips the slug and answers it in `skipped_retired`, and `push-ingest.mjs` and `migrate-from-backup.mjs` log it by name and send nothing more for it). It then empties the conference's Durable Object (talks, topics, facets, people and everything connected to them, reports and the usage meter), and last deletes the conference from the directory. The object keeps only its replay nonces and these `meta` rows: `schema_version`; `retired_at`, the marker that makes it refuse a late conference document and every admin write until the conference is unretired; and `wipe_seq` and `unretire_seq`, the order numbers below. The next meter write recreates a `usage_days` row for the requests that still reach it. A second removal is harmless and answers zero counts with `already_retired_at`. If the answer is `removal_incomplete`, the tombstone is in place and a step after it failed: send the same removal again until it answers 200. Remove a conference well away from the daily written-rows limit, because the wipe deletes every row of the conference (several thousand for a large one) and each deleted row counts as written, never while an ingest run is pushing it, and never unretire it while its removal is running. If the two do overlap, the later of them wins everywhere, by the order in which the directory committed them: each removal (at its tombstone step) and each unretire takes the next number of a sequence the directory keeps, the object takes an unretire only when its number is above its last wipe's and refuses a wipe whose number is below the last unretire it took, and the directory deletes the conference row only when no unretire came after the removal. The conference therefore ends either removed or live, never as a live object that no directory row names. A removal that loses answers `409 removal_superseded` (step `wipe` when nothing was deleted, step `directory` when the object was emptied first) and leaves the conference live; an unretire that loses, or whose document did not reach the object, answers `502 unretire_incomplete` with its `cause`, and sending it again makes it the later one. When the unretire's fan-out hit the daily limit the answer is `503` with `cause` `daily_limit` instead; wait for the reset. An automatic retry is a new, later request: `adminClient` repeats a removal that answered a 503 other than `daily_limit`, so a retried removal can undo an unretire the operator ran in between. It also repeats an unretire that answered 502, so a removal that answered 200 can be undone by the unretire's hidden retry, and both operators then see 200. When the unretire carries the `expect_status` precondition with `null` (no row, a finished removal), the row its first attempt stored makes that retry answer `409 status_mismatch` and change nothing, and `adminClient`'s error says that an earlier attempt answered 502 and may have been applied; repeat the unretire without `expect_status` until it answers 200 (see [worker/README.md](../worker/README.md), Operator routes). A removal that finished between the two attempts deleted that row, though, so the retry matches again and still wins. After any overlap, check the conference's state (`GET /api/conferences` lists it only while the directory has its row; a signed `GET /admin/stats?event=<slug>` answers `400 conference is not available` once it is removed) and run the operation you intended again. Neither check can tell a live conference from one whose directory row exists while its object is still marked as removed, which is what an unretire that answered 502 or 503 and was not repeated leaves: both list the conference and answer the stats. So repeat an unretire until it answers 200. For up to 5 minutes the Worker's directory cache can still name the slug, and requests for it answer `400 conference is not available`. The Pages bundles and tier 3 keep a removed conference out through `data/conference-operator.json` and a retired `data/<slug>/conference.json`, which `caddie-admin conferences remove` writes. To bring it back, send its document with `"unretire": true` (`caddie-admin conferences unretire --event <slug>`, or the command in [worker/README.md](../worker/README.md) (Operator routes)), then run `gh workflow run ingest.yml -f events=<slug>`. The removal deletes personal data for good; there is no undo other than people making their profiles again.

**Re-run the migration.** The migration is repeatable: `node worker/ingest/migrate-from-backup.mjs --backup <dir> --api "$CADDIE_API_BASE"`, with `--dry-run` first. It ends with a summary naming every conference it skipped, and exits 3 when a conference was skipped because the Worker answered `conference is not available` (its data was not all sent; check that the Worker lists it, then run the migration again), 0 when everything was sent or only removed conferences were skipped, 2 when a request failed, and 1 on a usage error. It never sends an `unretire` key from the backup. Conferences, talks, topics and facets are upserted, sample profiles are copied and re-embedded, and presence, location and Bluetooth fields are never copied. Only sample profiles are copied by default; `--include-real` also copies real profiles, whose owners cannot edit them from the Worker's origin, because their device secrets live on the old origin. The backup holds personal data and stays in the git-ignored `data/exports/`.

**Moderation.** `node scripts/caddie-admin.mjs moderation queue --event <slug>`, with a tier 2 backend, lists what two reports, or the operator, have hidden. See [worker/README.md](../worker/README.md) (Moderation) and [ADMIN_CLI.md](ADMIN_CLI.md) for undo, delete and purge. `worker/scripts/moderation.mjs` is deprecated: it only prints the `caddie-admin` command to use and exits 2. The operator routes there (Operator routes) find people by name or ref, show one person's flags and counts (and, on request, their profile text and contact), and block a profile or hide a spot line with an operator report that keeps it hidden through the owner's writes and a re-creation from the same device. The word list is compiled into the Worker, so changing `config/moderation-words.json` needs a deploy.

**Logs and CPU.** The Worker writes one line per request and never a body, header value or query text. Run `wrangler tail` only through the filter described in `worker/README.md`, because raw output can show device secrets. `GET /admin/stats?event=<slug>`, signed with the admin token, returns row counts and the day's usage meter. Each such reading writes at least two rows, the request's nonce and the meter's unwritten counts, and deletes the nonces older than 15 minutes, so it reports stored totals. Because of the nonce it needs written rows: once the account's daily written-rows limit is reached it answers `503 daily_limit`, like every admin route, until 00:00 UTC, and the cron's readings are what remains.

**Before every commit,** check the staged diff for secret values without printing them (the procedure is in `worker/README.md`), and make sure nothing under `data/exports/` and no `.dev.vars` file is staged.

## Known gaps

- **No CPU reading yet.** The live smoke passed, but nobody has read the deployed Worker's CPU time or a full day of the usage meter yet.
- **The usage meter can undercount, but never goes backwards.** A conference object evicted between two meter writes loses the counts since its last write: fewer than 100 requests, all within 15 seconds of that write, per idle gap (the meter has no timer, so an idle object keeps those counts in memory until its next request, reading or cron call). Those counts were never in any reading, so readings of the same day only grow, but the cron's totals and the pace can be that much too low. If a meter write fails (for example at the daily written-rows limit), the reading is the stored row read back, without the unwritten counts; if that read fails too, it is the last stored total the object saw, marked `stale: true`, which another instance may since have passed.
- **A rollback of the meter change restarts the day from older totals.** The new meter keeps the old `meta.usage` totals in place, so a redeploy of a version from before `usage_days` starts the day from the totals it last wrote there, not from zero, but its readings drop by what the new meter counted since, for the rest of that UTC day.
- **The `/admin/test/*` fixtures are off on a deployed Worker.** The four routes the smoke uses to make and age a fixture profile and to restart the usage meter (`POST` and `DELETE /admin/test/profile`, `POST /admin/test/age-presence`, `POST /admin/test/meter-restart`) answer 404, even to a correctly signed request, unless the Worker variable `ADMIN_TEST_ROUTES` is the string `"1"`. `wrangler.toml` does not set it, so against the deployed Worker the smoke prints SKIP, naming the variable, for the checks that need a fixture (`meter1`, the expired profile, the aged presence and `unav1`) instead of FAIL, once it sees that `GET /admin/stats` answers 200 with the same credentials; `worker/scripts/dev-vars.mjs` writes `ADMIN_TEST_ROUTES=1` into `.dev.vars`, so a local run keeps every check. To run them against the deployed Worker, deploy once with the variable (`cd worker && npx wrangler deploy --var ADMIN_TEST_ROUTES:1`, with `web/dist-worker/` built by an earlier `deploy.sh`), run the smoke, and deploy again without it (`bash worker/scripts/deploy.sh`; wrangler replaces the Worker's variables with those of `wrangler.toml` on every deploy). Set it only as a deploy-time variable, never with `wrangler secret put`: a secret survives every deploy, so the fixtures would stay on until someone deleted it. After pulling this change, re-run `npm --prefix worker run dev-vars` (or add `ADMIN_TEST_ROUTES=1` to an existing `worker/.dev.vars`), or the local smoke silently skips its fixture checks. While it is on, `meter1` starts a new usage meter on the primary conference and drops the counts the meter has not written yet (at most 15 seconds of real traffic on a deployed Worker) and touches nothing else.
- **A short window after each ingest.** The Worker has the new schedule as soon as the push ends, and the bundles a few minutes later, when the same run's Pages deploy ends (longer when the build waits for the CDN to show the previous deploy); Pages then caches `conferences.json` for up to ten minutes. A smoke run in that window can fail `bun1`, `x`, `o` or `sch1`. Run it again once the deploy has finished.
- **A queued publish can be cancelled.** GitHub keeps at most one pending run per concurrency group: when a Pages deploy is running and two more runs queue in the `pages` group (for example an ingest's publish and a push to `main`), the older pending one is cancelled. When the cancelled one is a `pages.yml` run of its own, nothing is lost: the ingest's publish builds from the `main` of the moment it starts, so it carries that commit. When it is the ingest's publish, its bundles are not published until the next ingest run, and the Worker is ahead of the bundles until then; the smoke's `bun1` shows it. Rerun the cancelled `publish` job, or the ingest.
- **Kept bundles wait for the next fetch.** A bundle that the ingest built from a newer fetch is kept as it is by later `pages.yml` runs, so a change to the bundle builder, and the weekly full re-embed, reach it only when an ingest fetches that conference again (the scheduled ingest re-embeds what it refreshes from scratch). A conference that has ended is never fetched again, so its last ingest bundle stays as it is for good. A takedown is the exception: a kept bundle that a takedown in `data/takedowns.json` still matches is rebuilt from `data/` instead. To retire a kept bundle, see [BUNDLES.md](BUNDLES.md#retiring-a-conference).
- **The first re-embed after a migration repeats the profiles.** The marker of the embedding conventions is written by the first `POST /admin/embed-pending` or cron run, not by the migration, so that first run marks every profile with text as pending and embeds it again (132 profiles on 2026-11-11, about 25 per call or cron run). Talks are not repeated. It costs a little of the daily Workers AI allowance once per conference.
- **People vectors are server-side.** The capabilities document says `people.semantic: server` and `people.live: poll`: client-computed profile vectors and the WebSocket channel of the tier 2 fixture are not implemented.
