# Operator checklist: from `main` to `then/integration`

The exact steps, in order, to take the live service from what `main` deploys to this branch: the Find & connect MVP, GPS bands, reports, the percolator rules (and the optional classifier, off by default), in-app and push nudges, the filter's hold, "Home is Around", and the Android companion's Bluetooth proximity. Every step names the env vars it reads and never a value. Run everything from the repository root on this branch with Node 26 and `gcloud` signed in to the project in `docs/CONTRACT.md`.

Rules that apply to every step: keys are passed inline (`VAR="$OTHER_VAR" command`) or through the shell's environment, never written to a file, never printed, never `set -x`. The admin key `ELASTISEARCH_API_KEY` is used by the CLI only and is never deployed. Each setup script is idempotent: running it again changes nothing.

| # | Step | Command | Env it reads |
|---|---|---|---|
| 1 | Install the root dependency (`web-push`, pinned) and the web app's. | `npm ci && npm --prefix web ci` | none |
| 2 | People index: add the new fields (`ref`, the presence fields, `presence_location`, `presence_accuracy`, `presence_spot_pending`, `ble_token`, `ble_token_until`, the unindexed `pending_about`, `pending_interests` and `pending_expertise`) with an additive `PUT _mapping`. | `npm run people:setup` | `ES_URL` (default: the deployment), `ES_PEOPLE_API_KEY` or `ELASTISEARCH_API_KEY` |
| 3 | Write `ref` on people documents from before the field existed. `REF_SALT` must equal what the service runs with (`deploy.sh` sets none, so leave it unset too). `--dry-run` first if in doubt. | `npm run people:backfill-ref` | `ES_URL`, `ES_PEOPLE_API_KEY` or `ELASTISEARCH_API_KEY`, `ES_PEOPLE_INDEX` (default `caddie-people`), `REF_SALT` (optional) |
| 4 | Reports index, plus `hidden` and `spot_hidden` on people and `hidden` on meets. | `npm run reports:setup` | `ES_URL`, `ES_PEOPLE_API_KEY` or `ELASTISEARCH_API_KEY`, `ES_PEOPLE_INDEX`, `ES_PEOPLE_MEETS_INDEX` (default `caddie-people-meets`) |
| 5 | Rules index (percolator) and its rules from `config/moderation-words.json`. Without it the server's in-process wordlist decides, so the app works either way. `rules:reload` requires `ELASTISEARCH_API_KEY` and refuses to run without it, even when `ES_PEOPLE_API_KEY` is set, so the plain command is safe. It writes the new rules first (stable ids, `refresh=wait_for`, every result confirmed) and only then finds and deletes the rules that are not in the new set, so a reload never empties an index that holds rules; an empty wordlist or a failed write keeps the old rules and exits non-zero. Caveat: after a fresh `rules:setup` the index holds no rules, and if the first reload fails it stays empty; the script then prints a warning, and the server falls back to its wordlist while the index is empty. Run one reload at a time. | `: "${ELASTISEARCH_API_KEY:?}" && npm run rules:setup && ELASTISEARCH_API_KEY="$ELASTISEARCH_API_KEY" npm run rules:reload` | `ES_URL`; `rules:setup`: `ES_PEOPLE_API_KEY` or `ELASTISEARCH_API_KEY`; `rules:reload`: `ELASTISEARCH_API_KEY` only |
| 6 | Push subscriptions and nudge records indices. | `npm run push:setup` | `ES_URL`, `ES_PEOPLE_API_KEY` or `ELASTISEARCH_API_KEY` |
| 7 | VAPID pair for push nudges, once per project. The script writes `vapid-public.key` and `vapid-private.key` (git-ignored) to the current directory and prints the two `gcloud secrets create` commands for `caddie-vapid-public` and `caddie-vapid-private` and the `rm`; run those three as printed. It prints no key value. Skip this step to deploy with nudges off. | `npm run push:vapid-keys` then the printed `gcloud secrets create ... --data-file` commands and `rm vapid-public.key vapid-private.key` | none for the script; `gcloud` uses the signed-in account |
| 8 | Optional: the text classifier. It is off by default (`MOD_CLASSIFIER=off` in the server and in `deploy.sh`) because the Natural Language API bills outside the approved services and the classifier fails closed. To turn it on later: enable the API once per project (no key, no IAM role: the service calls it with `caddie-runtime`'s own token) and set `MOD_CLASSIFIER=auto` in `scripts/deploy.sh` before step 10. | `gcloud services enable language.googleapis.com --project project-9205d6eb-366e-4844-b77` | none |
| 9 | Optional: a read-only, public-scope GitHub token in Secret Manager `caddie-github-token` raises the profile import's limit from 60 to 5000 requests an hour. The deploy mounts it only when it exists. | `gcloud secrets create caddie-github-token --project project-9205d6eb-366e-4844-b77 --replication-policy automatic --data-file <file holding the token>` then delete that file | none |
| 10 | Deploy. The script mounts `caddie-es-readonly` as `ES_API_KEY`, `caddie-es-people` as `ES_PEOPLE_API_KEY`, `caddie-vapid-private` as `VAPID_PRIVATE_KEY` and `caddie-github-token` as `GITHUB_TOKEN` (each only when it exists), reads `caddie-vapid-public` into `VAPID_PUBLIC_KEY`, sets `ES_URL`, `ES_INDEX`, `ES_RULES_INDEX`, `MOD_CLASSIFIER`, `MOD_REJECT`, `MOD_HOLD`, `MOD_TIMEOUT_MS`, `BLE_NEAR_RSSI` and `VAPID_SUBJECT`, grants `caddie-runtime` access to those secrets alone, and runs `gcloud run deploy --source .`. `SERVICE=conference-caddie-test npm run deploy` deploys a second service for testing without touching the live one. | `npm run deploy` | from the shell, optional: `SERVICE` (default `conference-caddie`), `VAPID_SUBJECT` (a `mailto:` address; default the repository URL), `BLE_NEAR_RSSI` (default `-75`) |
| 11 | Smoke test against the deployed URL that step 10 printed. It creates and deletes its own test profiles. | `BASE_URL=<the service URL> npm run smoke` | `BASE_URL`; `ES_URL` and `ES_PEOPLE_API_KEY` or `ELASTISEARCH_API_KEY` for the one expired-profile document it writes and removes; `SMOKE_SKIP_BUNDLE=1` only when `web/dist` was not built locally; `SMOKE_STRICT=1` (default off) also fails the run when any request answered 5xx or failed on its first attempt (the `NOTE` lines), even if the retry passed. Check `l0` reads each accepted profile write back through `POST /api/circles/members` and samples the requested and dropped talks against what is stored (a status it cannot interpret is reported as inconclusive, not as a mismatch) |
| 12 | Android APK: nothing to run here. The GitHub Actions workflow `.github/workflows/android-apk.yml` builds the debug APK on every push to an `android/**` branch and keeps it as a workflow artifact; it bakes in `VITE_API_ORIGIN` (the service URL) at build time. To build after this merge, push this branch's tree to an `android/**` branch, or run the workflow manually. `docs/ANDROID.md` has the local build steps. | none | none |

After step 10, check once that the Cloud Run revision's env has no `VAPID_PRIVATE_KEY` or key value in plain text (`gcloud run services describe conference-caddie --region us-west1 --format yaml` shows secrets by name only) and that the last log lines carry only method, path, status and duration.

After the conference: `npm run people:purge` (deletes expired profiles, presence, meets, push subscriptions and nudge records; env `ES_URL`, `ES_PEOPLE_API_KEY` or `ELASTISEARCH_API_KEY`) and `node scripts/moderation.mjs --event <slug> --purge` (deletes the reports; `ELASTISEARCH_API_KEY`).

What is not in this list, on purpose: `npm run es:setup`, `npm run ingest`, `npm run topics` and `node scripts/build-facets.mjs` are `main`'s own steps and the live indices already carry their data; `scripts/create-es-keys.mjs` was run for the two Elasticsearch keys (and re-run on `main` when the read key gained `caddie-facets*` and the pipeline-simulate action), so it is not needed again. If the live read key predates that re-mint, run it once with `ELASTISEARCH_API_KEY` before step 10. The people key keeps `read`, `write` and `view_index_metadata` on `caddie-people*`, and the server needs no refresh privilege with it: the server deletes by searching for the ids and sending a Bulk delete with `refresh=wait_for` (DECISIONS.md, "Deletes without the refresh privilege"). A 502 on smoke q8 or q9 after a 403 in the log means the deployed revision predates that change; redeploy from `main` rather than widening the key. Some operator scripts delete with `_delete_by_query?refresh=true`, which the people key cannot refresh, so they require `ELASTISEARCH_API_KEY` and exit with a clear message when it is missing: `npm run people:seed` (the sample cleanup uses the admin key; it still writes the new samples with `ES_PEOPLE_API_KEY` when that is set), and `node scripts/moderation.mjs --unhide` and `--purge`. `moderation.mjs --hidden`, `--since` and `--delete` and `rules:reload`'s `--test` still run with the people key alone. `npm run rules:reload` is in step 5.
