# Operator checklist: from `main` to `then/integration`

The exact steps, in order, to take the live service from what `main` deploys to this branch: the Find & connect MVP, GPS bands, reports, the percolator rules (and the optional classifier, off by default), in-app and push nudges, the filter's hold, "Home is Around", the Android companion's Bluetooth proximity, and native push to the official apps. Every step names the env vars it reads and never a value. Run everything from the repository root on this branch with Node 26 and `gcloud` signed in to the project in `docs/CONTRACT.md`.

Rules that apply to every step: keys are passed inline (`VAR="$OTHER_VAR" command`) or through the shell's environment, never written to a file, never printed, never `set -x`. The admin key `ELASTISEARCH_API_KEY` is used by the CLI only and is never deployed. Each setup script is idempotent: running it again changes nothing.

| 7a | Optional, **official deployment only**: native push to the official iOS and Android apps (APNs and FCM, `server/native-push.mjs`). A third-party operator skips this step, never creates these two secrets and leaves `FCM_PROJECT_ID` empty: the deploy then mounts nothing, and `/api/capabilities` answers `push.apns: false` and `push.fcm: false`, as the live service does today. **APNs:** in Apple Developer, Certificates, Identifiers & Profiles, then Keys, create a key with "Apple Push Notifications service (APNs)" enabled and download `AuthKey_<KEY ID>.p8` (Apple lets you download it once). Note its Key ID (10 characters, shown with the key) and the Team ID (10 characters, Membership details). One key serves both the production and the sandbox environment and every app of the team; the server sends to the bundle id `app.conferencecaddie` (`APNS_BUNDLE_ID` in step 10 changes it). Store the file as `caddie-apns-key` and the two ids, which are not secret, as `caddie-apns-ids` in the form `<KEY ID> <TEAM ID>`; then delete the downloaded file or move it to the team's password manager. **FCM:** there is no key to create, export or store. The server sends with the access token the Cloud Run metadata server issues for the runtime service account `caddie-runtime`, asked for with the one scope FCM's `messages.send` needs (`https://www.googleapis.com/auth/firebase.messaging`), so this step only links a Firebase project and grants one role. In the Firebase project the Android app `app.conferencecaddie` is registered in (simplest: add Firebase to this Google Cloud project, so the service and Firebase share one project), enable the Firebase Cloud Messaging API (V1) and grant `caddie-runtime` the role Firebase Cloud Messaging API Admin (`roles/firebasecloudmessaging.admin`, which holds `cloudmessaging.messages.create`, the permission `messages.send` needs) on that project. When the Firebase project is another Google Cloud project, enable the API in this project too, because a service account's own project is the quota project of its calls (as for the classifier in `scripts/deploy.sh`). Then set `FCM_PROJECT_ID` in `scripts/deploy.sh` to the Firebase project id (it is not a secret) and commit it, so every deploy keeps FCM on. **Rotating:** add the new `.p8` as a version of `caddie-apns-key` and its ids as a version of `caddie-apns-ids`, deploy (step 10 reads both at once), then revoke the old key in Apple Developer. FCM has nothing to rotate. | APNs: `gcloud secrets create caddie-apns-key --project project-9205d6eb-366e-4844-b77 --replication-policy automatic --data-file AuthKey_<KEY ID>.p8` then `printf '%s %s' <KEY ID> <TEAM ID> \| gcloud secrets create caddie-apns-ids --project project-9205d6eb-366e-4844-b77 --replication-policy automatic --data-file=-`. | 9a | Bluetooth derived tokens (`ble.mode` `derived-v1`, docs/contracts/ble-tokens.md): the master keyring in Secret Manager `caddie-ble-master`. The script creates the secret, generates a 32-byte master with a dated id, and writes the keyring as a new version through `gcloud`'s standard input; it never prints, logs or writes a key value, and it refuses to run `--init` when the secret already holds a keyring. Until this secret exists the deploy mounts nothing, and the server keeps advertising the legacy `server-rotate` mode with the mitigations on. The legacy rotate route and its tokens keep working in both modes, so the old APK is unaffected. Rotating it later is three steps with a deploy after each, see "Rotating the Bluetooth master" below. `--status` shows the key ids of the latest version and of the version the service runs with. | `node scripts/ble-master.mjs --init` then `node scripts/ble-master.mjs --status` | none (`gcloud` signed in to the project; `--project <id>` overrides the default project) |
| 10 | Deploy. The script mounts `caddie-es-readonly` as `ES_API_KEY`, `caddie-es-people` as `ES_PEOPLE_API_KEY`, `caddie-vapid-private` as `VAPID_PRIVATE_KEY`, `caddie-github-token` as `GITHUB_TOKEN`, `caddie-ble-master` as `BLE_MASTER_KEYRING` and `caddie-apns-key` as the file `/secrets/apns/AuthKey.p8` of a secret volume (named by the plain env var `APNS_KEY_FILE`), both pinned to their latest enabled version at deploy time (each only when it exists), reads `caddie-vapid-public` into `VAPID_PUBLIC_KEY` and, with the APNs key, `caddie-apns-ids` into `APNS_KEY_ID` and `APNS_TEAM_ID`, sets `ES_URL`, `ES_INDEX`, `ES_RULES_INDEX`, `MOD_CLASSIFIER`, `MOD_REJECT`, `MOD_HOLD`, `MOD_TIMEOUT_MS`, `BLE_NEAR_RSSI`, `VAPID_SUBJECT`, with the APNs key `APNS_BUNDLE_ID`, and `FCM_PROJECT_ID` when it is set, grants `caddie-runtime` access to those secrets alone, and runs `gcloud run deploy --source .`. `SERVICE=conference-caddie-test npm run deploy` deploys a second service for testing without touching the live one. | `npm run deploy` | from the shell, optional: `SERVICE` (default `conference-caddie`), `VAPID_SUBJECT` (a `mailto:` address; default the repository URL), `BLE_NEAR_RSSI` (default `-75`), `APNS_BUNDLE_ID` (default `app.conferencecaddie`), `FCM_PROJECT_ID` (default: the value in `scripts/deploy.sh`, empty until step 7a) |
| 11 | Smoke test against the deployed URL that step 10 printed. It creates and deletes its own test profiles. Their words are synthetic (made-up tokens with the run's tag, in about, interests, expertise and the people searches) and they carry no topic but the common one, which only makes a broad match; the three that turn presence on keep interests and expertise empty while they are around. So they share no word or specific topic with a real attendee, and no real attendee can be nudged about one of them or the other way round, although they run against the live conference and its real zones. While the run lasts, a visible test profile with text can at most show up far down someone's list as a weak semantic neighbour. | `BASE_URL=<the service URL> npm run smoke` | `BASE_URL`; `ES_URL` and `ES_PEOPLE_API_KEY` or `ELASTISEARCH_API_KEY` for the one expired-profile document it writes and removes; `SMOKE_SKIP_BUNDLE=1` only when `web/dist` was not built locally; `SMOKE_STRICT=1` (default off) also fails the run when any request answered 5xx or failed on its first attempt (the `NOTE` lines), even if the retry passed. `SMOKE_NATIVE_PUSH` (default unset) names the native push platforms the service should push to (`none`, or `apns` and/or `fcm`, comma-separated); check `np2` then compares `push.apns` and `push.fcm` with it, and unset it passes when both are false and is skipped when one is true. Check `np3` registers a made-up token only for a platform whose flag is false, where the answer must be 404 `push_unavailable`. Check `l0` reads each accepted profile write back through `POST /api/circles/members` and samples the requested and dropped talks against what is stored (a status it cannot interpret is reported as inconclusive, not as a mismatch) |

After step 10, check once that the Cloud Run revision's env has no `VAPID_PRIVATE_KEY`, `BLE_MASTER_KEYRING` or key value in plain text and that `caddie-apns-key` appears only as a secret volume mounted at `/secrets/apns` (`gcloud run services describe conference-caddie --region us-west1 --format yaml` shows secrets by name only) and that the last log lines carry only method, path, status and duration. After step 9a and step 10, `curl -s <the service URL>/api/capabilities` answers `"mode":"derived-v1"` inside `ble`; without the secret it answers `"mode":"server-rotate"`. After step 7a and step 10 it answers `"apns":true` and `"fcm":true` inside `push`; a channel whose settings are unusable stays false, and the revision's log has one line `APNs push is off: ...` or `FCM push is off: ...` that names the setting, never its value (`APNs push is off: APNS_KEY_FILE names no readable file.` means the key file is not mounted, or not readable by the container's user). A true flag means configured and well-formed, not accepted: when Apple or Google refuse the credentials five times in a row (a revoked `.p8` key, a wrong team id, a missing FCM role binding), the instance turns that flag false, logs `APNs push is off: 5 authentication failures in a row.` (or `FCM`), and stays so until the next deploy or instance start; fix the key or the binding and deploy. A server whose keyring is unusable, for example one whose current id is not among its keys, refuses to start, so the new revision fails its health check and the previous revision keeps serving.

**Rotating the Bluetooth master.** Each step is completed on every instance before the next one starts, so that no instance issues a session under a master that another instance does not hold. The deploy pins the newest enabled keyring version, so a change reaches the instances only with a deploy, and the script checks the version the service runs with: it refuses `--promote` until the deployed keyring holds the key, and `--retire` while the key is still current there, and both while the latest revision is not ready or traffic goes to another revision.

1. `node scripts/ble-master.mjs --add-next`, then `npm run deploy`. The new master is held everywhere but not used yet.
2. `node scripts/ble-master.mjs --promote <new id>`, then `npm run deploy`. New sessions are issued under it.
3. Once the sessions of the old master have ended (at the latest after the conference day), `node scripts/ble-master.mjs --retire <old id>`, then `npm run deploy`. A device whose session was issued under the retired master gets 403 `ble_rekey` and fetches a new key with its next presence write.

After a leak, run the three steps one after another, each with its deploy, without waiting for the old sessions to end before step 3, and then destroy every version of `caddie-ble-master` older than the one `--retire` added, because those still hold the leaked master (`gcloud secrets versions list caddie-ble-master --project project-9205d6eb-366e-4844-b77`, then `gcloud secrets versions destroy <version> --secret caddie-ble-master --project project-9205d6eb-366e-4844-b77` for each older version). `node scripts/ble-master.mjs --status` lists the key ids and which one is current, never a key.

After the conference: `npm run people:purge` (finishes profile deletes that failed part-way, and deletes expired profiles, presence, meets, push subscriptions and native push registrations, nudge records and blocks; env `ES_URL`, `ES_PEOPLE_API_KEY` or `ELASTISEARCH_API_KEY`) and `node scripts/moderation.mjs --event <slug> --purge` (deletes the reports; `ELASTISEARCH_API_KEY`).

What is not in this list, on purpose: `npm run es:setup`, `npm run ingest`, `npm run topics` and `node scripts/build-facets.mjs` are `main`'s own steps and the live indices already carry their data; `scripts/create-es-keys.mjs` was run for the two Elasticsearch keys (and re-run on `main` when the read key gained `caddie-facets*` and the pipeline-simulate action), so it is not needed again. If the live read key predates that re-mint, run it once with `ELASTISEARCH_API_KEY` before step 10. The people key keeps `read`, `write` and `view_index_metadata` on `caddie-people*`, and the server needs no refresh privilege with it: the server deletes by searching for the ids and sending a Bulk delete with `refresh=wait_for` (DECISIONS.md, "Deletes without the refresh privilege"). A 502 on smoke q8 or q9 after a 403 in the log means the deployed revision predates that change; redeploy from `main` rather than widening the key. Some operator scripts delete with `_delete_by_query?refresh=true`, which the people key cannot refresh, so they require `ELASTISEARCH_API_KEY` and exit with a clear message when it is missing: `npm run people:seed` (the sample cleanup uses the admin key; it still writes the new samples with `ES_PEOPLE_API_KEY` when that is set), and `node scripts/moderation.mjs --unhide` and `--purge`. `moderation.mjs --hidden`, `--since` and `--delete` and `rules:reload`'s `--test` still run with the people key alone. `npm run rules:reload` is in step 5.
